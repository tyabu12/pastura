# ADR-020: Backward-Compatibility Strategy for Shared Scenarios Across Engine Breaking Changes

> **Status:** Proposed
> **Date:** 2026-07-04
> **Context:** Pastura is heading toward its first App Store release, after
> which app versions in the field diverge from the curated Shared Scenarios
> gallery (`gallery.json`, read-only feed; #87/#93). A scenario authored to use
> an engine capability added in a *later* app version — most concretely a new
> `PhaseType` — will reach an **older installed app** that cannot execute it.
> Today that mismatch is handled only by accident: `PhaseType` is a `String`
> enum with no `unknown` case, so `ScenarioLoader.parsePhaseType` throws on an
> unrecognized type, and the gallery install path (`SharedScenariosViewModel`
> `tryInstall`) surfaces the throw as `.networkError("Failed to parse gallery
> YAML: …")` — a **misleading message**, with no grey-out and no "update the
> app" guidance. There is no version field on `Scenario`, no engine-capability
> constant, and the gallery envelope's own `GalleryIndex.version` is decoded but
> **never checked** (dead metadata). This ADR decides the compatibility contract
> *before* the first release, while the installed base is still zero, so no
> shipped app predates the mechanism.

---

## 1. Decision

Adopt a **two-layer hybrid gate**, evaluated against a single monotonic engine
capability version, that greys out incompatible gallery scenarios at
index-display time and guides the user to update — never runs a partial or
silently-wrong simulation, and never requires launch-time network.

### D1. `ENGINE_SCHEMA_VERSION` — a monotonic integer capability version

Introduce `ENGINE_SCHEMA_VERSION: Int` in the **Engine** layer as the single
authoritative declaration of "what capabilities this build's engine can
execute." It is a plain monotonic counter, **not** semver — the only comparison
anyone performs is `appVersion >= scenarioRequirement`, so ordinal semantics are
unneeded and semver's minor/patch distinction would only invite confusion.

Engine is the correct home because bumping it is coupled to engine feature
additions (a new phase handler under `Engine/Phases/`, a new `ScoreCalcLogic`
under `Engine/ScoringLogic/`). The App layer — which may depend on everything —
reads the constant to drive the gate; the Models-layer capability enums
(`PhaseType`, `ScoreCalcLogic`, `AssignTarget`, `PairingStrategy`) it stands for
are what actually get parsed. No dependency-rule violation: App→Engine and
App→Models are both allowed.

### D2. Primary gate — capability-derived phase check (automatic)

For each gallery entry, compare its index-level `phases: [String]?`
(`GalleryScenario.phases`) against the raw values of `PhaseType.allCases`. If any
listed phase kind is unknown to this build, the scenario is **incompatible** and
greyed out. This needs **no YAML download** — `phases` is already denormalized
into the index (it drives the Browse-tab art-tile signature glyph via
`GalleryCatalogRowFormat.signaturePhase(phases:)`) — and the *client* half is
drift-proof, because `PhaseType.allCases` is the build's real capability set, not
a hand-maintained list.

**Honest framing (do not overstate).** The `phases` array the gate reads is
itself a *curation-authored, optional* field. The gate is drift-proof on the
client side only; on the data side it shares the same authoring risk this ADR
otherwise ascribes to D3 — a curator who omits the new phase from `phases` is
often the same one who forgets to raise `min_engine_version`. Two consequences,
both load-bearing:

- **D2a. `phases` MUST be the fully-flattened phase-kind set, including
  `conditional` branch sub-phases** (`then:` / `else:`, which the engine reaches
  via `mapBranch → mapPhase → parsePhaseType`). A new phase kind appearing *only*
  inside a `conditional` branch would otherwise be invisible to this gate. The
  current `GalleryScenario.phases` doc-comment does not specify branch
  flattening; this ADR makes it a requirement.
- **D2b.** Pin D2a with a **curation-time CI test** (mirroring the existing
  `GallerySeedYAMLTests` / `recommendedModelMatchesRegistry` pattern) asserting,
  for every entry, that `phases` equals the flattened phase-kind set of the
  backing YAML. Without this pin, D2's "drift-proof" claim holds only halfway.

### D3. Secondary gate — declared `min_engine_version` (escape hatch)

Add an optional `min_engine_version: Int?` to each gallery entry
(`GalleryScenario` + `gallery.json`), decoded **leniently** (absent → `nil` →
unconstrained → `0`) for the same forward-compat posture every other index field
documents. Grey out when `min_engine_version > ENGINE_SCHEMA_VERSION`.

This covers breaking-change classes **invisible to D2's phase-name check**:

- A **new value of any closed enum the loader parses by name** other than
  `PhaseType` — `ScoreCalcLogic` (`parseLogic`), `AssignTarget`
  (`parseAssignTarget`), `PairingStrategy` (`parsePairing`), or a new token in
  the `conditional` `if:` DSL (`ConditionEvaluator`). Each of these *also* throws
  at parse today, but none of them appears in the index `phases` array.
- A **new required property on an existing phase**.
- **Changed semantics of an existing, syntactically-unchanged phase or property**
  — the one class no static check can ever see (the YAML is byte-identical).

**D3a. `min_engine_version` is a tooling-computed floor, author-raisable for
semantics.** The curation pipeline that already emits `phases` SHALL also compute
a `min_engine_version` **lower bound** by static feature detection (any
by-name-parsed enum value or key the *baseline* schema doesn't recognize implies
that feature's version). This converts the *structural* subset of D3 from
author-discipline to tooling-discipline — the same robustness D2 claims. The
author manually **raises** it only for the semantics-changed-but-YAML-identical
class that tooling cannot detect. This split is what makes the belt-and-suspenders
genuinely two-layered rather than two fields sharing one failure mode.

### D4. Gate at index-display time; grey out the whole scenario

The gate fires when the Browse (さがす) tab renders the index — a compatible-vs-
incompatible decision made from index metadata alone, **before** any YAML fetch.
An incompatible entry renders as a disabled row with an "app update required"
badge and an App Store deep-link. There is **no launch-time network dependency**
(the rejection of option ① below).

**Never partial-run.** Detection gates the **whole scenario**, never a
"skip-the-unsupported-phase-and-run-anyway" degradation: dropping a `vote` /
`eliminate` phase changes the simulation into a different game. This is not
merely a preference — it is **architecturally forced**: `parsePhaseType` throws
on an unknown type, so no `Scenario` value even materializes to partially run.
A future contributor must **not** "helpfully" add a `PhaseType.unknown` case to
enable partial execution; the clean throw is the safety property.

### D5. Keep the parse-throw as the last-line safety net; fix its message

The D2/D3 index gates are the primary UX. The `parsePhaseType` /
`parseLogic` / … parse-time throw remains the final backstop for anything that
slips past them (a curation bug, or an index-bypassing import — D6). One
change (the throw itself is unchanged standing behavior):

- `tryInstall`'s catch SHALL map an incompatibility-shaped parse failure to
  **update-guidance** copy ("this scenario needs a newer version of Pastura"),
  not the current generic `.networkError("Failed to parse gallery YAML: …")`.
  This is the belt-and-suspenders *floor*, so it must guide the user forward
  rather than dead-end on a "network"/"parse" error.

### D6. Index-bypassing paths (local authoring / file import) are out of scope

Locally-authored and file-imported YAML never traverse the gallery index, so
they carry neither `phases` nor `min_engine_version`. For genuinely local
authoring on *this* build, forward-compat is a non-issue. For a peer-shared YAML
exported from a *newer* app (plausible in Phase 2+), the **only** protection is
D5's improved parse-throw message. This ADR declares those paths **out of scope
for the automatic gate** — a decision, not an omission.

Documented future extension (not adopted here): carry an optional
`min_engine_version` at the **top level of the scenario YAML itself** so imports
can self-declare their requirement. Note the decoder trap — a bare top-level
scalar `Int` **throws** in `ScenarioLoader.convertToAnyCodableValue` (only
`String` / `[String]` / `[String:String]` / `[[String:String]]` values sweep
safely into `extraData`), so any such field must be a **quoted string**
(`min_engine_version: "3"`) or the loader must special-case the key.

### D7. Repurpose `GalleryIndex.version` as the manifest *structural* format version — bounded

Keep the currently-dead `GalleryIndex.version` and give it one narrow job: the
**structural format version of the envelope itself**, distinct from per-scenario
capability gating (D2/D3). "Start checking it" only under a **bounded** contract:

- A structural bump is reserved for a genuinely-incompatible **envelope reshape**
  — a change to `gallery.json`'s top-level shape that an old app cannot even
  parse. Because the envelope is all-additive-optional today
  (`agent_count` / `rounds` / `phases` / `language` were all added leniently),
  this is a **near-never** event.
- Its failure UX, when `index.version > appKnownStructureVersion`, is an explicit
  **whole-gallery "update the app" screen**. This is exactly the feed-level block
  that this ADR rejects for §案1 *content* gating (below) — but it is legitimate
  **here** precisely because it fires only on an unparseable envelope reshape, not
  on the routine addition of a new scenario. If that distinction cannot be held,
  D7 should be dropped rather than "checked" with an undefined failure mode.

## 2. Rationale

### 2.1 Why hybrid rather than either gate alone

D2 (capability-derived) and D3 (declared) are **not opposites** — they are the
"derived" and "declared" halves of the same question, "can this build execute
this scenario?" D2 covers the single most common breaking change (a new phase
kind) automatically, with no server field and no authoring step, and cannot
drift on the client side. But D2 is structurally blind to breaks that do not
surface as a new phase *name* (D3's list). D3 covers those, but rests on a
declared field. Running both — with D3's structural subset tooling-derived
(D3a) — leaves only one residual manual step: raising `min_engine_version` for a
semantics-only change where the YAML is byte-identical and no static analysis can
help.

### 2.2 Why grey-out-at-index, not fail-at-install

The index already carries every field the gate needs (`phases`,
`min_engine_version`, and — separately — `language`, `agent_count`, `rounds`).
Deciding compatibility at render time means the user never downloads a YAML they
cannot run and never sees a post-download failure; the incompatible row simply
reads as "needs an update." This matches the existing lenient-index design intent
(`GalleryScenario`'s forward-compat doc-comments).

### 2.3 Why no forced update

Option ① (a hard minimum-app-version gate) would require a network check at
launch to be enforceable, and the App Store cannot truly compel an update
anyway; it is heavy-handed for what are usually additive changes. The
grey-out + deep-link approach delivers the same "you need to update to run this"
outcome for the *specific* incompatible scenarios, offline, without holding the
whole app hostage. A hard gate remains conceptually available as a
security/legal emergency lever only.

## 3. Rejected Alternatives

### ① App-version forced update — rejected as the general mechanism

Needs launch-time network to enforce; the App Store cannot truly force an
update; disproportionate for additive changes. Kept only as a
security/legal emergency lever, not a compatibility mechanism.

### ②案1 Gallery-level minimum version gating the whole feed — rejected as the gating mechanism

A single minimum version on the envelope that blocks the *entire* gallery refresh
when unmet means one new incompatible scenario denies the user every *other*
(compatible) scenario too — bad UX, and a direct contradiction of the existing
lenient-decode design. Rejected for **content** gating. The envelope's `version`
field is instead repurposed under D7 for **structural** envelope reshapes only,
where a whole-feed block is the sole coherent behavior *and* the trigger is
near-never — a principled distinction from §案1, not a re-entry of it.

### ③-as-partial-run — rejected

"Detect unsupported features and run the scenario anyway, skipping them" is
rejected: skipping a `vote` / `eliminate` phase silently changes the simulation
into a different game. D2/D3 use capability detection to **gate**, never to
partial-run (D4). (This ADR's "③" is the *detect-and-gate* reading, adopted as D2.)

## 4. Bump policy for `ENGINE_SCHEMA_VERSION`

The escape hatch (D3) is only as good as the discipline behind the version it
compares against. The policy is framed on **semantic equivalence**, not
syntactic additivity — because an additive-*looking* key can still change a run.

**BUMP `ENGINE_SCHEMA_VERSION` when adding any of:**

- A new `PhaseType` case.
- A new value of any **closed enum the loader parses by name**: `ScoreCalcLogic`,
  `AssignTarget`, `PairingStrategy`, or a new function/operator token in the
  `conditional` `if:` DSL (`ConditionEvaluator`).
- A new **required** property on an existing phase.
- A new **top-level scalar** (`Int` / `Bool` / `Double`) or nested-object key —
  these **throw** on an old decoder (`convertToAnyCodableValue`).
- Any change to the **semantics** of an existing phase or property such that an
  old app which ignores or mis-handles it produces a **different** simulation.

**DO NOT bump for:**

- A new **optional** top-level key whose value is `String` / `[String]` /
  `[String:String]` / `[[String:String]]` — swept harmlessly into `extraData`
  by an old decoder — **provided** the old app's ignoring of it leaves the
  simulation **semantically identical**.
- A new **optional** key *inside* an existing phase — silently ignored by an old
  loader (`mapPhase` reads only known keys) — **subject to the same semantic-
  equivalence proviso.**

> ⚠️ **The silent-wrong-run class.** Unknown keys inside a phase are ignored with
> *no* throw and are invisible to *both* index gates. So a new phase property that
> an author files as "additive optional → don't bump" but which *changes behavior*
> when honored yields, on an old app, a run that is silently wrong with no error at
> all — strictly worse than a confusing error. The semantic-equivalence proviso
> above exists to close exactly this hole: additive-optional is bump-exempt **only
> if** an old app ignoring the key is semantically identical. When in doubt, bump.

**Maintainer checklist (add-a-feature):** for each new `Engine`/`Models`
extension point, map it to its obligation — every by-name-parsed enum value and
every semantics-bearing change ⇒ BUMP; a truly inert additive-optional string ⇒
no bump.

## 5. Consequences, Scope, and Sequencing

- **Sequencing (load-bearing).** The gate protects only apps that ship **with**
  it. Any app already installed without it still hits the raw parse-throw on the
  first future new-phase scenario. The installed base is currently **zero** (ASC
  upload not started), so the mechanism — and `ENGINE_SCHEMA_VERSION` set to its
  baseline — MUST land **before the first App Store release** and before any
  curated scenario adopts a post-baseline feature, so that no shipped app
  predates the gate.
- **Cross-layer contract.** Implementation spans Engine (`ENGINE_SCHEMA_VERSION`),
  Models (`GalleryScenario.min_engine_version`), the curation tooling
  (`phases` flattening + derived floor + CI pin), and the App-layer Browse gate +
  the D5 message. No dependency-rule change; the gate reads `PhaseType.allCases`
  (Models) and the index fields (App).
- **This ADR ships no code.** Status is **Proposed** by design: the strategy
  introduces a cross-layer contract plus an author-discipline policy that warrant
  buy-in before implementation. Implementation is a follow-up.
- **Out of scope:** index-bypassing import compatibility (D6, message-only);
  a hard app-version gate (①, emergency-only).

## 6. Implementation Sketch (non-normative)

1. `ENGINE_SCHEMA_VERSION` constant in Engine; set baseline before first release.
2. `GalleryScenario.min_engine_version: Int?` (lenient decode) + `gallery.json`
   field; curation tooling computes the derived floor and flattens `phases`
   (incl. `conditional` branches); `GallerySeedYAMLTests` pins both.
3. App-layer Browse gate: `phases ⊄ PhaseType.allCases` OR
   `min_engine_version > ENGINE_SCHEMA_VERSION` ⇒ disabled row + "update" badge +
   App Store deep-link.
4. D5 message change in `tryInstall`'s catch.
5. (D7, optional/near-never) bounded `GalleryIndex.version` structural check with
   a whole-gallery update screen.
