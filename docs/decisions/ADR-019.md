# ADR-019: Raise Minimum Deployment Target to iOS 18

> **Status:** Accepted
> **Date:** 2026-06-28
> **Context:** Pastura shipped on iOS 17.0 as the minimum deployment target
> (the Phase 1 MVP default). A recurring cost has surfaced: SwiftUI APIs that
> would simplify the app — most recently `ScrollPosition.scrollTo(edge:)` for
> the cross-language detail swap ([#830](https://github.com/tyabu12/pastura/issues/830))
> — are iOS 18+, forcing `#available` branches and inferior iOS-17 fallbacks
> (`RootTabView`'s `.tabItem` legacy bar alongside the iOS 18 structural `Tab`
> API, ADR-016). This ADR decides to raise the floor, and records *why the
> raise costs Pastura essentially nothing* given its hardware gate.

---

## 1. Decision

**Raise `IPHONEOS_DEPLOYMENT_TARGET` from 17.0 to 18.0.** Not to iOS 26 (see §3).

This ships alongside the consequent cleanups in the same PR: removing the
iOS-17 `RootTabView` fallback, applying `ScrollPosition.scrollTo(edge:)` for
#830, and the doc updates (`CLAUDE.md` Tech Stack, `README.md`).

## 2. Rationale

### 2.1 The RAM gate already excludes every iOS-17-bound device

Pastura runs on-device LLM inference and gates execution on
`ModelRegistry.minRAM = 6.5 GB` (`ModelRegistry.swift`; the shared
`physicalMemory` floor in `ModelManager`, see ADR-011). **No device with
< 6.5 GB physical RAM can run a Pastura simulation** — the model download is
blocked at the gate.

The set of iPhones meeting the 6.5 GB floor is exactly the 8 GB-RAM tier:
iPhone 15 Pro / Pro Max (A17 Pro, 2023) and every iPhone since (16 line incl.
16e, 17 line). Framed by capability rather than the "iPhone 15 Pro and newer"
shorthand — the gate is RAM, not a model name — **every device that clears the
gate is a 2023-or-later A17-Pro-class phone, all of which support iOS 26.**

Therefore there is **no Pastura-capable device that is stuck below iOS 18.**
The only users a floor-raise can exclude are those on capable hardware who have
*deliberately declined* to update past iOS 17.

### 2.2 Adoption makes that excluded sliver negligible

As of June 2026, across recent iPhones (the cohort that meets Pastura's gate),
~86% run iOS 26 and ~11% run iOS 18 — **~97% on iOS 18+** — with only ~3% on
iOS 17 or earlier, all of which *can* update. (Worldwide across all compatible
devices the iOS-17-or-older share is ~3–7%; the figure is lower still for the
recent-device cohort Pastura targets.) Sources: TelemetryDeck Apple survey,
iOS Ref usage, Gadget Hacks (June 2026 adoption), Business of Apps adoption
data — see References.

### 2.3 Pre-wide-release is the cheapest moment

Pastura is at TestFlight conditional-Go (2026-04-13) with a near-zero install
base. Raising the floor now breaks no shipped users; deferring it past a wide
release would only grow the (already small) affected sliver.

## 3. Why iOS 18, not iOS 26

iOS 18 is the minimal raise that unblocks the needed APIs (`ScrollPosition`,
etc.) while excluding ~no capable device. Raising to iOS 26 would additionally
drop the ~11% of the cohort still on iOS 18 for no concrete benefit: the
iOS-26-only capabilities Pastura uses (BGContinuedProcessingTask background
execution, ADR-003; the Liquid Glass toolbar opt-outs) are already
`#available(iOS 26, *)`-gated as *progressive enhancement* and degrade
cleanly. There is no iOS-26 API Pastura needs as a hard floor. Revisit only if
such a dependency appears.

## 4. Consequences

- `#available(iOS 18, *)` checks become redundant. SwiftLint's default-on
  `deployment_target` rule flags them under `--strict`, so the bump and the
  `RootTabView` fallback removal must land in one commit to keep it green. The
  only two such sites are in `RootTabView` (verified). iOS 26 checks stay valid
  (18 < 26).
- `RootTabView` collapses to a single unconditional structural-`Tab` bar; the
  "two OS branches" doc-comments are rewritten to match.
- #830's large-title-on-swap limitation is fixed with `ScrollPosition`.
- Future code may use any iOS 18 API without an availability branch; iOS 26
  features remain opt-in via `#available`.
