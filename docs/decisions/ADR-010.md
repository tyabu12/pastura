# ADR-010: Localization (i18n: ja / en)

> **Status:** Proposed
> **Date:** 2026-05-12 (stub: 2026-04-29)
> **Context:** Phase 2. The Localization Plan promotion (#276 / PR #277)
> introduced 6 sequential Steps (A → E) for shipping English UI on the
> App Store. The pre-Step A stub (PR #279) captured four narrow
> decisions to unblock UI shell + error message i18n. This body PR
> (issue #367) closes the stub's Open Questions and locks the schema /
> alias / Engine-strategy / resolver-placement decisions that Step C-1
> implementation and Step C-2 (DB compat / drift script / gallery) and
> Step D (bundled English presets) all depend on.
> Operational rule lives in `.claude/rules/i18n.md`.

> **Lifecycle note:** Status flips Proposed → Accepted when Step C-1's
> implementation PR ships (per CLAUDE.md "ADR editability window" — the
> ADR is in-place-editable until its decisions are realized in code,
> after which changes go through `§N. Amendment YYYY-MM-DD` sections).
> This body PR is itself an in-place edit of stub PR #279; it does not

## Decision

Ten decisions, organized lowest-level (data shape) → highest-level
(cross-cutting policy). Decisions 1, 2, 7, 9 are inherited verbatim
from the stub (PR #279); decisions 3, 4, 5, 6, 8, 10 are new — five of
them close stub Open Questions, one (D8) makes the dependency-rule
guarantee normative.

### D1. Scenario YAML `language` field — name and accepted values

**(inherited from stub)** The field is named `language` and accepts an
ISO 639-1 lowercase code (`ja`, `en`). No literal default in the
schema — absence triggers D2's backward-compat rule.

The field is **parsed by `ScenarioLoader` and acted upon by the Engine
at runtime** (see D7). It is not "parse-only" — Step C-1's DoD
requires `scenario.language = "ja"` to drive Japanese Engine output
and `"en"` to drive English. Contrast with D5 (`simulation_language`),
which *is* parse-only in C-1.

Storage shape: extends `Models/Scenario.swift` with
`public let language: String` (non-optional after loader applies D2's
default). Loader maps absent → `"ja"` before constructing `Scenario`,
so the Engine never sees `nil`.

### D2. Phase 1 backward-compat rule — absent `language` → `ja`

**(inherited from stub)** When `language` is absent from a scenario
YAML, `ScenarioLoader` substitutes `"ja"`. Phase 1 shipped
Japanese-only presets and authored scenarios; absorbing the default at
load-time preserves Past Results, bundled-preset behavior, and
user-authored YAML without migration.

### D3. Per-language scenario YAML file layout — sibling files

**(closes stub Open Question)** Per-language scenarios live in
**sibling files** with a `_<lang>` suffix on the filename, not in a
single multilingual YAML. Example: `word_wolf.yaml` (Japanese) and
`word_wolf_en.yaml` (English) coexist under
`Pastura/Pastura/Resources/Presets/`.

Each file is a complete scenario in one language — same `phases`,
`personas`, `rounds` structure, with all user-facing strings (`name`,
`description`, `context`, `prompt`, `template`, `personas[].background`,
`personas[].goal`, `extraData` string values) in the target language.

The file itself declares its language via `language: en` (or `ja`).
The filename suffix is convention, not load gate — the loader trusts
the YAML field.

**Why sibling files over a single multilingual YAML.** (a) Diffing a
single-language edit stays localized to one file. (b) Bundled-preset
drift between languages is auditable per-file
(`scripts/check_demo_replay_drift.py` extends from `REQUIRED_LANGUAGE`
to `ALLOWED_LANGUAGES = {"ja", "en"}` per ROADMAP Step C-2). (c) The
DL-time demo replay (Step D) can ship per-language bundled YAML
without forcing a runtime language-switch mid-replay. (d) Translation
quality for `personas[].background` is acceptable in self-contained
files but degrades in mixed multilingual blocks.

### D4. Per-language scenario IDs reuse `ScenarioRecord.sourceId`

**(closes stub Open Question)** Per-language scenarios have
**independent primary keys** in `Pastura/Pastura/Data/Models/ScenarioRecord.swift`'s
`id` column. The cross-language canonical link reuses the existing
`sourceId: String?` column — no GRDB migration required.

Concrete shape:

| `id` (PK)        | `sourceId`   | `language` (via `yamlDefinition`) | Notes                          |
|------------------|--------------|-----------------------------------|--------------------------------|
| `word_wolf`      | `word_wolf`  | `ja`                              | Phase 1 baseline, unchanged    |
| `word_wolf_en`   | `word_wolf`  | `en`                              | New in Step D                  |

`SimulationRecord.scenarioId` (the FK to `ScenarioRecord.id`) keeps
referencing the per-language `id` — Past Results queries by exact `id`
return the same simulation rows they did in Phase 1. Cross-language
queries (e.g., "show me all results for any word_wolf variant") group
by `sourceId`.

For locally-authored scenarios that never get translated, `id ==
sourceId` (existing Phase 1 behavior) — D4 introduces no new burden on
single-language users.

This reuses the column that the inline doc on
`ScenarioRecord.swift:30-34` already named for "future namespacing
schemes or multi-source provenance" — D4 makes that future concrete.

### D5. `simulation_language` schema — definition only, Engine wiring deferred to Step E

**(closes stub Open Question)** `simulation_language` is parsed and
schema-validated in Step C-1 but **not passed to the Engine** until
Step E. Storage shape: an optional sibling on `Scenario` —
`public let simulationLanguage: String?` — accepting `"ja"`, `"en"`,
or absent (`nil`).

Step C-1 loader behavior:
- Parse top-level YAML key `simulation_language` if present.
- Validate against `{ja, en, nil}`; reject other values with a
  `SimulationError` matching the existing validation idiom.
- Store on `Scenario.simulationLanguage`.
- **Do not propagate to PromptBuilder / Handlers** — the Engine's
  language is `scenario.language` only.

Step E will wire the override at the Engine entry point: when
`simulationLanguage != nil`, prompt generation and default fallbacks
use it instead of `scenario.language`, enabling "run an `en` scenario
on a `ja` device with `simulation_language: ja` for cross-language
output validation."

The field exists in the schema in C-1 (not just docs) so that the YAML
loader does not reject it as unknown — preventing a forward-compat
break when Step E adds wiring.

### D6. Language resolution priority — scoped by consumer

**(new — promotion of stub Open Question implied by ROADMAP Step D)**
The effective language is resolved differently per consumer. There is
no single global resolver:

| Consumer                                       | Resolver expression                                              |
|------------------------------------------------|------------------------------------------------------------------|
| **Engine** (prompt / scoring / default text)   | `scenario.simulationLanguage ?? scenario.language` (Step E adds the override; C-1 collapses to `scenario.language`) |
| **Preset picker UI** (which YAML to surface)   | `Bundle.main.preferredLocalizations.first` matched against available preset languages (Step D) |
| **UI shell** (`Localizable.xcstrings`)         | `Bundle.main.preferredLocalizations` (Apple's standard `String(localized:)` resolution) |

The three consumers are intentionally decoupled. A user on a `ja`
device can pick an `en` preset and run it with
`simulationLanguage: en` — the UI shell stays Japanese, the preset
picker had already shown an `en` row in its default sort, the Engine
emits English.

**`Bundle.main.preferredLocalizations` is read only in App / Views
layers.** Engine never imports `Bundle`. This guarantee is normative
in D8.

### D7. Engine hardcoded-Japanese strategy: Y (dynamic per `scenario.language`)

**(inherited from stub, body specifies the per-site table)** The
Engine reads `scenario.language` and emits the appropriate language at
each user-facing site. The translation contract per site is the
**Translation Table** below; this decision records *what* gets
localized and the strategy, not *how* the implementation dispatches
(helper function naming, switch vs. dictionary, etc., are Step C-1 PR
scope — the ADR's Editability window covers the strategy, not the
code shape).

Strategy X (`Localizable.xcstrings`-based) is rejected for two
compounding reasons (the stub recorded the first; this body adds the
second):

1. **Locale mismatch:** Apple's `String(localized:)` resolves against
   `Bundle.main.preferredLocalizations` (device locale). An `en`
   scenario on a `ja` device would emit Japanese prompt text —
   incompatible with Step E's cross-language goal and with running an
   `en` scenario on a `ja`-device tester.
2. **Dependency-rule break:** `Localizable.xcstrings` resolution requires
   reading `Bundle.main`, which Engine cannot import per CLAUDE.md
   Dependency Rules (Engine → LLM, Models only). Forcing a Bundle
   read inside an Engine type would also trigger the Pattern 4
   isolation trap (`.claude/rules/swift-isolation.md` § Pattern 4 —
   reference type adding sync methods alongside Sendable protocol
   async), silently flipping the Engine type to MainActor inference.

### D8. Engine dependency-rule guarantee

**(new — critic-driven normative addition)** Strategy Y maintains
Dependency Rules: Engine reads `Scenario.language: String` (Models
layer, `nonisolated`) and nothing else. **Engine does not import
`Bundle`, `Locale`, `Foundation.LocaleResolver`, or any App / Views
type.**

The Engine receives the resolved language as a member of `Scenario`
(D6's resolver runs in App / Models before Engine starts the
simulation; Engine sees only the final string). Step E does not relax
this — the `simulationLanguage` override is also a `Scenario` field.

This guarantee is verified by the existing dependency-rule lint
(CLAUDE.md `## Dependency Rules`). Any Step C-1 / Step E PR that adds
`import Bundle` or equivalent to an Engine file violates the ADR.

### D9. `Localizable.xcstrings` scoping boundary

**(inherited from stub)** Step A's xcstrings sweep stops at the
Views/ + App/ boundary. Engine, LLM, Models, Data layers retain
`nonisolated` per CLAUDE.md and handle their own language switching
via D7.

This boundary is enforced operationally by Step A's audit list (per
ROADMAP Step A details); future Engine-touching i18n work must use D7,
not xcstrings.

### D10. ContentFilter — full-set application regardless of UI locale

**(closes stub Open Question)** `ContentFilter` applies the **full
blocklist** to all simulation output, regardless of `scenario.language`
or device locale. There is no per-language filtering subset.

Rationale: ADR-005 (Content Safety) treats the blocklist as a
correctness gate, not a localization layer. The blocklist contains
patterns across both languages (`docs/blocklist/source.json` `lang`
field is metadata for human auditors per Step A's absorbed B-2
scope — it is not consumed by the runtime filter). An `en` scenario
on a `ja` device must reject Japanese blocklist hits in the LLM
output stream, even if Japanese should not naturally appear (the
filter is a safety net, not a language-purity validator).

Future per-language blocklist tuning (e.g., language-specific severity
thresholds) is out of scope for ADR-010 and would warrant a separate
ADR amending ADR-005.

### Fallback rule

When `scenario.language` is `nil` post-load (shouldn't happen given
D2's loader-side default, but defensive): Engine emits Japanese (the
Phase 1 baseline). C-1 implementation may either (a) leave the
fallback implicit because D2 guarantees non-nil, or (b) add a defensive
`switch scenario.language { case "en": ...; default: /* ja */ ... }`
that treats `default` as Japanese. The ADR does not prescribe which.

## Test Compatibility (DoD)

Step C-1's implementation PR keeps existing tests green and adds new
English-path coverage. Concretely:

1. **Existing Japanese assertions stay valid.** All current
   `PromptBuilderTests`, `SimulationRunnerTests`, `WordwolfJudgeLogicTests`,
   and phase-handler tests pass via the
   `scenario.language = "ja"` (or defaulted-from-absent-via-D2) path —
   no test text updates required for the Japanese baseline.
2. **New English-path tests added.** For each Engine site in the
   Translation Table, C-1 adds at least one test that constructs a
   `Scenario` with `language: "en"` and asserts the English literal is
   emitted.
3. **Round-trip stability.** `ScenarioLoader` round-tripping a YAML
   with `language: en` preserves the field; round-tripping without the
   field produces `language == "ja"` (D2 verification).
4. **Validator coverage.** `ScenarioValidator` rejects
   `language: fr` (unsupported value) with a `SimulationError`
   matching the existing validation-error idiom.
5. **`simulation_language` parser tests.** `ScenarioLoader` parses
   `simulation_language: en` to `Scenario.simulationLanguage == "en"`,
   `simulation_language: fr` rejected, absence → `nil`. No Engine-side
   test for `simulationLanguage` in C-1 (it is parse-only; Step E adds
   the Engine wiring tests).
6. **`ContentFilter` cross-language tests.** Add a test asserting the
   full blocklist applies to an `en` simulation's output stream,
   matching D10.

C-1's PR description enumerates which test files added which cases.

## Alternatives Considered

| | Approach                                                                                       | Verdict                                                                                                                                                                                                                                  |
|---|------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| α | Engine uses `Localizable.xcstrings` + `String(localized:)`                                     | **Rejected.** D7 §1 (locale mismatch) and D7 §2 (dependency-rule break + Pattern 4 isolation trap) — compounding correctness and architecture failures.                                                                                  |
| **β** | **Engine emits language dynamically per `scenario.language`** (Strategy Y)                  | **Accepted** as D7. Preserves Engine `nonisolated`, enables cross-language simulation, keeps the dependency graph clean.                                                                                                                 |
| γ | Single multilingual YAML file per scenario with inline ja/en strings                           | **Rejected** in D3. Diff legibility degrades for single-language edits; bundled-preset drift audit ambiguous; DL Demo Replay (Step D) language switch mid-replay surprising; translation quality of `personas[].background` poor in mixed blocks. |
| δ | Per-language scenario IDs without `sourceId` alias (new GRDB column)                           | **Rejected** in D4. The existing `ScenarioRecord.sourceId` already targets exactly this use case ("future namespacing schemes or multi-source provenance" — `ScenarioRecord.swift:30-34`); adding a column duplicates the slot.            |
| ε | Engine reads `Bundle.main.preferredLocalizations` as final fallback                            | **Rejected** in D6 / D8. Breaks Dependency Rules (Engine → Models only); triggers Pattern 4 isolation trap; collapses the consumer-scoped resolver into a global one, defeating cross-language simulation on a non-matching device.       |
| ζ | `simulation_language` wired in C-1 (not just parsed)                                           | **Rejected** in D5. Bundling C-1 with cross-language Engine output enforcement balloons C-1 scope and conflates "preset bilingual coverage" (D, required for App Store launch) with "cross-language adherence quality" (E, post-launch).  |
| η | Per-language `ContentFilter` subsets keyed by `scenario.language`                              | **Rejected** in D10. The blocklist is a safety gate, not a language-purity validator; language-specific severity is a future ADR-005 amendment.                                                                                          |

## Consequences

**Positive**

- Step C-1 implementation has a fully-specified target: 10 decisions,
  ~22 translation sites, 6 DoD bullets, no Open Questions remaining.
- Step C-2 inherits a concrete schema (sibling files, sourceId alias)
  and unblocks `scripts/check_demo_replay_drift.py` extension.
- Step D inherits a concrete preset picker rule (D6 middle row) and
  bundled-YAML layout (D3).
- Step E's `simulation_language` wiring inherits a schema that already
  parses and validates correctly — no forward-compat break.
- The dependency-rule guarantee (D8) is normative, so any C-1 / E PR
  introducing `Bundle` to Engine is detectable in code review against
  the ADR text, not just CLAUDE.md.

**Negative**

- The Translation Table is now a maintenance surface: any new
  Engine-side user-facing string requires both a new row and a C-1
  follow-up. Mitigation: re-running the audit grep before each Engine
  edit (covered by `.claude/rules/i18n.md`'s leak detection workflow,
  Tier 2 audit script).
- `ScenarioRecord.sourceId` semantics expand from "gallery provenance"
  to "gallery provenance OR cross-language alias." A scenario that is
  both gallery-sourced and translated needs careful sourceId handling
  in Step D / curation. C-1 should not block on this — it surfaces
  in Step D / Phase 3 marketplace work.
- `simulation_language` as a parsed-but-unused field for a release
  cycle (C-1 → Step E) carries a minor forward-compat risk: if Step E
  redesigns the override semantics, the field name / shape may need
  amendment. Mitigation: Step E's wiring is bounded to "override
  Engine language at runtime"; the schema shape (string ISO code, same
  values as `scenario.language`) is unlikely to change.

**Neutral**

- D3 (sibling files) is a convention. The loader trusts the YAML's
  `language` field, so a misnamed file (e.g., `word_wolf.yaml` with
  `language: en` inside) is not a load-time error but a curation
  hygiene issue, caught by Step C-2's drift script extension.
- The Translation Table's "en literal (proposed)" column is a draft.
  C-1's PR may revise individual strings during implementation review;
  the ADR's value is fixing the *set* of sites and the *language
  source* per site, not the exact English wording. Wording revisions
  inside C-1 are not ADR amendments.

## Out of Scope (Step E and beyond)

These items are deliberately deferred and **not** part of this ADR's
decisions:

- **Engine wiring of `simulationLanguage` override.** Step E.
- **LLM output-language adherence enforcement.** Step E. Includes the
  decision of which language detector to use
  (Apple `NLLanguageRecognizer` / cld3 / langdetect — Step E confirms)
  and the measurable DoD thresholds (per-preset JSON parse success
  ≥ N% and target-language adherence ≥ M% on Qwen 3 4B Q4_K_M).
- **Benchmark harness** (`PasturaTests/Localization/LanguageAdherenceBenchmark.swift`
  etc.) — built in Step E, gated by an env var like `OLLAMA_INTEGRATION`,
  CI-disabled by default.
- **Per-language blocklist tuning** (D10's deferred extension).
- **Languages beyond `ja` / `en`.** Out of scope for Phase 2 entirely;
  a future ADR would handle a third language by extending D1's
  accepted values, D3's filename suffix convention, D4's id /
  sourceId scheme (already extensible), and the Translation Table.
