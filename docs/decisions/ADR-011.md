# ADR-011: 6 GB RAM Tier Device Support — Selection Criteria for 1B-Class On-Device Models

> **Status:** Accepted
> **Date:** 2026-05-29
> **Context:** Phase 2. Issue #477 set out to add a 1B-class GGUF
> descriptor to `ModelRegistry` so iPhone 13 / 14 / 15 standard +
> SE 3rd-gen (6 GB physical RAM tier) would resolve to a
> downloadable model. PR #480 implemented the registry / gating /
> picker plumbing with Gemma 3 1B IT as the candidate; real-device
> PoC then uncovered a llama.cpp engine constraint that excluded
> this specific candidate. This ADR captures the constraint, the
> evaluation pattern that surfaced it, and the prerequisites
> future 6 GB tier candidates must clear — so the same multi-round
> PoC investigation doesn't replay from scratch on the next attempt.

---

## Decision

1. **Defer 6 GB tier device support in Phase 2.** The shared 6.5 GB
   `physicalMemory` floor in `ModelManager.checkModelStatus`
   (`Self.minimumRAM`) remains the gate. PR #480 introduced
   *gating wiring* that consumed per-descriptor
   `ModelDescriptor.minRAM` from `checkModelStatus`, and that wiring
   was reverted with the PR close-out. The `ModelDescriptor.minRAM`
   field itself shipped with the multi-model plumbing PR #206
   (commit `500a62b`, 2026-04-23) and stays — the Phase 3 tier-auto
   reservation for `ModelDescriptor.minRAM` is documented at
   `ModelManager.swift:93` (in the `minimumRAM` constant's
   doc-comment), not on the field declaration in
   `Pastura/Pastura/Models/ModelDescriptor.swift:53` itself.
2. **Hard prerequisites for any future 6 GB tier candidate** (all
   must clear before merging to `catalog`):
   1. **Non-gated GGUF source on HuggingFace** — direct
      `URLSession` fetch without auth-token negotiation. Gating
      is a **per-repo measurement, never inferred from the
      publisher**: Google's Gemma *3* QAT repos are gated behind
      a license click-through (the observation this ADR was
      written against; `google/gemma-3-1b-it-qat-q4_0-gguf` was
      still `gated: manual` when re-checked 2026-08-08), whereas
      the Gemma *4* QAT repos are **not** (`gated: false`,
      Apache-2.0, anonymous resolve succeeds; same date) —
      though clearing P1 does not imply the GGUF is usable — P1 is
      about licence gating, never loadability. At the then-pinned
      b8694 those exports cleared P1 and still failed to load
      ([`docs/models/eval-log.md`](../models/eval-log.md)
      §2026-08-08); the b10327 bump (#1487) closed that **loader**
      gap, but the QAT-Mobile `UD-Q2_K_XL` export still fails on
      absent Metal quant kernels (§2026-08-13), which no bump fixes.
   2. **Tokenizer + chat template metadata correct in the GGUF** —
      `tokenizer.ggml.token_type` flags `<start_of_turn>` /
      `<im_start>` / equivalent control markers as `CONTROL (3)`
      not `NORMAL (1)`. Verify by inspecting the GGUF metadata
      dump at load time (`print_info` output of `llama_model_load`),
      NOT by trusting the source's claim.
   3. **Real-device GBNF PoC on ≥ 2 distinct presets** — both
      `prisoners_dilemma` (simplest output schema:
      `{action, inner_thought}`) and one preset with a longer
      prompt surface (`bokete` / vote phase) must produce a valid
      JSON token stream without `Unexpected empty grammar stack` /
      `GGML_ASSERT` crash on the first generated token.
   4. **No regression on the existing catalog** — Gemma 4 E2B and
      Qwen 3 4B PoC must re-run successfully alongside the new
      candidate, on the same device, in the same session. Catches
      sampler-chain / chat-template changes that silently corrupt
      previously-stable descriptors.
   5. **Sampler-API shape constraint** — do not introduce raw
      `llama_sampler_accept` calls for prompt tokens on a sampler
      chain that includes a GBNF grammar component (Round 3
      lesson, below). If sampler-chain prompt-token initialization
      becomes load-bearing for a future candidate, route through a
      Pastura wrapper modeled on llama.cpp's
      `common_sampler_accept(smpl, id, /*is_generated=*/false)`
      semantics — `is_generated == false` skips the grammar
      component while still updating penalty / history samplers
      (`common/sampling.cpp` source-of-truth as of llama.cpp
      `master`).
3. **Revisit triggers — re-evaluate this deferral when any of:**
   - The LLM backend migrates from llama.cpp to LiteRT-LM (per
     ADR-001 / ADR-002 forward-looking decisions). Apple's engine
     enforces structured output differently from llama.cpp's
     GBNF mask and may not surface the 1B-tokenizer interactions
     documented below.
   - llama.cpp upstream merges a fix that addresses the grammar
     `accept_token` empty-stack crash for non-special tokens
     (`ggml-org/llama.cpp#21017`, currently "closed as not
     planned" — a sibling re-file with a different repro might
     reopen the work).
   - A user-supplied model meeting all five §Decision-2
     prerequisites — in particular **Qwen 2.5 1.5B Instruct** (or
     a derivative such as the DeepSeek R1 Distill Qwen 1.5B
     listed in §Alternatives), since the Qwen tokenizer family is
     already verified by the in-catalog Qwen 3 4B descriptor.

## Why this shape

### Investigation chain (PR #480)

The deferral isn't a pre-existing constraint; it surfaced through
three rounds of real-device PoC, each closing one hypothesis and
opening the next.

**Round 1 — unsloth GGUF chat-template bug.** Initial descriptor
sourced `unsloth/gemma-3-1b-it-GGUF` at the unsloth commit pinned
for similar Gemma 4 E2B usage. First simulation crashed with
`Unexpected empty grammar stack after accepting piece: > (236813)`.
Root cause traced to `unslothai/unsloth#5070` (labelled "currently
fixing" upstream; sibling PRs `unslothai/unsloth#5115` merged
2026-04-22 and `#5080` merged 2026-04-23 — Pastura's Round 1
PoC ran against an unsloth GGUF predating these merges and
observed the bug):
Gemma 3 GGUF exports flag `<start_of_turn>` / `<end_of_turn>`
markers with `tokenizer.ggml.token_type = NORMAL (1)` instead of
`CONTROL (3)`, so llama.cpp's `parse_special` path doesn't
recognise them; the chat-template markers get BPE-split, the
model receives a garbled prompt and emits `>` (the trailing byte
of a split `<end_of_turn>`) as its first generated token.
**Fix found**: source pivot to `ggml-org/gemma-3-1b-it-GGUF`
(llama.cpp team's own conversion — the same maintainers who
define the GGUF metadata contract). Round 1 hypothesis confirmed;
resolved. *(A future re-test of unsloth's regenerated GGUF
post-#5115/#5080 merge is possible; the source-pivot conclusion
above is bound to the PoC-time GGUF state.)*

**Round 2 — `情報` first-token crash on ggml-org GGUF.** Re-PoC
with the ggml-org source: chat-template markers tokenized as
expected (verified in `print_info` log output — token 105 / 106
both flagged CONTROL), but generation still crashed —
`Unexpected empty grammar stack after accepting piece: 情報 (19990)`
on `prisoners_dilemma` and `bokete` alike. Now a regular Japanese
vocab token rather than a control-marker fragment. The GBNF mask
should have rejected `情報` (the root rule starts with `"{"`), but
the sample-time accept path triggered the empty-stack throw at the
first generated token. `ggml-org/llama.cpp#21017` documents the
identical crash signature class (Qwen3-Coder-Next, `? (30)`) and
is labelled "closed as not planned" with no fix-commit reference.
A separately filed but adjacent Gemma 3 engine issue —
`ggml-org/llama.cpp#12357` "Gemma 3 Outputs Gibberish After
Context Shift" — was fixed via PR #12373, but that fix is a
sliding-window-attention patch for a different code path and
does not address the Round 2 GBNF mask interaction.

**Round 3 — `llama_sampler_accept` for prompt tokens hypothesis.**
llama.cpp's canonical examples (`common/sampling.cpp`) feed
prompt tokens through the sampler chain after prefill so penalty
/ grammar samplers see prompt context as part of their state.
Pastura was skipping this. Implemented
`pastura_llama_sampler_accept_safe` (SafeSampler-style C++
exception catcher) and called it for every prompt token in
`prepareGeneration` after sampler creation. On real device:
**every prompt token (448 / 448) threw**, starting with `<bos>`
(id 2) — `<bos>` doesn't match the GBNF `root` rule, grammar
`accept_token` throws, sampler state corrupts. The subsequent
`llama_sampler_sample` then hit `GGML_ASSERT(!stacks.empty())`
(observed at `llama-grammar.cpp:940` in the PoC-time crash log —
line number is pin-relative to llama.swift's then-current
llama.cpp commit) and `ggml_abort`-ed via SIGABRT —
*uncatchable* by the SafeSampler bridge (POSIX signals don't
propagate through `try / catch`; this is the documented uncovered
class in `SafeSampler.h:18-21`, issue #253).

Round 3 reverted (commit `4ffaf6f` on the PR #480 branch). The
canonical pattern in llama.cpp is
`common_sampler_accept(smpl, id, is_generated)` where
`is_generated == false` skips the grammar component while still
updating penalty samplers — `common/sampling.cpp`'s implementation
gates the grammar `llama_sampler_accept` call on
`is_generated && grammar_should_apply(gsmpl)`. The raw
`llama_sampler_accept` C entry point that Pastura uses has no
such bypass, so it can never be safely called for prompt tokens
on a chain that includes a GBNF grammar sampler. This is the
prohibition captured in §Decision-2 P5.

### Why this rules out *this* candidate, not all 1B-class models

The three rounds collectively rule out **Gemma 3 1B IT
specifically on the current llama.cpp pin with GBNF enforcement**.
They do not collectively prove that all 1B-class models will fail
similarly:

- Round 1's failure mode is GGUF-source-specific (unsloth tooling
  bug); ggml-org doesn't have it. A future candidate with a
  correct upstream GGUF clears this without diagnostic cost.
- Round 2's failure mode is model-tokenizer + llama.cpp grammar
  mask-specific. Different tokenizers (e.g., Qwen 2.5's) might
  not trigger the empty-stack path on the first generated token.
- Round 3's failure mode is API-shape-specific (Pastura's use of
  raw `llama_sampler_accept`); it would re-fire if a future
  contributor independently adds prompt-token sampler init for
  unrelated reasons (penalty state warm-up, etc.), so §Decision-2
  P5 explicitly forbids this shape going forward.

Qwen 3 4B and Gemma 4 E2B both ship in the current catalog with
the same `LlamaCppService` + GBNF grammar workflow, so the engine
constraint is not universal — it intersects with specific
tokenizer + model-size combinations the investigation surfaced.

### Why a mechanism contract, not a model-pinned gate

`.claude/rules/adr-writing.md` § "Mechanism contract over pinned
model thresholds" calls for DoD criteria that survive model
swaps. The five prerequisites in §Decision-2 are mechanism
contracts — they phrase the gate as "non-gated source / correct
metadata / behavioral contract on real-device PoC / regression
protocol / sampler-API shape", not "≥ N% success rate on
Gemma 3 1B". Same shape as ADR-010 §D for cross-language
adherence: the acceptance reads off real-device PoC output at
adoption time rather than pinning a per-model threshold in the
ADR.

This also avoids forcing a full ADR amendment when LiteRT-LM
lands (revisit trigger 1) — most prerequisites still apply, with
the GBNF substring in P3 / P5 swapped for LiteRT-LM's
structured-output mechanism. P5 specifically is bound to
llama.cpp's sampler-chain API; the binding is intentional and
time-bound to the llama.cpp era.

## Consequences

### Install base — Phase 2 unchanged

iPhone 13 / 14 / 15 standard and SE 3rd-gen (the 6 GB physical
tier) remain `.unsupportedDevice` for Pastura through the rest of
Phase 2. The TestFlight install-base impact is contained because
Pastura's pre-PR-#480 catalog (Gemma 4 E2B + Qwen 3 4B, both at
6.5 GB `minRAM`) already gates these devices out behind
`ModelManager.Self.minimumRAM`; no shipped user flow regressed.

### `ModelDescriptor.minRAM` field stays — only the gating wiring reverted

PR #480's per-descriptor `minRAM` gating in `checkModelStatus`
(displacing `Self.minimumRAM` as the floor source) was reverted
alongside the rest of the PR. The `ModelDescriptor.minRAM` field
itself shipped with PR #206 (multi-model plumbing, commit
`500a62b`, 2026-04-23) — predating PR #480's first commit
`3237e7a` (2026-05-25) by ~1 month — and the Phase 3 tier-auto
reservation for `ModelDescriptor.minRAM` is documented at
`ModelManager.swift:93` (in the `minimumRAM` constant's
doc-comment), not on the field declaration in
`Pastura/Pastura/Models/ModelDescriptor.swift:53` itself.
A future 6 GB tier candidate that clears
§Decision-2 will re-land the gating-migration commit class, but
the surface lives in `ModelManager.swift` rather than
`ModelDescriptor.swift`, so the field-level contract isn't an
ADR change.

### Future model-addition workflow expectation

The Round 3 regression (sampler corruption + SIGABRT) was caught
only because the user ran real-device PoC across multiple presets
*and* compared against the existing catalog descriptors on the
same device. The §Decision-2 prerequisites (P3 + P4 + P5)
formalize the "compare against the existing catalog on the same
device, same session, no sampler-API regression" loop so it
survives memory churn.

### Model-selection-criteria documentation surface

Pastura's `README.md` "Supported LLM models" + CLAUDE.md "Phase 2
progress" + `docs/ROADMAP.md` Multi-model row all mention the
existing 2-descriptor catalog. None of them documents the
candidate exclusion criteria — that gap motivated this ADR.
Future "why isn't model X in the catalog?" questions land on
§Decision-2 + §Alternatives instead of recurrent diagnostic loops.

## Alternatives considered

### Candidate A — Gemma 3 1B IT (Q4_K_M)

| Source attempted | Failure | Rejected because |
|---|---|---|
| `unsloth/gemma-3-1b-it-GGUF` | Garbled prompt; `>` first-token crash | Round 1 — `unslothai/unsloth#5070` control-token export bug ("currently fixing") |
| `ggml-org/gemma-3-1b-it-GGUF` | `情報` first-token crash; sampler accept attempt → SIGABRT | Rounds 2 + 3 — llama.cpp grammar empty-stack + uncatchable abort |

Status: **Rejected for the Phase 2 catalog.** Re-evaluation gated
on the revisit triggers in §Decision-3.

### Candidate B — DeepSeek R1 Distill Qwen 1.5B

| Property | Value | Note |
|---|---|---|
| Vendor | DeepSeek | Reasoning-brand recognition (R1 distillation lineage) |
| Quantisation | Q4_K_M | ~1.12 GB |
| Tokenizer family | Qwen 2.5-derived | Qwen 3 4B in current catalog shares the Qwen tokenizer lineage → engine-compat risk lower than Gemma 3 |
| Source | `unsloth/DeepSeek-R1-Distill-Qwen-1.5B-GGUF` (non-gated) | bartowski / community alternatives exist if unsloth's Qwen-distill exports also have token-flag issues |

Status: **Not evaluated.** Listed as one of the two
highest-confidence next candidates if §Decision-3 trigger 3
fires — but not pursued in Phase 2.

### Candidate C — Qwen 2.5 1.5B Instruct

| Property | Value | Note |
|---|---|---|
| Vendor | Alibaba | Direct sibling lineage to the in-catalog Qwen 3 4B |
| Quantisation | Q4_K_M | ~1.0 GB (varies by GGUF source) |
| Tokenizer family | Qwen 2.5 native | Lowest engine-compat risk — same family as Qwen 3 4B which ships in the current catalog |
| Source | `Qwen/Qwen2.5-1.5B-Instruct-GGUF` or community re-pack | Non-gated, same publisher class as the in-catalog `Qwen/Qwen3-4B-GGUF` |

Status: **Not evaluated.** Listed alongside Candidate B as the
two highest-confidence next candidates if §Decision-3 trigger 3
fires. Direct Qwen lineage means the §Decision-2 P2
chat-template-metadata check has the highest prior odds of
clearing.

Rationale for *not* adopting either B or C in Phase 2: Round 3's
regression revealed that the investigation cost per candidate is
multi-day with real-device PoC; queuing a second candidate
immediately after a no-go runs the same investigation cost
without a load-bearing reason for the specific Phase 2 timeline.
Defer until either a §Decision-3 revisit trigger fires or the
user re-prioritizes 6 GB tier coverage.

### Candidate D — Llama 3.2 1B Instruct

| Property | Value | Note |
|---|---|---|
| Vendor | Meta | llama.cpp ecosystem support is deepest here |
| Quantisation | Q4_K_M | ~808 MB |
| Chat template | Llama 3.2 native | Format support in llama.cpp is mature |
| Tokenizer family | Llama (BPE, ~128k vocab) | Distinct from both Gemma and Qwen lineages; no in-catalog precedent → unknown engine-compat fingerprint |
| Source | `hugging-quants/Llama-3.2-1B-Instruct-Q4_K_M-GGUF` (non-gated) | hugging-quants is the post-Meta-license-acceptance redistribution channel |

Status: **Not evaluated.** Higher prior risk than Candidates
B / C because no Llama-family descriptor ships in the existing
catalog. A PoC would need to run the full §Decision-2
prerequisite ladder fresh.

### Candidate E — Phi-4 mini Instruct (3.8B)

Out of 6 GB tier scope: `minRAM` would land at 6.5 GB+ alongside
the existing catalog, not opening any new device tier. Listed
here only to document the rationale for not exploring it under
issue #477.

### Candidate F — Apple Foundation Model

Surfaced briefly in the issue-#477 candidate triage: Apple's
iOS-26 on-device foundation model has ~3B-parameter footprint,
but exposes through the `FoundationModels` framework rather than
as a GGUF file. Pastura's iOS 17 deployment target + the
LiteRT-LM migration path both make this an ADR-001 / ADR-002
sequel decision, not a 6 GB tier catalog addition. Out of scope.
