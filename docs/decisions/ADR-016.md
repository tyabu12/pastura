# ADR-016: Bottom-Tab Information Architecture & Deep-Link Tab Routing

> **Status:** Accepted
> **Date:** 2026-06-14
> **Context:** The Home screen was redesigned from zero base (confirmed
> 2026-06-14, "D3" mock, see
> [`docs/design/home-redesign/`](../design/home-redesign/)). The new
> information architecture replaces the single root `NavigationStack` +
> Home-as-launchpad model with a **four-tab bottom bar**. That structural
> shift forces decisions the current navigation contract
> ([`.claude/rules/navigation.md`](../../.claude/rules/navigation.md))
> does not cover: how many navigation stacks exist, where `selectedTab`
> lives, which screens stop being `Route` cases, and — the load-bearing
> one — how a deep link resolves onto a specific tab's stack when there
> are now four stacks instead of one. This ADR records the IA + routing
> **posture**. It ships no code; the multi-phase implementation (P0–P6,
> §4) inherits these decisions.

---

## 1. Decision

### D1. Four-tab bottom-bar IA

The app's top level becomes a four-tab bottom bar. Tabs (Japanese labels,
matching the existing JA-first UI):

| Tab | Label | Icon (SF Symbol family) | Content |
|-----|-------|-------------------------|---------|
| Home | 牧場 | house | Brand header + resumable-simulation card + scenario list |
| Search | さがす | magnifyingglass | Shared-scenario gallery + search |
| History | 観察履歴 | clock | Past results, date-grouped |
| Settings | 設定 | gearshape | Existing settings surface |

Tabs are **icon-only**; each carries an `accessibilityLabel` so VoiceOver
announces the Japanese label. The active tab is tinted `Color.moss`
(token confirmed present: `moss` / `mossDark` / `mossInk` / `mossSoft`).

### D2. Tab bar = native `TabView`, OS-gated styling (no hand-roll)

The bar is SwiftUI's native `TabView`, **not** a custom hand-rolled bar.
Styling is OS-gated via `if #available`:

- **iOS 26+**: accept the native floating Liquid Glass bar; apply
  `.tint(Color.moss)`. The search tab adopts the search-role treatment.
- **iOS 17–25**: standard tab bar + `.tint(Color.moss)`.

Both code paths require **real-device QA on their respective OS** — the
simulator does not faithfully render the iOS 26 Liquid Glass bar (same
class of simulator/device divergence already documented for toolbar
chrome in `swiftui-traps.md` § "Toolbar-hide API matrix").

`design-system.md` §5.8 (Toolbar buttons — Liquid Glass opt-out) governs
**toolbar items**, not the tab bar, and does **not** justify hand-rolling
the bar. Where toolbar buttons opt *out* of Liquid Glass for visual
quietude, the tab bar opts *in* to the native treatment — a deliberate
asymmetry: the tab bar is a system-level surface where platform-native
behavior (haptics, accessibility, search-role morphing) outweighs visual
custom control.

### D3. `TabCoordinator` owns four **unmodified** `AppRouter` instances

The app does **not** widen `AppRouter` into a four-path container, and
does **not** add `selectedTab` to `AppRouter`. Instead a new
`TabCoordinator` (App layer — dependency-rule-clean, since `App/` may
depend on everything and `AppRouter` already lives at
`Pastura/Pastura/App/AppRouter.swift`) owns:

- one `AppRouter` per tab (four instances, each driving its own tab-root
  `NavigationStack`), and
- the `selectedTab` selection state.

Each tab's `AppRouter` keeps its current contract verbatim — `push` /
`pop` / `popToRoot` / `pushIfOnTop` / `RouteHint` identity semantics
([ADR-008](ADR-008.md)) are preserved **per tab**. This honors
`navigation.md` § "AppRouter scope (load-bearing)", which forbids adding
non-path state (selection / modal flags / etc.) to `AppRouter`:
`selectedTab` is tab-selection state and so belongs on the coordinator,
not the router.

Why four routers rather than one widened router: the existing
`pushIfOnTop` / `popToRoot` / `path.last` guards are written against a
single linear stack. Four independent `[Route]` arrays preserve those
guards unchanged inside each tab; a single four-segmented path would
require every guard to learn which segment it operates on. The
small-surface choice (four instances of an unchanged type) is strictly
less risky than mutating the type every guard depends on.

### D4. Remove promoted screens from the `Route` enum

Three screens stop being push destinations and become **tab roots**.
Their `Route` cases are deleted so the compiler enforces the new IA
(the implementation PR for this lives in P1; this ADR only records the
target shape):

- `case sharedScenarios` (`App/Router.swift`) — **deleted**; the
  Search (さがす) tab root replaces it.
- `case settings` (`App/Router.swift`) — **deleted**; the Settings
  (設定) tab root replaces it.
- `case results(scenarioId:)` (`App/Router.swift`) — **split**. Its
  Home-entry semantic (empty `scenarioId`, cross-variant aggregation —
  the `sourceId` linkage from [ADR-010](ADR-010.md) D4 plus the
  cross-variant-vs-per-variant UX seam in `App/Router.swift`'s `results`
  doc-comment; #392) becomes the History (観察履歴) tab
  root, owning **no** `Route` case. Its detail-entry semantic (non-empty
  `scenarioId`, per-variant, reached from inside a `ScenarioDetailView`)
  **keeps** its `Route` case and continues to push onto whichever tab's
  stack surfaced it.

`case resultDetail(simulationId:)` (`App/Router.swift`) is **kept** —
it is a genuine push destination, not a promoted root.

Rationale: keeping `.settings` / `.sharedScenarios` as `Route` cases
*and* exposing them as tabs would create two reach-paths to the same
screen with mismatched back-chrome (a pushed `.settings` shows
`PasturaBackButton`; a tab-root `.settings` shows none). Deleting the
cases turns every now-illegal `router.push(.settings)` /
`.sharedScenarios` callsite into a **compile error**, surfacing the
full migration surface mechanically rather than by audit.

### D5. Deep-link → tab routing redesign (load-bearing)

This is the decision the prior nav/sequence critic flagged as a
Must-fix. Today the deep-link machinery assumes a **single** stack:

- `isSimulationOnTop` (`PasturaApp.swift`) is
  `if case .some(.simulation) = router.path.last`.
- The drain (`handleOpenURL` → `tryDrain` → `applyResolution` in
  `PasturaApp.swift`) pushes onto the one router; the terminal action is
  `router.push(.galleryScenarioDetail(scenario:))`.

Under four stacks the contract is redefined as follows.

**D5.1 — `isSimulationOnTop` becomes "any tab".** Redefine it as: a
`.simulation` route is on top of **any** tab's stack (not just the
selected tab's). A simulation the user backgrounded by switching tabs
must still block the drain.

**D5.2 — Drain targets a named tab, then pushes onto that tab's router.**
The resolved deep-link destination is `.galleryScenarioDetail` — a
**Search (さがす)** tab destination. So the drain becomes: *select the
さがす tab, then **plain-`push`** `.galleryScenarioDetail` onto that
tab's `AppRouter`* — **not** `pushIfOnTop`. The `await` that
`pushIfOnTop` guards already completed upstream in `PasturaApp.tryDrain`
before the drain reaches the coordinator, and the freshly-selected tab
root is normally an empty stack where the guard would no-op; the
rationale is documented on
`TabCoordinator.presentDeepLinkedGalleryScenario(_:)`. The target tab is
fixed by the resolution kind, not by whichever tab is currently selected.
`lastDeepLinkedScenarioId` (a `PasturaApp` `@State`, injected as an
environment value, set on deep-link resolution and cleared when the
Search tab's stack empties) remains **app-global** — it is a
cross-cutting display hint read across the whole view tree, not per-tab
state, so it stays on the app root and is not duplicated per coordinator.

**D5.3 — Complete single-stack consumer inventory.** Every site coupled
to the single-stack assumption must be migrated to per-tab routers. The
table below lists the single-stack consumers found at ADR time via a
`router.path.last` / `router.path.count` grep (the three view-layer
sites, plus `AppRouter.popToRoot()` whose semantics shift). That grep
did **not** cover path *observation* sites that read the whole path
(`.map(\.path)` / `.path.isEmpty`); the implementation added two such
`PasturaApp` guards, listed after the table:

| Site | Current coupling | Per-tab disposition |
|------|------------------|---------------------|
| `PasturaApp.swift` `isSimulationOnTop` | `router.path.last == .simulation` | Fold over all four routers (D5.1). |
| `Views/Home/HomeView.swift` `.onChange(of: router.path.count)` | pop-reload on the single stack | Bind to the **Home tab's** router; pop-reload is Home-local. |
| `Views/Results/ResultDetailView+Delete.swift` `router.path.last == .resultDetail(...)` | post-delete pop guard on single stack | Bind to the router of the tab that surfaced the detail (History tab root, or whichever tab pushed it). |
| `App/AppRouter.popToRoot()` (`App/AppRouter.swift`) | "unwind to root" of the one stack | Now means "unwind **this tab's** stack"; tab re-selection (tapping the active tab) maps to `popToRoot()` on that tab's router. |

Two additional `PasturaApp` path-observation guards (outside the
`.last`/`.count` grep above) make the per-tab wiring complete:

- **Drain trigger** — `.onChange(of: tabCoordinator.allRouters.map(\.path))`
  re-fires `tryDrain()` when **any** tab's path changes, so a
  `.simulation` popped on a backgrounded tab unblocks a pending drain.
  Observing only the selected tab's path would strand the drain.
- **Attribution clear** — `.onChange(of: tabCoordinator.searchRouter.path.isEmpty)`
  clears `lastDeepLinkedScenarioId` when the **Search tab's** stack
  empties. The deep-linked detail lands on さがす (D5.2), so the
  source-attribution must clear when *that* tab returns to root — not
  when an unrelated tab happens to be empty.

**D5.4 — Non-drain consumers of `isSimulationOnTop`.** The redefinition
in D5.1 is **not** confined to deep linking. `isSimulationOnTop` also
feeds two launch/lifecycle consumers, and widening it to "any tab"
changes their behavior:

- `PasturaApp.swift` derives the `.simulationActive` lifecycle state
  from it.
- `LaunchPhaseCoordinator.shouldPlayWarmSplash(launchKind:appIsReady:isSimulationOnTop:isSheetActive:)`
  (`App/LaunchPhaseCoordinator.swift`) returns
  `appIsReady && !isSimulationOnTop && !isSheetActive` — so a simulation
  on a **non-selected** tab would now suppress the warm splash (#412 /
  #415 launch animation) and flip the lifecycle classification.

**Decision:** "any tab" is the correct semantic for **both** consumers.
A simulation running in a backgrounded tab is genuinely in-flight — its
inference and `BGContinuedProcessingTask` re-attach lifecycle
([ADR-003](ADR-003.md)) keep running regardless of which tab is
selected — so suppressing the warm splash and reporting `simulationActive`
is correct, not a regression. This is recorded explicitly so the P-phase
implementer does not "narrow" `isSimulationOnTop` back to the selected
tab to preserve the old warm-splash timing.

**D5.5 — Test strategy (mechanism, not pinned cases).** The redesign
ships with tests asserting the *mechanism*, layered on the existing
`AppRouterTests` pattern:

- A deep link arriving while the user is on any non-Search tab selects
  the Search tab and pushes the gallery detail onto **that** tab's
  router (not the previously-selected tab's).
- A `.simulation` route on any tab makes the global `isSimulationOnTop`
  true and defers the drain until the simulation is popped.
- `popToRoot()` triggered by re-selecting a tab unwinds only that tab's
  stack and leaves the other three intact.
- The three migrated view-layer guards (D5.3) operate against their own
  tab's router.

## 2. Why this shape

### Native bar over hand-roll

A hand-rolled bar would have to re-implement, per OS, the search-role
morphing, the Liquid Glass material, accessibility focus order, and the
re-select **gesture surface** — all of which the native `TabView`
provides. (Note: the native bar provides only the gesture — its
selection `Binding`'s setter fires on re-tap — and does **not** auto-pop
a `[Route]`-bound `NavigationStack` to its root; that path reset is
performed manually by `TabCoordinator.handleSelection(_:)`. The code
carries the matching `(ADR-016 §2, corrected)` marker. Riding the native
gesture surface still beats hand-rolling the bar — the manual pop is one
small method, not a per-OS re-implementation.) The cost of OS-gated
*styling* (`.tint` + an `if #available` branch) is far below the cost of
owning the bar's behavior across two OS generations. This mirrors the
project's standing preference to ride platform-native surfaces where
behavior (not just pixels) is at stake.

### Four routers over one widened router

See D3 rationale: the existing navigation guards are single-stack by
construction. Four unchanged routers preserve every guard's correctness
locally; one segmented path would force a cross-cutting rewrite of code
that is currently load-bearing and well-tested (`pushIfOnTop`,
`RouteHint` identity, `popToRoot`). The smaller blast radius wins.

### Compile-error-driven migration over audit

D4 deliberately deletes `Route` cases rather than leaving them dormant.
Dormant cases invite a future `router.push(.settings)` that compiles but
mis-renders (two reach-paths, mismatched chrome). Deletion converts the
entire migration surface into compiler diagnostics — the same
"stray-push becomes a compile error" discipline the project already
relies on for `Route` identity.

### Mechanism contract for the routing tests

Per `.claude/rules/adr-writing.md` §2, D5.5 defines the routing
*mechanism* (target-tab selection + per-tab push + global sim gate)
rather than pinning a fixed enumeration of deep-link scenarios. New
deep-link kinds added later (beyond the current single `.scenario`
resolution in `DeepLinkURL`) inherit the mechanism without an ADR
amendment.

## 3. Consequences & relations to existing ADRs

- **`navigation.md` requires a full revision** — its core premise ("The
  root `NavigationStack` lives in `RootView` … its `path` is owned by
  `AppRouter`") becomes four stacks owned by a `TabCoordinator`. The
  rule's "AppRouter scope" section is *honored* by D3 (selection state
  stays off `AppRouter`), but the single-stack framing throughout must
  be rewritten. This revision is a **P1 deliverable**, not part of this
  doc-only ADR.
- **[ADR-008](ADR-008.md) (`RouteHint`)** — unchanged and preserved
  per-tab. Render-time hints continue to ride `RouteHint<T>` with
  identity-neutral `==`/`hash`.
- **[ADR-010](ADR-010.md) D4 (`sourceId` linkage) + the `App/Router.swift`
  `results` doc-comment (cross-variant UX seam)** — the History tab root
  inherits the empty-`scenarioId` aggregation semantic verbatim; only its
  *reach path* changes (tab root vs Home push).
- **[ADR-003](ADR-003.md) (BG execution)** — informs D5.4: backgrounded-
  tab simulations are genuinely in-flight, which is *why* "any tab" is
  the correct `isSimulationOnTop` semantic.
- **`design-system.md` §5.8** — clarified by D2: it governs toolbar
  items, not the tab bar; the tab bar opts into native Liquid Glass.

## 5. Alternatives considered

- **Widen `AppRouter` to a four-segment path** — rejected (D3): forces a
  cross-cutting rewrite of single-stack guards that are currently
  correct and tested.
- **Add `selectedTab` to `AppRouter`** — rejected (D3): violates
  `navigation.md` § "AppRouter scope"; selection is not navigation-path
  state.
- **Keep promoted screens as dormant `Route` cases** — rejected (D4):
  invites mis-rendered dual-path pushes; deletion is compiler-enforced.
- **Hand-roll the tab bar for full visual control** — rejected (D2):
  re-implements platform behavior (search-role, accessibility, Liquid
  Glass) at high cost; `design-system.md` §5.8 does not extend to tab
  bars.
- **Narrow `isSimulationOnTop` to the selected tab** — rejected (D5.4):
  a backgrounded-tab simulation is genuinely in-flight (ADR-003);
  reporting it inactive would mis-time the warm splash and lifecycle
  state.

## 6. Amendment 2026-06-18 — focus mode re-anchors the `isSimulationOnTop` fold

[ADR-017](ADR-017.md) introduces **simulation focus mode**: while a
simulation is on top of a tab's stack, the bottom tab bar is hidden, so a
foreground tab switch *during a run* is structurally impossible (#646
Phase A). That changes the **motivation** — not the **correctness** — of
D5.4's any-tab fold. This amendment disentangles two notions D5.4
conflated.

**Hosting vs switching.** `isSimulationOnTop` folds `path.last` over all
four routers. Its load-bearing job is detecting that a simulation is the
**top of any one tab's stack** — multi-tab *hosting*. A sim can be hosted
on Search (a fresh run), Home, or History (a resume); that is independent
of whether the user can *switch* tabs mid-run. D5.4's original prose
motivated the fold with the **switching** case ("a simulation the user
backgrounded by switching tabs"). Focus mode removes that case, but the
hosting case remains, and so does the **scenePhase-background** case (home
button / app switcher — [ADR-003](ADR-003.md)), which focus mode does not
touch (app-background does not fire `onDisappear`; a foreground tab switch
does — that asymmetry is the whole point).

**Decision.** The any-tab fold **stays exactly as implemented** (`.simulation`
/ `.resumeSimulation` over all four routers) and must **not** be narrowed to
the selected tab. Its justification is re-anchored on (1) multi-tab
*hosting* and (2) scenePhase-background continuation — both still live under
focus mode — rather than on tab-switch backgrounding. D5.1/D5.4's
deep-link-drain-gating and warm-splash-suppression consumers are unchanged.

**Do not delete the fold as "now redundant".** Under Phase A a sim is only
ever hosted on the *currently selected* tab at the moment of hosting, which
can read as "selected-tab only". It is not: a backgrounded app (scenePhase)
keeps a hosted sim in-flight regardless of selection, and ADR-017 Phase B
(opt-in cross-screen continuation) re-loads the multi-tab-switching case in
full.

## 7. Amendment 2026-06-20 — iOS 18+ structural `Tab` API + icon-only preservation

D2 anticipated the iOS 26 search-role morph ("the search tab adopts the
search-role treatment"). Implementing it (#693) forces an API migration
this amendment records.

**Why the whole bar branches.** `Tab(role:.search)` (and the iOS 26
tab-bar↔search-field morph it triggers) require SwiftUI's structural
`Tab` API, which is **iOS 18.0+**. The new `Tab{}` builder **cannot be
mixed** with the closure-based `.tabItem` form in one `TabView`, and
`.tabItem` is deprecated on iOS 18+. So `RootTabView.body` branches the
*entire* bar on `if #available(iOS 18.0, *)`: a modern `Tab`-based
`TabView` and the existing `.tabItem` bar verbatim for iOS 17. The same
`AppTab` selection binding and the per-tab `TabNavigationStack` content
(D3 router injection) are shared across both branches — only the tab
*enumeration wrapper* (`Tab(value:)` vs `.tag()`/`.tabItem`) differs.

**D1 icon-only is preserved, not abandoned.** The structural `Tab` API
has **no icon-only *titled* initializer** — every `init(_:systemImage:…)`
forces a visible text title. D1's icon-only mandate is kept via the
**empty-label `label:`-closure form** (`Tab(value:…) { content } label:
{ Image(systemName:…) }` with a bare `Image`, no `Text`). This is
**verified to compile** (build succeeded on this branch). The さがす tab
uses `Tab(value:.search, role: .search)` with a **custom `label:`**
(magnifyingglass + the "Browse" `accessibilityLabel`) rather than the
empty-label form, so VoiceOver and the UI tests
(`DeepLinkTabRoutingUITests`, `NavigationRegressionTests`,
`SimulationFocusModeTests`) keep locating the tab by "Browse"; the search
role still drives the morph.

**Device-QA-contingent fallback.** Whether the bare-`Image` label renders
cleanly icon-only on the iOS 26 Liquid Glass **floating** bar is
**verifiable only on a real device** (the simulator mis-renders the
iOS 26 bar — D2). If on-device QA shows it cannot render icon-only
cleanly, the fallback is to accept the native **titled** labels on the
iOS 18+ branch — which would amend D1's all-OS icon-only mandate to
"icon-only on iOS 17; native labels on iOS 18+". That amendment is
deferred until device QA decides; D1 stands as written unless/until then.
