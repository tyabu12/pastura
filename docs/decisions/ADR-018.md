# ADR-018: Format-Preserving Visual→YAML Boundary Sync (Surgical Scalar Patch)

> **Status:** Accepted
> **Date:** 2026-06-22
> **Context:** The dual-mode scenario editor reconciles its visual fields and
> raw `yamlText` buffer only at materialization, through the private
> `currentScenario()` funnel (PR #336, ADR-001 editor design;
> `.claude/rules/scenario-editor.md`). Today both `switchToYAMLMode()` and the
> visual-mode arm of `currentScenario()` produce YAML via
> `serializer.serialize(scenario)` — a **full canonical re-serialize** that
> silently discards the user's original comments, key order, and quoting style
> the moment they touch a field in visual mode and switch to YAML mode (or
> save from visual mode). [#725](https://github.com/tyabu12/pastura/issues/725)
> redefines the direction of the now-closed
> [#338](https://github.com/tyabu12/pastura/issues/338) (which proposed making
> `yamlText` the single source of truth — rejected: per-keystroke sync has no
> UX benefit since the two editors are never shown together, and it would cost
> cursor/IME stability and format normalization). This ADR decides the
> **opposite** north star: preserve formatting harder at the boundary, not
> normalize harder. It is the design pass #725 flagged as a prerequisite to
> implementation, and ships with the implementation in the same PR.

## 1. Decision

### D1. The logical source of truth is the abstract `Scenario` model

The editor's source of truth is neither the visual fields nor the raw
`yamlText` string — it is the abstract `Scenario` model. Visual and YAML are
two *editing surfaces* over it. The dual-buffer + boundary-reconcile design
(each surface authoritative for whichever mode the user last touched,
reconciled via `currentScenario()`) stays. This ADR does **not** unify the
buffers; it narrows the loss on the lossy `visual → YAML` conversion that
happens at the boundary.

Key asymmetry: **YAML is a strict superset** of the `Scenario` model. It
carries comments, key order, quoting style, and (via `extraData`) top-level
keys the visual UI does not expose. That superset relationship is exactly why
a pure single-source design (#338) loses data, and why minimizing
boundary-conversion loss — rather than buffer unification — is the right
target.

### D2. Scope: scalar-value *updates* only; everything else falls back

When the user's visual edits since the base YAML was last current amount to
**only scalar-value changes with no structural change**, the boundary emits
the original `yamlText` with **just those value spans patched in place** —
every comment, key order, and untouched-field formatting survives. Anything
outside that envelope falls back to today's full `serializer.serialize(...)`:

- **Structural change** — persona/phase add, remove, or reorder; phase `type`
  change; any list-length change (`options`, `then`/`else`, `output` keys);
  `extraData` key add/remove. A new element has no prior formatting to
  preserve, so a plain canonical serialize is the correct, lossless-of-intent
  result.
- **Block-scalar value change** (D4).
- **No base to preserve** — `yamlText` empty/blank (fresh-editor and
  template-seeded flows never populate it), or the base fails to re-parse.
- **Any uncertainty** in locating a value span (D3, conservative fallback).

This scoping aligns the high-value zone (an existing, hand-formatted value the
user tweaked) with the tractable zone (a single-line `key: value` splice).

### D3. Mechanism: `Yams.compose` + `Mark` → self-implemented value-end detection → text splice

`ScenarioYAMLPatcher` (a `nonisolated public struct` in `Engine/`, depending
on Yams + Models only) computes `patch(visual: Scenario, base: String) ->
String`:

1. Guard the fallback cases of D2 (blank base; base re-parse throws).
2. Detect structural change by diffing the re-parsed `base` Scenario against
   `visual`; on any structural difference, return `serializer.serialize(visual)`.
3. Collect the changed **inline** scalar fields. If any *changed* field is a
   block scalar in the base (Yams `Node.Scalar.Style.literal`/`.folded`),
   fall back (D4).
4. For each changed inline scalar, walk the composed Node tree to that scalar's
   node and read its `Mark` (start line + column). Locate the value span on
   that logical line — **column-anchored**, derived from the node position,
   never by searching for the old value string (which would mis-hit duplicate
   values elsewhere). The value end is the end of the logical line, excluding
   a trailing ` # comment` (and never splitting inside a quoted scalar that
   itself contains ` #`). Splice in the newly serialized value, quoted via the
   shared `YAMLScalarFormatter` (D6).
5. **Conservative fallback**: if any value span cannot be located with
   confidence (e.g. flow-style `{a: 1}` mappings the serializer never emits),
   abandon the patch and return the full serialize for the whole document. The
   patcher must **never emit corrupt YAML**.
6. **Reparse safety-net**: re-run the loader on the patched text and require
   semantic equivalence; on any divergence — including a parse failure — fall
   back:

   ```swift
   do {
     let reparsed = try loader.load(yaml: patched)
     guard reparsed == visual else { return serializer.serialize(visual) }
   } catch {
     return serializer.serialize(visual)
   }
   return patched
   ```

   `ScenarioLoader.load` *throws* on construct-time invariant violations (it is
   more than a parse — see `.claude/rules/engine.md` § "Parse vs validate
   boundary"), so the `catch` arm is load-bearing, not defensive cosmetics:
   `Scenario`/`Persona`/`Phase` all conform to `Equatable`, but the `== visual`
   comparison never runs if the patched text fails to parse. Both the
   inequality and the throw fall back.

The mechanism is deliberately **correct-by-fallback**: the patcher is an
*optimization* over `serializer.serialize`. Any case it cannot handle
confidently degrades to the status quo, never to a worse-than-today result.

### D4. Block-scalar value changes fall back to full serialize (v1)

`context`, `prompt`, and `template` serialize as `|` literal block scalars
spanning multiple lines (`ScenarioSerializer.yamlBlockScalar`); a top-level
`description` may also be authored as a block scalar in hand-written presets.
In-place patching a block value requires multi-line subtree replacement +
content-indent reconciliation — sharply higher complexity for what is, for
these fields, **no user-facing loss**: a block-scalar edit that falls back
re-serializes canonically, which normalizes *formatting* but loses *no
information* (the value itself is written faithfully). Since the only thing
lost is comment/key-order preservation on that one switch — and the value the
user just typed is preserved exactly — v1 accepts the fallback rather than pay
the block-patcher complexity. `context` is a frequently-edited block field, so
this is a real coverage limit, taken knowingly. Lifting it (block-scalar
patching) is a tracked follow-up (§5), not a v1 gap.

### D5. Preservation guarantee (in-scope updates)

For an in-scope scalar update, the emitted YAML equals the base `yamlText`
**byte-for-byte except the spliced value span(s)**: all head/inline/foot
comments, key order, quoting style of untouched fields, blank lines, and
trailing whitespace survive. Out-of-scope edits get today's behavior (full
canonical normalization) — **no regression**, because that is already the
status quo for every visual→YAML switch.

### D6. Quoting in lockstep — shared `YAMLScalarFormatter`

The splice must quote a new value by the *same* rules
`ScenarioSerializer.serialize` would, or the patched and fallback paths could
disagree (a value the serializer would quote, spliced raw, is a silent
corruption source). `ScenarioSerializer.yamlScalar` is `private`. The quoting
predicate + escape is extracted into a shared `internal nonisolated` helper
(`YAMLScalarFormatter`) consumed by **both** the serializer and the patcher, so
a future quoting-rule change cannot desync them.

### D7. Slot-in + funnel invariant + perf

- **Slot-in**: `ScenarioEditorViewModel.switchToYAMLMode()` and the
  `currentScenario()` visual-mode arm route the visual `Scenario`
  (`buildScenario()`) and the current `yamlText` through the patcher.
- **Funnel invariant preserved**: `buildScenario()` still appears exactly 3×
  (1 decl + the 2 sanctioned callsites), so
  `scripts/scenario-editor-funnel-gate.sh` stays green. The patcher is a
  **pure function** of `(Scenario, base)` — it reads no `ScenarioEditorViewModel`
  fields directly, so it introduces no new visual-state read that would
  re-open the #336 drift class. The `visualModeSavePreservesExtraData`
  behavioral tripwire remains the backstop.
- **Perf**: the patch runs only at the boundary (mode switch / save), exactly
  like today's serialize — **no per-keystroke work** (the #338 round-trip cost
  this design explicitly avoids). One `compose` parse of the base + a
  field-count-bounded tree walk + O(changed-fields) splices is well under any
  frame budget; no benchmark gate is warranted.

## 2. Why this shape

The drift class behind #336 was a *developer-facing correctness* problem (a
code path read the wrong buffer), already solved by the `currentScenario()`
funnel and guarded by the #338 tripwire. The *remaining* gap is narrow and
*user-facing*: a user who opens an existing, commented scenario
(`loadForEditing` seeds `yamlText` with the stored definition), tweaks one
field in visual mode, and switches to YAML mode finds every comment gone. The
surgical patch closes exactly that gap and nothing wider.

The correct-by-fallback posture (D3) is the load-bearing safety property: a
byte-splice driven by a start-only `Mark` is inherently error-prone at the
margins (quoting transitions, CRLF, trailing comments). Rather than chase
total robustness, every uncertain case degrades to the already-correct full
serialize, and the reparse net catches any splice bug semantically. The
feature can therefore ship without a proof of splice totality.

## 3. Consequences & relations to existing ADRs / rules

- **Supersedes the direction of #338** — preserve formatting at the boundary,
  not normalize. #338's "single source of truth" is explicitly rejected (D1).
- **`.claude/rules/scenario-editor.md`** — the funnel invariant is unchanged;
  its design-home pointer for the editor source-of-truth question is updated to
  cite this ADR. The `buildScenario()`-count tripwire and the
  `visualModeSavePreservesExtraData` backstop both remain authoritative.
- **`.claude/rules/engine.md` § "Parse vs validate boundary"** — the reparse
  safety-net (D3.6) relies on `ScenarioLoader.load` throwing on construct-time
  invariants; this ADR's `catch`-arm fallback is consistent with that boundary.
- **No new dependency** — reuses the already-pinned Yams (ADR-001/engine.md
  decode path); `ScenarioYAMLPatcher` stays within `Engine/ → Yams + Models`.

## 4. Definition of Done (mechanism contract)

The implementation is done when round-trip tests assert:

1. **Preservation** — load a YAML carrying comments + non-canonical key order +
   mixed quoting, change one in-scope scalar in the visual model, and assert
   the output equals the base with only that value span changed (comments, key
   order, untouched formatting intact).
2. **Fallback parity** — a structural change, a block-scalar change, a blank
   base, and an unparseable base each return exactly
   `serializer.serialize(visual)`.
3. **Semantic equivalence** — `loader.load(patched) == visual` for every
   in-scope patch (the safety-net never fires on a correct patch).
4. **Corruption resistance** — the documented edge cases (quoted value
   containing ` #`, plain↔quoted transitions in both directions, CRLF line
   endings, trailing-comment preservation on a quoted scalar) either patch
   correctly or fall back — never emit unparseable YAML.

## 5. Out of scope / open questions / follow-up

- **Block-scalar patching** (D4) — lifting `context`/`prompt`/`template` from
  fallback to in-place patch. Tracked as a follow-up to #725; v1 ships without
  it.
- **Structural-change patching** — persona/phase add/remove/reorder with
  surrounding-comment migration. Out of scope by design (D2); a new element has
  no prior formatting, and reorders raise orphaned-comment questions with no
  obviously-correct answer.
- **Confirmation diff UX** — the cheaper "name: A → B will be written"
  consent-on-loss affordance the #725 discussion raised. Complementary, not a
  substitute for preservation; deferred.
- **Flow-style input** — the patcher falls back on flow-style mappings the
  serializer never emits; native support is unmotivated until a real input
  source produces them.

## 6. Alternatives considered

- **#338 single source of truth (`yamlText` authoritative, visual as
  projection)** — rejected: per-keystroke parse→mutate→serialize has no UX
  benefit (the editors are never co-visible), and costs cursor/IME stability
  and unavoidable format normalization. This ADR is the deliberate inverse.
- **A format-preserving YAML library** (ruamel.yaml-style round-trip) — Swift
  has no mature equivalent; Yams round-trips through its `Node` model, which
  re-emits canonically and loses comments. A narrow self-implemented
  scalar-splicer is the minimum viable mechanism, and the fallback posture
  bounds its blast radius.
- **Confirmation diff only** (make the loss visible/consensual without
  preserving) — cheaper, but does not deliver the preservation #725 targets;
  kept as a complementary future option (§5).
