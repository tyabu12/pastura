## 1. Context

### 1.1 What forces the decision now

- **ADR-004 §4** ratified Option A at the Phase 2 → Phase 3 gate (Conditional GO on the
  #220 Models spike). The Engine port is Phase 3.0's core work item, and its architecture
  — what crosses the Kotlin/Native (K/N) boundary, and in what shape — determines both
  the port cost and the permanent interop surface iOS lives with afterwards.
- **ADR-004 §9.6's sizing basis has drifted.** It sized the Engine port at ~3 weeks on an
  8-phase-handler basis (2026-06-11). Current `main` has **13 phase handlers**
  (`Engine/Phases/`) and **39 files / ~5.4k lines** under `Engine/` (measured 2026-07-08,
  post-S0.1), plus two decisions that add port obligations: ADR-018 (`ScenarioYAMLPatcher`
  on Yams `compose`+`Mark`) and ADR-020 (`ENGINE_SCHEMA_VERSION` capability gate).
- **The named checkpoint risk needs a design answer, not a hope.** ADR-004 §6 flags
  "Kotlin expressiveness for the Engine's `AsyncStream<SimulationEvent>` pattern" as the
  abort-or-redirect checkpoint. §5 below dissolves most of that risk by inventory: the
  `AsyncStream` exists only at the outermost shell (`SimulationRunner.swift:125`), so the
  boundary can be callback-shaped without touching handler internals.

## 2. Options

Three axes were genuinely contested. Everything else (binding selection, SKIE adoption,
Android NPU, LiteRT-LM sequencing) stays deferred exactly as ADR-004 §3.6/§6/§7 left it.

### 2.1 Boundary shape — how the Engine surface crosses K/N

| Option | Pros | Cons |
|--------|------|------|
| **A — Plain functions + callbacks both directions; no `suspend`/Flow/AsyncSequence crosses (chosen)** | Boundary is inspectable and debuggable; each language keeps native structured concurrency; SKIE demotes to optional ergonomics; cancellation/suspension semantics are explicit contract clauses | Adapter code on both sides; callback-shape is less idiomatic than async sequences |
| **B — SKIE-generated Flow ↔ AsyncSequence bridging** | Most idiomatic Swift call sites; least adapter code | Hard-couples the app build to SKIE's Kotlin-version skew (ADR-004 §7 Q1); cancellation and back-pressure semantics are generated, not owned; the #220 spike did not exercise Flow bridging, so the risk is unmeasured on the hottest path |
| **C — `expect`/`actual` suspend functions at the boundary** | Single-language mental model inside Kotlin | K/N suspend-to-Swift interop is exactly the ergonomics risk §6 names; suspension/cancellation crossing the boundary implicitly is how the ADR-003 contract gets silently broken |

### 2.2 iOS engine switch timing (D1)

| Option | Pros | Cons |
|--------|------|------|
| **A — Switch iOS to the shared Kotlin Engine in Phase 3.0, behind an explicit gate (chosen)** | One engine, zero drift; parity harness becomes load-bearing rather than advisory; ADR-020 capability gate keeps a single `PhaseType` source of truth | K/N runtime on the app's hottest path; requires the §6 gate (parity + H7 symbolication + soak) before the switch |
| **B — Dual engines until Android ships** | Zero iOS runtime risk in Phase 3.0 | Every Engine PR lands twice; at current Engine velocity (3 new handlers in the month before this ADR) dual-maintenance cost is real; iOS-vs-Android drift undermines shared-scenario semantics (ADR-020) |

### 2.3 Data layer (D2)

| Option | Pros | Cons |
|--------|------|------|
| **A — Data stays Swift/GRDB for Phase 3.0 (chosen)** | Zero cost now — Engine never imports Data (hard rule), so the port never touches it; removes the ±2-week branch from §9.6 | Cross-platform persistence semantics duplicate later, when Android is scoped |
| **B — Port Data to a KMP stack (SQLDelight) now** | One persistence layer from day one | Pays a migration of working GRDB code for zero Phase 3.0 benefit (no Android app exists); expands the port surface exactly when the Engine port needs focus |

## 3. Decision

1. **Port the run-path Engine to `shared/engine` `commonMain`**, per the §4 scope split.
   The authoring/serialization path and all LLM backends stay Swift.
2. **Boundary principle: plain functions + callbacks at the K/N boundary, both
   directions.** No `suspend` function, no Flow, no AsyncSequence crosses. Structured
   concurrency stays inside each language. Two contracts implement this: the
   event/control boundary (§5.1) and the inference boundary (§5.2).
3. **`SuspendController` never crosses the boundary.** It stays a Swift object owned by
   the Swift adapter layer; suspension reaches Kotlin as a signal relay (§5.2), and the
   four invariants listed there are contract clauses, not implementation detail.
4. **Staged sequencing with a two-boundary vertical slice as the GO/NO-GO gate**
   (§6, Stage 2) — the ADR-004 §6 checkpoint made concrete and measurable.
5. **Acceptance mechanism = cross-language parity harness** (§6, Stage 4): same scenario
   YAML + same scripted mock-LLM outputs through the Swift Engine (ADR-013 harness) and
   the Kotlin Engine, canonicalized event-transcript comparison. Mechanism contract, not
   pinned thresholds (`.claude/rules/adr-writing.md` §2). Two rungs: JVM per-PR, K/N
   native (`macosArm64`) at least nightly — JVM parity alone does not witness the K/N
   memory model iOS will run.
6. **D1 (resolved): iOS switches to the shared Kotlin Engine in Phase 3.0, gated.** All
   three, explicitly: (i) Stage-4 parity green on both rungs; (ii) **H7 executed** —
   Kotlin-crash dSYM symbolication verified on a TestFlight build *before* the switch
   (graduates from ADR-004 §9.2 launch-prep deferral to hard switch precondition);
   (iii) one TestFlight soak cycle on the switched engine. Until all three fire, the
   Swift Engine remains the shipping engine.
7. **D2 (resolved): Data stays Swift (GRDB) for Phase 3.0.** Zero cost during the port:
   Engine never imports Data (hard rule), and the DB record types in `Data/Models/` are
   already separated from domain Models, so the D1 switch touches only conversion sites.
   Named revisit: when the
   Android app is scoped, evaluate consolidating iOS onto SQLDelight for a shared KMP
   Data layer as an explicit option (its own ADR) rather than defaulting to two
   platform-native stacks.
8. **D3 (resolved): planning figure ~4–5 wk + 1 wk interop hardening** (§1.3).
9. **LiteRT-LM stays orthogonal to the port** (ADR-004 §3.6 unchanged) — but the ported
   `LLMBackend` contract (§5.2) is written so a future `LiteRTLMService` slots in behind
   it, and the #969 exposure-path choice must weigh Android/Kotlin reuse, because the
   Kotlin API has the same constraint-exposure gap (§8).

## 5. Boundary contracts

Two directions cross K/N. Shared principle (Decision 2): callbacks at the boundary,
structured concurrency inside each language.

### 5.1 Event + control boundary (Kotlin → Swift events; Swift → Kotlin control)

The inventory that shrinks ADR-004 §6's named risk: `SimulationRunner.run` is the *sole*
`AsyncStream` continuation owner (construction `SimulationRunner.swift:125`, emitter
closure `{ continuation.yield($0) }` at `:135`); every downstream handler sees only the
two plain closures on `PhaseContext`. So the stream never needs to cross — only callbacks
do.

```kotlin
// commonMain surface
fun run(scenario, backend, …, onEvent: (SimulationEvent) -> Unit): RunHandle
// RunHandle: pause() / resume() / cancel() / notifyLLMResumed() — plain methods
```

- A thin Swift adapter — **`SharedEngineRunner`** — owns (i) `AsyncStream<SimulationEvent>`
  reconstruction exactly as today's shell does (yield from `onEvent`, finish on terminal
  event, `RunHandle.cancel()` from `onTermination`) and (ii) the suspension relay task
  (§5.2). **The App-facing surface (`SimulationViewModel`) does not change.**
- `pauseCheck` stays Kotlin-internal (runner → handler), never crossing. Today's
  `CheckedContinuation`+lock pause mechanism is reimplemented coroutine-native;
  `RunHandle.cancel()` maps to structured `Job` cancellation.
- **Threading clause**: `onEvent` fires from a Kotlin worker context; the adapter must not
  assume MainActor (today's `continuation.yield` is already thread-agnostic). Measured at
  the Stage-2 gate.
- SKIE (ADR-004 §7 Q1) demotes from "possible hard dependency" to "optional ergonomics",
  evaluated at Stage 2 with both callback boundaries in hand.

### 5.2 Inference boundary (Kotlin `LLMCaller` → Swift backend)

`LLMCaller` consumes the streaming path (`generateStream` at `LLMCaller.swift:322`) and
awaits `SuspendController.awaitResume()` on suspension (`:347`). Porting it requires
Swift→Kotlin streaming; the contract keeps it callback-shaped:

```kotlin
// commonMain — plain interface + constructor injection (no expect/actual;
// mirrors today's LLMService protocol-injection pattern)
interface LLMBackend {
  fun generateStream(request: GenerationRequest, callbacks: StreamCallbacks): StreamHandle
}
interface StreamCallbacks {
  fun onChunk(delta: String, isFinal: Boolean, completionTokens: Int?)
  fun onTerminal(status: TerminalStatus)  // completed | suspended | failed(errorCode, message)
}
// StreamHandle: cancel()
```

- **iOS actual**: a Swift adapter over `LlamaCppService` — one `Task` per call consuming
  the existing `AsyncThrowingStream`, forwarding chunks; `LLMError.suspended` maps to
  `onTerminal(suspended)`. `attachSuspendController` and the `SuspendController` object
  stay entirely inside this adapter.
- **Cancellation composition (contract clause)**: Kotlin coroutine cancellation MUST
  invoke `StreamHandle.cancel()` (`suspendCancellableCoroutine.invokeOnCancellation`),
  and the iOS actual MUST cancel the backing Swift `Task` from it. Without this clause,
  `RunHandle.cancel()` cancels the Kotlin `Job` but leaves the Swift stream — and its
  `llama_decode` loop — running.
- **Suspension relay** (ADR-003 semantics preserved): on `suspended`, Kotlin `LLMCaller`
  parks on a `CompletableDeferred`; `SharedEngineRunner` runs a Swift task
  `await controller.awaitResume()` → calls `RunHandle.notifyLLMResumed()` → the deferred
  completes and `LLMCaller` reissues. Invariants the port must carry:
  1. **Suspend re-issues stay OFF the retry budget** — the suspend loop is separate from
     the max-2 parse/empty retry counter (`SuspendController.swift:18` documents the
     contract). Stage-4 parity gets a scripted "suspend-then-succeed preserves retry
     budget" assertion.
  2. **One deferred + one relay task per suspension cycle** — a long inference can
     suspend N times; `CompletableDeferred` is single-shot, so each cycle allocates fresh.
  3. **Lost-wakeup safety is a design constraint, not luck** — it holds because
     `SuspendController` latches `.resumed` with no awaiter and the deferred completes
     sticky. Neither side may be refactored to a rendezvous primitive (e.g. a Channel)
     without re-proving this.
  4. **Controller ownership relocates** — today `SuspendController` reaches the engine
     via `PhaseContext`; post-port it is created/owned on the Swift side
     (`SharedEngineRunner` / backend adapter), and the App-lifecycle callers
     (`BackgroundSimulationManager.requestSuspend`/`resume`) re-point to that instance.
- Kotlin-side, `LLMCaller` wraps the callbacks internally
  (`suspendCancellableCoroutine`/`callbackFlow`); retry, `expectedKeys` parser guard,
  empty-field and language-mismatch retries (ADR-010 Step E) are all common code.
- **Crossing frequency**: per-chunk = on-device token rate (~10–50/s), orders of
  magnitude below K/N call-overhead concern; measured anyway at Stage 2.

## 6. Sequencing and gates

- **Stage 0 — pre-port refactors on `main`** (independent Swift PRs, land before the
  Phase 2 stabilization gate): S0.1 de-localization (merged, PR #990); S0.2 `EngineLogger`
  seam (PR #991, open at write time); S0.3 — record the scope split — is discharged by
  this ADR (§4); lock-seam follow-up (`OSAllocatedUnfairLock` shared *by value*
  into the nested `ExecutionContext` struct — a Swift `Mutex` swap needs a class-box
  restructure of the pause path; tracked on #501).
- **Stage 1 — land `shared/models` + CI groundwork**: land the validated `shared/models`
  module on `main` as **infrastructure** — not production-wired; the Swift consumer wiring
  (framework linkage, Roundtrip/KMPSpike tests) stays on `feature/kmp-spike-models` until
  **Stage 5** (was "Stage 2/5"; #1135's B′ decision supersedes the Stage-2 half — the
  2-gate consumer is a new detached package, not a revival of this wiring, and what returns
  at Stage 5 must be retargeted per the Stage-5 landmine below) — imported from that branch
  (`f73bc48`) with the §9.7 landmine checklist
  discharged (CI gate fix, stale-§9 guard, T11 removal). Add the empty `shared/engine`
  Gradle module beside it; konan pre-warm design for the Q4-cold CI ceiling (ADR-004 §9.3:
  17m40s measured warm vs 20-min budget).
- **Stage 2 — vertical slice = the GO/NO-GO gate** (ADR-004 §6 checkpoint, made
  concrete). Two PRs, deliberately ordered so the gate artifact stays minimal:
  - *(2-pre)* `ConditionEvaluator`+`Parser` standalone pure-module port — heaviest-tested
    pure logic, touches neither boundary; tooling shakedown, not part of the gate.
  - *(2-gate)* Minimal both-boundaries slice: `PhaseDispatcher` + `SpeakAllHandler` +
    `PromptBuilder` (hard build-dep — in the slice, or stubbed) + minimal runner loop +
    minimal `JSONResponseParser` + `LLMCaller` core (retry loop + stream consumption +
    suspension relay IN; `PartialOutputExtractor`, language-adherence retry,
    `StreamFailure` taxonomy stay Stage 3) — wired through **both** §5 contracts to a
    Swift spike consumer, **including a Swift-side scripted streaming `LLMBackend`
    actual** producing a real `AsyncThrowingStream` through the §5.2 adapter. A
    Kotlin-side mock alone does NOT satisfy the gate — the point is to measure the real
    Swift→Kotlin inference seam before GO fires.
  - **Spike-consumer host — decision B′, "detached package"** (resolved 2026-07-16, #1135;
    independent Fable-tier second opinion). The spike consumer is a standalone macOS
    SwiftPM package at `tools/kmp-gate-spike/` with a local-path `.binaryTarget`, built by
    the nightly + `workflow_dispatch` only. **No per-PR lane acquires an XCFramework
    dependency** — not the iOS xcodebuild, not the root `Package.swift` harness build, not
    a dev `swift build`. Rejected: *(A)* linking into the iOS app target — buys evidence
    this gate does not need (iOS-runtime evidence is routed to H5/H7/Stage 5) at the cost
    of re-coupling every iOS build to XCFramework assembly, which Stage 1 deliberately
    stripped; *(B-root)* a `.binaryTarget` in the root `Package.swift` — relocates that
    coupling into the harness lane rather than removing it, since `.claude/rules/xcodebuild-cli.md`
    mandates `swift build` after Engine changes; *(C)* a throwaway spike branch — discards
    the §10-permanent adapters (`SharedEngineRunner`, the backend adapter) while still
    paying the stale-pbxproj rebase.
    - **Host-bound claims.** Of the five measurements below, only (ii)'s performance
      *absolutes* are host-sensitive (macOS vs iOS K/N — same Darwin/arm64 runtime and
      memory model). (i), (iii), (iv), (v) are host-insensitive. Record the gate's perf
      figures on #501 as macOS-host; iOS-device absolutes defer to Stage-5 QA. The
      abort/redirect criteria are unaffected — §5.2 already frames per-chunk crossing at
      10–50 tok/s as orders of magnitude below K/N call-overhead concern. This is
      consistent with the ADR's existing evidence architecture: Stage 4's parity rung is
      `macosArm64` and §7 names the ADR-013 macOS harness as its Swift-side runner.
    - **Enabled at 2-gate, not Stage 5** (both landed by #1135): the `macosArm64` Gradle
      **target** on both shared modules, and a framework/XCFramework **export** on
      `shared/engine` (`PasturaSharedEngine`, re-exporting `shared/models` — which forces
      the models dep to `api`). Only the target *registration* is pulled forward from
      Stage 4; **the Stage-4 parity harness itself is unchanged** and lands on schedule.
      The engine export was previously scoped to Stage 5, which contradicted this gate's
      own acceptance criterion — Swift must link a real framework *before* GO fires.
  - **Measured at the gate**: (i) event-boundary ergonomics incl. threading clause;
    (ii) inference-boundary ergonomics — chunk-relay overhead at realistic token rates +
    suspension-relay round-trip; (iii) K/N shim-budget re-measure on the Engine-consuming
    surface (the spike exercised 8/21 Models types — ADR-004 §9.3 Q9); (iv) SKIE-vs-vanilla
    (ADR-004 §7 Q1) with both boundaries in hand; (v) kotlinx.serialization round-trip parity on
    `TurnOutput`/`OutputSchema`. Result recorded on #501; abort/redirect per ADR-004 §6
    if ergonomics fail.
- **Stage 3 — bulk port in dependency order**, `commonTest` parity porting with each
  module: the Swift Engine test files are the executable spec; a module isn't done until
  its test file has a commonTest sibling.
- **Stage 4 — cross-language parity harness** (Decision 5): JVM rung per-PR; K/N native
  rung (`macosArm64`) at least nightly.
- **Stage 5 — iOS consumption switch + code-merge** (Decision 6 gate; carries the
  ADR-004 §9.7 items and merges the remaining `shared/` — the engine module + the Swift
  consumer wiring held back at Stage 1. `shared/models` itself already landed at Stage 1).
  - **§9.7 landmine — two-umbrella exclusivity** (created by #1135; recorded by the PR
    that created it). `PasturaShared` (models-only) and `PasturaSharedEngine` must
    **never be linked into the same binary**: the engine umbrella statically embeds every
    models symbol, so the pair means duplicate symbols and two copies of the K/N runtime.
    Inert today — nothing on `main` links either. It arms at Stage 5, because the retained
    `feature/kmp-spike-models` wiring embeds the *models* umbrella into the app target
    (`Pastura.xcodeproj/project.pbxproj` Frameworks + Embed Frameworks phases,
    `scripts/kmp/assemble-xcframework.sh`, `scripts/setup.sh`, `scripts/git-hooks/pre-commit`)
    and Stage 5 merges that wiring back. **At merge-back, retarget it to
    `PasturaSharedEngine` or drop it** — do not restore it as-is. The spike branch's H6
    framework-size check ("Expected 1 PasturaShared.framework") needs the same retarget.
  - **Open, informed by the #1135 probe**: whether the app's per-PR CI assembles the
    XCFramework itself or consumes a prebuilt artifact. The nightly's
    `workflow_dispatch`-only warm-cache probe measures the assembly lower bound against
    the repo's ≤10-min per-PR budget; read it together with cache-restore time and a
    key-miss margin, both of which the probe deliberately excludes.
  - **Umbrella consolidation** — whether the two umbrellas collapse into one is a Stage-5
    call *by design*: its inputs are the 2-gate SKIE-vs-vanilla and shim-budget
    measurements, which do not exist until the gate runs. Deciding earlier would be
    deciding without evidence.

## 7. Cross-language parity obligations (standing, not stage-scoped)

- **ADR-020 `ENGINE_SCHEMA_VERSION`**: once two engines exist, `PhaseType` parity is
  load-bearing for the capability auto-gate. One source of truth — parity test at
  minimum, codegen if noisy; the Kotlin enum must never fork from `PhaseType.allCases`.
- **`ScenarioConventions.isValidFieldName` — single source of truth across the port
  boundary**: the rule-name char-class rule lives once, in Models
  (`ScenarioConventions.swift:134`), called by both the ported `ScenarioValidator`
  (`ScenarioValidator+OutputFieldNames.swift:27`) and the Swift-resident
  `GBNFGrammarBuilder` (`GBNFGrammarBuilder.swift:146`). Post-port the function moves to
  commonMain with Models, so the Swift-side builder must keep calling the ported function
  through the K/N Models surface — not fork a Swift copy. Stage 1's spike-branch rebase
  verifies `shared/models` actually carries `ScenarioConventions`; a shared fixture test
  pins the behavior on both sides.
- **Scenario-factory census CI gate**: new `PhaseType` cases already break the Swift-side
  shell gate; the Kotlin port must not introduce a second place that check needs to know
  about.
- **ADR-010 language axis**: the `LanguageDispatch` port keeps the consumer-scoped
  `engineLanguage` resolver naming + CI-guard semantics; the language-mismatch retry
  stays in shared `LLMCaller`.
- **ADR-003 BG execution**: the §5.2 suspension relay is the load-bearing piece —
  `SuspendController` semantics survive the port bit-for-bit (Stage-2 measured, Stage-4
  asserted).
- **ADR-013 harness**: unchanged (Swift/macOS); Stage 4 *uses* it as the Swift-side
  runner.

## 8. Relation to the LiteRT-LM track (#496 / #969)

The port and the backend migration stay decoupled (ADR-004 §3.6: Phase 3.0 is
llama.cpp-unified), but two design facts couple their futures:

- **The §5.2 `LLMBackend` interface is the future migration seam.** A `LiteRTLMService`
  would slot in behind it exactly as `LlamaCppService` does. The #969 R1–R8 parity
  contract (fixed primary-first key order for `PartialOutputExtractor`, structure-only
  constraints, `schema == nil` no-op, failure-taxonomy mapping) therefore binds any
  backend implementing this interface — the ported common `LLMCaller`/parser/extractor
  pipeline is deliberately backend-neutral, which is what makes both the llama.cpp
  present and any LiteRT-LM future (including its prompt-only Path-3 floor) viable
  without Engine changes.
- **The constraint-exposure gap is cross-platform.** LiteRT-LM's C++ core has full
  constrained decoding, but neither the Swift nor the Kotlin API exposes it (#969 survey;
  upstream Kotlin FR: LiteRT-LM #1662, watched — not filed by us, per operator decision).
  Whatever exposure path #496 eventually lands (tool-call vehicle / upstream / two-layer
  patch / prompt-only) should be evaluated for Android reuse, since Phase 3.1's Android
  backend hits the identical gap. iOS migration readiness (re-anchored off LiteRT
  #6745 on 2026-07-10 — ADR-004 §3.6): `official-LiteRT-LM-release iOS GPU works
  via the SwiftPM xcframework (presumed-met, LiteRT-LM #2689) AND (constraint-exposed
  OR prompt-only-acceptable)` — the live conjunct is the second one (#969). LiteRT
  #6745/#1050 stay live markers for *this* Android/KMP path, where the Kotlin
  artifact's GPU link topology is unverified.

## 9. Rationale

- **Callbacks over generated bridging (Options 2.1)**: the #220 spike validated plain
  K/N interop, not Flow bridging; the boundary inventory (§5.1) shows the async-sequence
  shape is only skin-deep on the Swift side. Owning the boundary as explicit callbacks
  makes the two hardest semantics — cancellation composition and the ADR-003 suspension
  contract — *contract clauses that Stage-2/Stage-4 can test*, instead of emergent
  behavior of a codegen layer pinned to Kotlin-version skew.
- **A-with-gate over dual engines (Options 2.2)**: dual maintenance is a real, recurring
  cost at current Engine velocity, and engine drift directly threatens ADR-020's
  shared-scenario semantics. The gate converts the "K/N on the hottest path" risk into
  three checkable preconditions and makes the parity harness load-bearing.
- **Data stays put (Options 2.3)**: the Engine → Data import ban (CLAUDE.md hard rule)
  means the port literally cannot touch Data; porting it now would be scope creep with
  no consumer.
- **Serialization path stays Swift**: 736 lines whose only consumers are the iOS editor
  and run-record snapshots; the ADR-018 design is Yams-node-specific by construction.
  Porting it buys nothing until an Android editor exists.
- **Parity harness as acceptance**: transcript-level comparison through the existing
  ADR-013 harness measures the thing that actually matters (identical event streams for
  identical inputs) and survives model/backend swaps per the mechanism-contract rule —
  no pinned thresholds to re-litigate.

## 10. Trade-offs

**Easier:**

- Android (Phase 3.1) and Desktop (3.2) consume a tested, parity-proven Engine instead of
  re-implementing it in Kotlin — the benefit ADR-004 §5.1 records.
- Engine behavior gets a second, cross-language executable spec (Stage-4 harness), which
  also hardens the Swift side against accidental semantic drift.
- The `LLMBackend` seam makes the eventual LiteRT-LM evaluation (#496) a contained
  backend-swap behind the seam on each platform independently — iOS-first per the resolved
  sequencing (ADR-004 §3.6; #496 OQ#1), with Android reusing whatever exposure path #496
  lands at Phase 3.1 (§8).

**Harder / accepted costs:**

- iOS's hottest path eventually runs on the K/N runtime (D1) — mitigated by the three-part
  gate, but a K/N field issue class (GC pauses, allocation behavior under memory
  pressure) is genuinely new to iOS; H7 symbolication as a hard precondition exists
  precisely for this.
- Two boundary adapters (`SharedEngineRunner`, `LLMBackend` iOS actual) are permanent
  code with subtle contracts; the §5.2 invariants must be defended in review forever
  (they are documented here for that reason).
- ~5–6 weeks of Engine-freeze-ish sequencing: Stage 3's bulk port conflicts with
  concurrent Engine feature work; new handlers landed mid-port must be ported twice.
  (Accepted: Phase 2 feature velocity on the Engine is expected to taper by then.)
- CI cost: KMP jobs (konan cache, JVM parity per-PR, nightly native rung) press against
  the ≤10-min CI budget; Stage 1 owns the pre-warm design (ADR-004 §9.3 Q4-cold).
- The authoring path staying Swift means a future Android editor pays the
  serializer-port (or redesign) cost later, knowingly.

§6's Stage-2 gate listed five measurements. All five are now discharged, but not all
five by the same *kind* of evidence, and the difference matters when reading the
result — so each row below states its method, not just its outcome.

**The GO/NO-GO verdict is deliberately NOT recorded here.** Its absence is a decision,
not an omission: the gate's job was to produce evidence, and the call belongs to the
operator reading it. Everything below is input to that call.

Swift-side artifacts: `tools/kmp-gate-spike/` (two §10 permanent adapters, their
contract suite, and `kmp-gate-bench`). Figures reproduced with
`swift run --package-path tools/kmp-gate-spike kmp-gate-bench` from the repo root.

| # | Method | Result |
|---|---|---|
| (i) event-boundary ergonomics | counted from source by `ShimInventory`; threading clause evidenced by the Pattern 6 probe | see shim budget below |
| (ii) inference-boundary cost | runtime, differential, macOS host | ≈20 µs/chunk (17.8–25.4 over 5 runs); suspension round trip ≈50 µs best |

### (i)/(iii) Shim budget — 24 declarations

Counted, not tallied by hand, because a budget quoted in prose stops matching the code
it describes. Mutually exclusive categories, so the total counts declarations:
**retroactive `Sendable` vouch 2**, **hand-asserted `Sendable` conformance 13**,
**type-level `nonisolated` only 9**. (Re-run after code review: the review's own fixes
added three shims — a latch-testing `RunHandle` fake among them — which is the figure
behaving as intended rather than drift.)

**The count includes test-side shims**, because the scan roots are the adapter sources
*and* their test target. That is deliberate — a Kotlin protocol implemented in a test
needs the same hand-written `Sendable` vouch a production one does, so it is real
boundary cost — but it means the figure moves when tests are added, and a Stage-3
reader comparing budgets must compare like for like rather than assume production-only. Not counted because it is a burden rather than a
construct: K/N exports no default arguments, so every `Scenario` is built with all 12
parameters spelled out.

### (ii) The crossing has ~3 orders of magnitude of headroom

Per-chunk overhead is **≈20 µs** (17.8–25.4 µs across five consecutive runs), implying
roughly 40,000–56,000 tok/s if the crossing were the only cost; real generation runs at
10–50 tok/s. §5.2 already framed per-chunk crossing as "orders of magnitude below K/N
call-overhead concern" — that was an estimate, and this is the first direct measurement
supporting it. The run-to-run spread is ±20%, which is why a range is quoted: the
differential is a slope between two timings on a contended host, and a single decimal
would be false precision.

The **suspension round trip is ≈50 µs best** — a spread on one host, not a bound. The
same caveat as the per-chunk figure applies: re-running will not reproduce these digits
(review runs landed both above and below the recorded spread), and nothing here depends
on it doing so. What the figure has to support is an order-of-magnitude claim, and it
does that at any sample in the observed range.

> **Correction (supersedes the figures first published on #501).** The initial
> measurement reported 19.9 µs/chunk and a 2.08 ms suspension round trip. Both were
> instrument artefacts, found in code review:
>
> - The per-chunk denominator was computed as `(deltas + 1) × 2` while the script
>   builder actually emitted a different number of chunks, so the slope was divided by
>   the wrong count.
> - **The 2.08 ms was almost entirely the measuring apparatus.** The round trip was
>   timed by a 1 ms poll loop, so no sample could report less than the poll interval
>   plus timer leeway. Timestamping inside the backend's call handler instead puts the
>   same quantity at ≈50 µs — the published figure was ~40× the real latency.
>
> The *conclusion* is unchanged (and slightly strengthened): the crossing retains ~3
> orders of magnitude of headroom. Only the numbers moved.

**Configuration: these are `debug` Kotlin/Native figures.** `stage-framework.sh` defaults
to debug and the nightly calls it with no argument, so that is what the recorded numbers
measure. Spot-checked against a `release` XCFramework over three runs: per-chunk
17.1–27.9 µs (indistinguishable) and round trip 32.5–38.6 µs best (release is the faster
of the two). The headroom conclusion holds under either configuration, which is why the
debug default is left as-is — but a Stage-3 reader comparing absolutes must match
configurations first.

Per §6's host-bound clause, only these absolutes are host-sensitive.

### (iv) SKIE evaluation — evidence for ADR-004 §7 Q1, which stays open

SKIE's headline features target a boundary shape this ADR **deliberately did not
choose** — §2.1's option A predicted exactly this, listing "SKIE demotes to optional
ergonomics" among its consequences. §5 mandates a callback-only boundary, so no
`suspend` function and no `Flow` crosses it, and SKIE's suspend→`async` and
Flow→`AsyncSequence` conversions have nothing to act on here. Its sealed-class and enum exhaustiveness support likewise
applies to types the run path does not marshal.

What SKIE *would* remove from the measured costs is the default-argument burden — real,
but the one item above that was not even countable. What it would **not** remove is the
dominant one: SKIE does not generate `Sendable` conformances, so all 15 `Sendable`
shims (2 + 13) survive it. That request has sat open with no maintainer reply and was
questioned as abandoned in July 2025; commenters there point at a Kotlin-compiler
request (KT-74440) as the underlying blocker, i.e. not something SKIE resolves alone
([touchlab/SKIE#48](https://github.com/touchlab/SKIE/discussions/48), read 2026-07-18). Practitioners
also report Swift 6 strict-concurrency violations inside SKIE-*generated* files, which
would land in exactly the regime this app compiles under.

Against that, Q1's stated cost — coupling the iOS build to a Kotlin-version-specific
compiler plugin — is unchanged. This is evidence, not a verdict: adoption stays where
§"Out of scope" put it.

### (v) `OutputSchema` does not round-trip — the one negative result

Two-sided parity is not reachable today: no build in this repo can link the Swift
`Codable` types and Kotlin in one process (SwiftPM forbids a target's sources from
escaping its package root, and the conformances live in `Pastura/Pastura/Models/`).
The measurement is therefore one-sided — Kotlin decoding Swift-authored bytes frozen by
`pastura-harness emit-golden`. Swift decoding Kotlin's output stays unmeasured and
belongs to Stage 3's parity harness.

`TurnOutput` is in parity. `OutputSchema` is not: Kotlin cannot decode Swift's bytes at
all. Three divergences, only the first of which is a serialization detail —
**tagging** (`{"string":{}}` vs `{"type":"string"}`), **case name** (`choice` vs
`enumeration`), and **payload** (Kotlin's `Enumeration` requires `options: List<String>`;
Swift carries none).

The third outlives the wire question. Swift removed that payload because enumerating
options into the GBNF grammar crashed llama.cpp's sampler on multi-byte values
(ADR-002 § Amendment 2026-06-14, #599), so the mistake is unrepresentable in the Swift
type. Kotlin still models the retired concept. Nothing reads `options` today — the
**Kotlin** `PromptBuilder.formatOutputSchema`
(`shared/engine/src/commonMain/kotlin/com/pastura/engine/PromptBuilder.kt`) ignores
every `Kind`, including `Kind.Enumeration`, and carries a comment warning that a port
"improving" it into option literals would reintroduce the crash class — so there is
**no behavioural divergence at present**. (The language matters: Swift has a
`PromptBuilder` of the same name, and it is not the one carrying this guard.) The gap
is that Swift's guard is the type system and Kotlin's is a comment. Which side should
move is a Stage-3 question; this gate only records that they disagree.

The parity suite asserts the rejection rather than skipping the type, so aligning the
shapes later fails a test and forces this record to be updated instead of going stale.

## 12. Amendment 2026-07-18 — Stage-2 gate verdict: **GO**, with four conditions

§11 (same date) records what the gate *measured*; this section records what the operator
*decided* from it. §11's deliberate blank is now filled.

**Verdict: GO.** Stage 3 proceeds, subject to the four conditions below — they are
constituents of the decision, not recommendations attached to it.

### Why

ADR-004 §6's checkpoint list has two entries; only one applies to the Engine port —
"Kotlin expressiveness for the Engine's `AsyncStream<SimulationEvent>` pattern" (the
other concerns Android beta reception). §5's callback-only boundary dissolves it by
construction — the stream never crosses — and the gate confirmed that against a real
Swift consumer rather than a Kotlin-side mock. **No measurement fires the criterion
independently.** Note also that §6 places that checkpoint *after step 3, the whole port*;
this ADR discharges it early, at a vertical slice. That is a strengthening of ADR-004's
sequencing, not a departure from it.

The second consideration is blast radius. **This GO commits labor, not shipped behavior.**
The iOS consumption switch is D1's separate three-part gate (both parity rungs + H7
symbolication + TestFlight soak); a wrong GO here costs port weeks, not users. That
asymmetry is what makes the residual uncertainty below tolerable.

### Per-measurement reading

| # | Bearing on the verdict | Fires ADR-004 §6? |
|---|---|---|
| (i) event boundary | **Strongly supports** — the direct answer to the named criterion. Caveat carried forward: "neither adapter needs `@concurrent`" holds for a *structural* reason (both entry points are synchronous), and Stage 5 changes the shape — so it is a Stage-5 checklist item, not a settled property | No |
| (ii) inference boundary | **Supports; the most robust figure here.** Only an order-of-magnitude claim is load-bearing, and the largest instrument error already found in this PR was ~40× — applying that again leaves the conclusion intact | No |
| (iii) shim budget | **Weakly supports.** 24 is a minimal slice *including test-side shims*: a **floor** on the full-port budget, not an estimate of it | No |
| (iv) SKIE | **Neutral-to-supporting.** It closes the escape hatch (SKIE generates no `Sendable` conformances; the blocker is KT-74440) — but the hatch was not needed. §2.1 option A predicted exactly this | No |
| (v) `OutputSchema` | **The one result arguing against**, and it converts into conditions 1–2 rather than into abort: the direction of the fix is determined, and the parity suite asserts the rejection instead of skipping the type, so the divergence cannot rot silently | No — a mirror defect, not a boundary-ergonomics failure |

### The four conditions

**1. Align `OutputSchema` at the head of Stage 3 — Kotlin moves to Swift's shape.**
Semantic authority is Swift's: the `options` payload was removed because enumerating
option values into the GBNF grammar crashed llama.cpp's sampler on multi-byte values
(ADR-002 § Amendment 2026-06-14, #599), which makes the mistake unrepresentable in the
Swift type while Kotlin still models the retired concept.

**The surface is wider than the type.** §11 records that nothing *reads* `options`, which
is true of `PromptBuilder.formatOutputSchema` — but Kotlin still *writes* it:
`OutputSchema.from(phase)`
(`shared/models/src/commonMain/kotlin/com/pastura/models/OutputSchema.kt:65`) constructs
`Kind.Enumeration(options)` for CHOOSE phases with non-empty options, and that value
crosses the §5.2 boundary as `LLMBackend.schema`
(`shared/engine/src/commonMain/kotlin/com/pastura/engine/LLMBackend.kt:95`). Scope the
Stage-3 PR to the construction branch and the boundary DTO, not to a two-line type edit.

**And the designated authority carries a stale reason.** `OutputSchema.swift:148`
justifies the removal by "``ChooseHandler`` `validateAction` (invalid → `options[0]`)" —
superseded by ADR-021 § "Amendment 2026-07-17", which drops off-menu actions and emits
`.actionRejected` instead. The Swift *type* is still the right authority; its *comment*
needs refreshing in the same PR. (This was caught by the Step-1b critic on the plan for
this very amendment — see condition 4, which it independently exemplifies.)

**2. Every type mirrored into `shared/**` lands with golden-parity coverage in the same PR.**
This condition replaces an earlier draft ("move the per-PR JVM parity rung from Stage 4 to
Stage 3 day one"), whose stated rationale the git record contradicts. `shared/models`'
`OutputSchema.kt` first reached `main` on 2026-07-12 (`a008e797`, Stage 1 PR-1), imported
from spike content predating the 2026-06-14 Swift change (`b5ffdca2`, #599/#606) by 28
days. **It was born diverged, not rotted** — it existed on `main` for 6 days before the
gate caught it, and what caught it was new coverage (`ed50ba71`, "measurement (v) golden
JSON parity"), not a faster cadence. A per-PR rung running on 2026-07-12 would have been
green, because no golden existed to compare against. `shared/models` is moreover *frozen
by design* at the spike SHA (see the ADR-027 entry in `docs/decisions/INDEX.md`), so
divergence there is the expected state rather than an incident.

The generalizable lesson is coverage-at-landing, not cadence. Whether the JVM rung also
moves earlier is a separate call on its own merits, weighed against the ≤10-min per-PR CI
budget §10 already flags — it is deliberately **not** decided here.

**3. Replace §10's velocity assumption with observation before scheduling Stage 3.**
§10 accepts the Engine-freeze cost on the basis that "Phase 2 feature velocity on the
Engine is expected to taper by then". As of this amendment that is false: the Engine took
**16 commits** in the ten days after 2026-07-08 (narrate phase, `pairwise_payoff`, mood,
persona secret, DRY anti-repetition sampler, lint rules). Either wait for the current
burst to actually subside, or adopt a **dual-landing policy** — every Engine PR during
Stage 3 carries its `commonMain` port or a port-ledger entry. Do not start on the
un-restated assumption. See also the sizing correction below, which moves the same
estimate.

**4. Stage 3's "module done" means a `commonTest` sibling whose deletion fails the build.**
§6 already requires the sibling to exist; existence is not the property that matters.
The evidence for this is this PR's own review history: what was found defective was
consistently the *instruments, guards, and why-comments* rather than the code they
watched — a poll loop that manufactured its own 2.08 ms reading, a `grep` guard matching
its own predicate string, a race test that scheduled no race, and three why-comments
asserting mechanisms the code did not have. Verify by perturbation, and treat a guard's
success case as proving nothing.

### Accepted on faith (the gate did not measure these)

1. **macOS ↔ iOS K/N runtime equivalence** — same Darwin/arm64 runtime and memory model;
   (ii)'s absolutes are macOS-host per §6's host-bound clause. Unverified until Stage 5.
2. **K/N GC behavior under device memory pressure**, with llama.cpp holding ~3 GB against
   the `ModelRegistry.minRAM` 6.5 GB floor. **The largest genuine risk the gate does not
   cover**; D1's gate and H7 symbolication are the backstops.
3. **The Swift-decodes-Kotlin direction** — (v) is one-sided by necessity; deferred to
   Stage 3's parity harness by design.
4. **H5/H7 distribution verification** — deferred per ADR-004 §9.2, unchanged.
