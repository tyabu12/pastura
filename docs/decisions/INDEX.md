## ADR-026 — LLM-dynamic Word Wolf topics (near-term no-go)

LLM-dynamic Word Wolf topic generation — near-term **No-Go**: keep the static `words:` pair; do not have the on-device model generate the majority/minority pair per playthrough. Harness-measured on Gemma 4 E2B (n≈100 × 5 categories × ja/en, 2026-07-16): a no-LLM-judge validator fails three ways — misses semantic part-of / script homographs (ja `カメ↔甲羅` 52%, `ネコ↔猫` 17%; caught 1 of ~70), false-positive-rejects good pairs (`Pen↔Pencil` via substring), and passes hallucinated non-words (`のび筆`); diversity collapses (every category dominated by 1-2 anchor pairs, ~3-5 usable distinct pairs each, so a curated ~30-pair static list wins on variety/cost/safety); and category quality is per-language (same "animals" catastrophic in ja, clean in en). General principle: LLM-generated game content must clear calibration AND diversity AND script-robustness, gated by harness measurement, else prefer static curation. Deferred (non-binding) design sketch retained for a stronger model: a non-diegetic `generate` LLM phase (structured pair → `state.variables`, not the conversation log; internal validator+retry+fallback) + `assign source_variable:`. Revisit on the LiteRT-LM migration / a successor model (ADR-002 §8.2; #496); tracked under #906 (Status: Accepted; #906)

## ADR-027 — Generic `pairwise_payoff` scoring logic

Generic `pairwise_payoff` scoring logic — move the two-player payoff matrix out of Swift (`PrisonersDilemmaLogic`'s `switch (act1, act2)` over English `cooperate`/`betray` literals) into scenario YAML (`payoff: [{when: [A, B], points: [x, y]}]`, positional match on `Pairing.action1/2`, no matching row → no points), on the `EventReactivePayoffLogic` (#931) YAML-authored-token precedent. Unblocks the last un-localized surface: `prisoners_dilemma.yaml` is `language: ja` with English options, because translating them makes every pair miss the switch and fall to `default:` → all agents scored as mutual defectors (a *latent* trap — under today's English options `default:` is reachable only as (betray,betray), where 1,1 is the correct game rule; PR2's legacy shim table must therefore keep all **four** rows). `ScoreCalcLogic.prisonersDilemma` is kept **permanently** and shrinks to a shim over the generic logic: Copy & Edit (`ScenarioDetailActionBar.swift:88-89`) clones preset YAML into `ScenarioRecord.yamlDefinition` (a text column) on TestFlight-shipped devices, and such local records never pass a gallery index, so only ADR-020's D5 parse-throw reaches them — deleting the case makes a user's own saved scenario unopenable, with no migration path. `?? ## ADR-028 — Dark-mode token pairing (trait-resolving `PasturaDynamicColor`)

Dark-mode token pairing mechanism — `PasturaDynamicColor` wraps a light/dark `PasturaColorValue` pair in a `UIColor(dynamicProvider:)` closure branching on `traitCollection.userInterfaceStyle`, and the paired `Color.*` aliases point at it, so every existing consumer adapts with **no callsite edit** (520 `Color.<name>` references in 87 files, of 218 Swift files in `Views/` + `App/`, at `15f8084`). **Eight pairs at landing, 67 now**: §2.9's table mapped both `nightSurface` and `nightBubble` onto `bubbleBackground`, so `nightSurface` (no UI consumer) had no light partner; **#1282 resolved it by deleting the token** (the leading candidate, per the doc's closing footer 「追加より削除を優先」) and wired 18 more pairs — the §2.6 alert family and §2.7 interactive states; **#1313 wired 14 more** (the §2.4 meta presets and two of the three §2.12 header slots). The **light** alias is the dynamic side; `night*` stays static so an explicit dark request stays expressible — though this change moved their last consumer to the raw palette, so `Color.night*` now has zero consumers. **Exactly 1** of 68 light tokens has no dark counterpart and **0** still owe gate 1 an answer: that one is #1313's `headerMetaSubdued`, unpaired but *resolved* — recorded as fixed in both appearances, the second branch gate 1 always admitted and nothing had exercised — so from #1313 on, "unpaired" and "owing an answer" are different counts, now 1 and 0. (`inkOnAccent`, added by #1283 with its dark answer open, was settled by slice 4: **paired**, because darkening `nightMoss` instead would have invalidated §2.7's washes, §2.4's dot ladder and §2.5's body window, all anchored on its value.) `UIUserInterfaceStyle = Light` is **removed** (#1284): all 5 gates are met — values designed, `nightSurface` resolved, raw-SwiftUI-colour sites triaged against a stated predicate rather than a pinned count, real-device dark QA, dark share-card verified on device — so the app now follows the device appearance. That device pass found **three** defects, each a class the gate ladder could not see: the launch colorset had no dark entry and `LaunchAnimationConfig.backgroundColor` would have flashed cream over it (the config's own doc comment had declared that lock-step load-bearing); five `.borderedProminent` buttons measured ≈2.13:1 in dark, which `PasturaPrimaryButtonStyle`'s doc comment had predicted exactly; and three `shadow(color:)` sites read paired aliases, inverting into pale halos. The last two are now barred by custom SwiftLint rules, each verified with a control pair. A **fourth** surfaced in re-QA of those fixes — the model-load scrim, same root cause — and it corrected the rule the shadows had suggested: an occluder's requirement is not "fixed in both appearances" but **darker than every ground it covers**, which raw `ink` still failed (it is lighter than every night surface), so a new alias-less `scrim` token carries it. That one has no lint guard and is pinned by `SimulationScrimStyleTests` instead. **Two scope corrections matter more than the defects**: gate 3's own predicate globbed `Views/` + `App/`, which does not reach the top-level `PasturaApp.swift` (three untriaged raw-colour hits there; use `Pastura/Pastura` instead), and **`Assets.xcassets` was outside every gate predicate**, leaving `AccentColor` unpaired and unflagged by construction — the § Alternatives rejection of asset catalogs had named the blinding mechanism but not the entries that already existed. Left open and stated rather than papered over: `nightPage` on `ViewerPredictionSheet` (slice 4's one named gate-4 question) was not confirmed on screen, and the three fixed surfaces post-date the pass that closed the gates. Manual walkthrough: `docs/qa/dark-mode-qa.md`. #1282 is **slice 1 of 4** on the first gate — all four have now shipped (**slice 3** the 17-colour §2.5 avatar palette, which needed a *fourth* derivation arm and silently un-pinned the share card one level below `HighlightCardPalette`; **slice 4** (#1325) the §2.1/§2.3/§2.8 remainder plus `inkOnAccent`, which found §2.3's four steps **invert** in dark and discharged the tripwire slice 2 armed on `promoBackground`) — and establishes that dark values derive by **three arms, not one formula** — measured deltas for mid-tone accents, role *inversion* for surfaces, target-contrast placement for foregrounds — with the 17-colour avatar palette fitting none of them. **#1313 (slice 2)** found the target-contrast arm has two failure modes worth inheriting: the dark card ground caps at 13.60:1 where the light ground affords 20.06:1, so the top of a ladder cannot be mirrored (rescued by an existing coincidence — both ceiling-bound tokens are `== ink` in light, so the answer was the `nightInk` the palette already had); and the arm goes **degenerate at mid-lightness**, where solving for the light ratio returns the light value, which is the method reporting the token needs no pair rather than a failure to work around. It also found that a *derived* value can move the target under a token: the unlit progress dot is `moss` at 38%, so its floor rises when `moss` resolves dark, and placing the lit dots by ground contrast (as for text) would have collapsed lit-vs-unlit to 1.34:1 — the dot ladder answers to lit-vs-unlit, at the accepted cost of the dark dot being louder than the meta text beside it. It also replaced the file's hand-computed pair-distance note with an assertion over every pair, verified by mutation, which incidentally established that `Color.Resolved` does **not** premultiply alpha into RGB. Verified via three deliberately-separated channels: `UIColor.resolvedColor(with:)` (mechanism — deterministic, skips `Color.Resolved`'s documented linear-light lossiness), `Color.resolve(in:)` (SwiftUI plumbing, i.e. that the *aliases* are dynamic), and one rendered-app check with the lock temporarily lifted (Home only, iOS 26.5 **simulator** — trait routing reaches rendering; explicitly NOT dark QA). A companion assertion that the unpaired aliases do NOT change (5 at landing, 1 after slice 4) is documentation-grade only: those tokens have no trait dependency, so invariance holds by *type* not by wiring and no plausible edit reddens it. That render check also found the unpaired damage is **concentrated, not uniform** — Home was already near-complete because its dominant tokens all sat in the original eight, so sequence the follow-up by screen; #1282 took the alert-family / interactive-state surfaces first on that basis. `HighlightCardPalette` (renamed from a file-private `Palette`) migrated to raw `PasturaPalette` values in the same change (it built **both** families from `Color.*` aliases, which would have collapsed light and dark into one) and is now pinned by `HighlightShareCardPaletteTests`, since ADR-009 rules out the snapshot test that would otherwise be the only detector. Isolation, all three claims observed rather than predicted: the type-level `nonisolated` on the pair type is a **runtime** guard, not a compile requirement (deleting it still builds clean) — it stops the provider closure being inferred `@MainActor` while UIKit may invoke it off-main, a third silent sibling of swift-isolation.md Patterns 6–7 covered by neither; `PasturaDynamicColor` is deliberately **not** `Equatable` (a synthesized `==` needs `PasturaColorValue`'s MainActor-isolated conformance from a nonisolated context — Pattern 5, under `SWIFT_APPROACHABLE_CONCURRENCY = YES` which enables `InferIsolatedConformances`); `PasturaDynamicPalette` is deliberately **not** `nonisolated` (its statics read MainActor `PasturaPalette`). Its `all` registry's count assertion guards that list's documented size, **not** completeness — an unregistered 68th pair still passes. Generalizable lesson: a compile-only probe that constructed the tokens **inline** passed while the real code reading them from `PasturaPalette`'s MainActor statics failed — a probe must replicate the dependency shape, not just the API shape. Asset-catalog color sets rejected because they blind two live gates (`check_design_tokens_css.py`'s hex→`tokens.css` mirror, and `DesignTokensTests`' sRGB-component assertions) (Status: Accepted; #1274)
