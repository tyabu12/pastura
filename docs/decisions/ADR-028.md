# ADR-028: Dark-Mode Token Pairing — Trait-Resolving `PasturaDynamicColor`

> **Status:** Accepted
> **Date:** 2026-07-27
> **Context:** Post-v1.0 design debt (#1274). `docs/design/design-system.md` §2.9
> defines nine `night*` dark-mode tokens but describes them as "未使用予約" — no
> mechanism resolved them, and no UI referenced them. Meanwhile the app is built
> from fixed light-mode tokens, so system dark mode flipped only the token-less
> default SwiftUI chrome and produced unreadable mixed-appearance screens. #1273 /
> #1275 stopped the bleeding with a defensive `UIUserInterfaceStyle = Light` lock;
> this ADR decides the permanent mechanism that lock is waiting on.
> **Verification basis:** every `file:line` below was read at `8b90421`, and the
> runtime claims were measured — see § "How the mechanism was verified".

## Decision

Introduce **`PasturaDynamicColor`** (`Pastura/Pastura/Views/DesignTokens+DynamicColor.swift`)
— a `light` / `dark` pair of `PasturaColorValue`s whose `color` is backed by a
`UIColor(dynamicProvider:)` closure that branches on
`traitCollection.userInterfaceStyle`. Point the paired `Color.*` aliases in
`DesignTokens+SwiftUI.swift` at it.

Because every consumer already reads a flat `Color.<token>` alias, redirecting
the alias is the whole adoption: **every existing consumer adapts with no edit**
— 520 `Color.<name>` references across 218 Swift files in `Views/` + `App/`,
measured at `15f8084` (this change's parent; the figure is a `grep` proxy that
also counts doc-comment mentions, and the change itself adds one file and one
such mention).

Three bounds are part of the decision, not incidental:

1. **Eight pairs, not nine** — see § "The `nightSurface` double-mapping".
2. **The light alias is the side that becomes dynamic**; `night*` aliases stay
   static, so an explicit dark request remains expressible.
3. **`UIUserInterfaceStyle = Light` stays** (`Pastura/Pastura/Info.plist:70`).
   The 59 remaining light tokens have no dark counterpart, so the lock is what
   prevents a half-dark surface. Removing it is gated — see § "Rollout".

### The eight pairs

| light token | dark token | §2.9 row |
|---|---|---|
| `screenBackground` | `nightBackground` | ✓ |
| `bubbleBackground` | `nightBubble` | ✓ |
| `whisperBubble` | `nightWhisperBubble` | ✓ |
| `ink` | `nightInk` | ✓ |
| `inkSecondary` | `nightInkSecondary` | ✓ |
| `muted` | `nightMuted` | ✓ |
| `rule` | `nightRule` | ✓ |
| `moss` | `nightMoss` | ✓ |

`PasturaDynamicPalette.all` registers all eight; `DesignTokensTests+DarkMode`
asserts the count, so wiring a ninth forces a reader through the next section.

### The `nightSurface` double-mapping

§2.9's table (`docs/design/design-system.md:149-157`) maps **nine** `night*`
tokens onto **eight** distinct day tokens: `nightSurface` (#232620) and
`nightBubble` (#2C2F28) both claim `bubbleBackground`. `nightSurface` has zero
consumers anywhere in `Pastura/Pastura` or `Pastura/PasturaTests` — only its own
declaration and the doc / CSS rows.

This is an unresolved *design* question, not a typo: dark wants a
background / surface / bubble three-step where light has only a two-step
(`screenBackground` / `bubbleBackground`). Resolving it means choosing among:

- **Add a light `surface` token** — pairs cleanly, but drags the full five-file
  token workflow (`.claude/rules/swiftui-traps.md` § "Adding a `Color` design
  token = 5 files") and adds to the palette, against §573's "トークンを**減らす
  方向**で拡張してください（追加より削除を優先）".
- **Delete `nightSurface`** — consistent with that same footer, and it costs
  nothing today given zero consumers. The leading candidate.
- **Context-dependent pairing** — reject; a token whose partner depends on the
  callsite is not a token.

**Deferred to the palette-completion follow-up**, where the visual judgment
already lives. §2.9's table row carries a matching note so the doc does not keep
asserting a pairing the code declines to implement.

### 59 tokens have no dark counterpart

`DesignTokens+SwiftUI.swift` declares 84 `Color` aliases. Excluding 9 `night*`,
4 §2.10 time-of-day, and 4 §2.11 chart leaves **67** light tokens; 8 are now
paired, so **59** remain light-only — the alert family (12), interactive states
(6), avatar palette (17), meta L1–L4 (12), link (3), header slots (3), the
remaining moss steps, `promoBackground` / `promoBorder`, and `page`.

Designing those 59 dark values is **not** mechanical translation — it is brand
work requiring visual sign-off, which is why it is a separate deliverable rather
than a larger version of this PR.

## How the mechanism was verified

`adr-writing.md` §1 requires SDK behaviour to be confirmed rather than recalled.
Three channels, deliberately separated because they observe different things:

| Channel | What it establishes | Result |
|---|---|---|
| `UIColor.resolvedColor(with: UITraitCollection(userInterfaceStyle:))` | The mechanism itself. Deterministic, and does not pass through `Color.Resolved`, which `DesignTokens.swift:23-25` documents as linear-light and lossy. | Pass — each side resolves to its own token; `.unspecified` falls to light. |
| `Color.resolve(in: EnvironmentValues)` with `colorScheme` pinned | SwiftUI plumbing, i.e. that the *aliases* are dynamic and not merely that the pair type works. | Pass — all eight aliases resolve to their dark token under `.dark` and their light token under `.light`. |
| Rendered app, lock temporarily lifted, simulator appearance dark | The render path, which neither query above exercises. | Pass — Home renders `nightBackground` / `nightInk` / `nightInkSecondary` / `nightMuted` / `nightRule` / `nightMoss`. |

A **negative control** accompanies the second channel: five unpaired aliases
(`page`, `promoBackground`, `warning`, `danger`, `mossSoft`) must resolve
*identically* under both schemes. Without it, a bug that dark-shifted every
alias would satisfy the positive assertions.

**Scope of the render check, stated precisely:** one screen (Home), on the
**iOS 26.5 simulator**, not a physical device. It confirms trait routing reaches
rendering; it is **not** dark-mode QA. Per
`.claude/rules/swiftui-traps.md` § "iOS 26 Liquid Glass toolbar capsule" and
§ "`ImageRenderer` does not inherit the ambient environment", simulator
appearance is not load-bearing for visual sign-off. Real-device QA is a gate in
§ "Rollout", not a claim made here.

That check also produced a finding worth recording: Home is *already* close to
complete in dark, because its dominant tokens all fall inside the paired eight.
The unpaired damage is therefore **concentrated, not uniform** — expect it on
surfaces driven by the alert family, interactive states, promo, and meta L-family
(Settings, download progress, editor), and on the avatar palette, whose
light-cream bodies stay light. Sequencing the follow-up by screen rather than by
token count is the cheaper path.

## Consequences

- **Adoption cost for the eight is zero at the callsite**, and stays zero for
  each of the 59 as its dark value lands: add the pair, repoint the alias.
- **The `tokens.css` mirror gate keeps working.**
  `scripts/check_design_tokens_css.py:37` globs
  `Pastura/Pastura/Views/DesignTokens*.swift` and requires every
  `PasturaColorValue(hex:)` literal to appear in `docs/design/ds/tokens.css`.
  `DesignTokens+DynamicColor.swift` introduces **no** hex literal — it composes
  existing `PasturaPalette` tokens — so the new file is inert to that gate.
- **Component-level token tests keep working.** `DesignTokensTests` asserts
  `PasturaPalette.<token>.red/green/blue`; the pair type wraps those values
  without changing them.
- **`Color.*` now means "the device's appearance" for eight tokens.** Any
  consumer needing a *fixed* appearance must read `PasturaPalette.<token>.color`
  directly. `HighlightShareCard` is the reference consumer and was migrated in
  the same change — it built **both** its light and dark families from `Color.*`
  aliases, so leaving it would have collapsed the two into one and made an
  explicit light or dark export unexpressible. Nothing would have caught that:
  the token tests assert `PasturaPalette`, ADR-009 rules out snapshot tests, and
  the light lock suppresses the symptom until whoever removes the lock hits it.
- **Two isolation constraints are load-bearing** under
  `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`:
  - The provider closure captures only copied `Sendable` `PasturaColorValue`s,
    never `self`. UIKit may invoke it off the main actor — the shape of
    `.claude/rules/swift-isolation.md` Patterns 6–7, which emit **no**
    diagnostic.
  - `PasturaDynamicColor` is **not** `Equatable`. A synthesized `==` needs
    `PasturaColorValue`'s `Equatable` conformance from a `nonisolated` context,
    and that conformance is MainActor-isolated (the target builds with
    `InferIsolatedConformances`) — Pattern 5, which fails the build with
    `main actor-isolated conformance of 'PasturaColorValue' to 'Equatable'
    cannot be used in nonisolated context`.
  - Conversely `PasturaDynamicPalette` is deliberately **not** `nonisolated`:
    its static initializers read MainActor-isolated `PasturaPalette` statics.
    Marking it `nonisolated` fails with `Main actor-isolated default value in a
    nonisolated context`. The isolation that matters is on the closure.
- **A compile-only probe was insufficient** and this is the generalizable
  lesson: a `swiftc -typecheck` probe that constructed `PasturaColorValue`s
  *inline* passed, while the real code — which reads them from
  `PasturaPalette`'s MainActor statics — failed. A probe must replicate the
  dependency shape, not just the API shape, or it measures nothing.

## Rollout

Landing here: the mechanism, the eight pairs, the `HighlightShareCard`
migration, and the doc/comment sweep. Appearance does not change, because the
lock stays.

Removing `UIUserInterfaceStyle` is gated on **all** of:

1. The 59 unpaired tokens have designed dark values with visual sign-off — or an
   explicit, recorded decision that a given token stays fixed in both
   appearances.
2. The `nightSurface` question above is resolved.
3. Sites relying on raw SwiftUI default colors are tokenized — 30 occurrences
   across 13 files in `Views/` + `App/` at `8b90421`.
4. Real-device dark QA across Home / ScenarioDetail / Demo / Simulation /
   Results / Settings.
5. The dark **share-card** path is re-verified on device. It is unreachable
   while the lock holds, and `ImageRenderer` does not inherit the ambient
   environment, so no automated test observes it (#1274 comment).

Until (1)–(5), a partial merge is safe precisely because the lock makes the
paired tokens unobservable.

## Alternatives considered

- **Asset-catalog color sets (`Contents.json` with Any/Dark appearances)** —
  rejected. This is the platform-idiomatic route and needs no custom type, but
  it moves the hex values out of Swift and **blinds two existing gates**:
  `check_design_tokens_css.py`'s `HEX_RE` extracts
  `PasturaColorValue(hex: 0x…)` from `DesignTokens*.swift`, so the `tokens.css`
  mirror check would silently have nothing to inspect; and `DesignTokensTests`
  asserts sRGB components directly, which a catalog color cannot offer at that
  granularity (`DesignTokens.swift:23-25` explains why the components, not
  `Color.Resolved`, are the assertion surface). Losing a CI gate to gain
  idiomaticity is the wrong trade here.
- **`@Environment(\.colorScheme)`-driven palette struct threaded through views**
  — rejected. It requires touching all 520 callsites (or every view's
  initializer), and it is *worse* than the status quo for `ImageRenderer`
  exports, which do not inherit the ambient environment at all. The one place
  this shape is correct is exactly where Pastura already uses it:
  `HighlightShareCard`, with an explicit `colorScheme` parameter.
- **`Color(light:dark:)` free function at each callsite** — rejected. Pushes the
  decision to 520 sites and loses the single canonical pairing table.
- **Complete all 59 dark values in this change** — rejected as a scope, not as a
  goal. The values need visual judgment per token, and the diff would cross the
  review-scope budget in `.claude/rules/subagent-usage.md` §2 several times over.

## Revisit trigger

- **The lock comes off** — revisit whether `Color.*` being appearance-dependent
  should be enforced mechanically rather than by the doc comment in
  `DesignTokens+SwiftUI.swift` (a lint rule banning `Color.<paired>` inside
  `ImageRenderer` content, say). While the lock holds, that comment is
  sufficient because the failure is unobservable.
- **A second fixed-appearance consumer appears** alongside `HighlightShareCard`
  — at that point the "read `PasturaPalette` directly" convention deserves a
  named helper rather than a doc comment.
- **`PasturaColorValue` gains a second nonisolated caller** — then marking it
  `nonisolated` becomes correct per Pattern 5's fix order, and
  `PasturaDynamicColor` can regain `Equatable`.
