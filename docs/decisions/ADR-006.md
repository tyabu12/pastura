# ADR-006: Cloud API Implementation Details — BYOK Scenario Generation Behind a Provider-Neutral Client

> **Status:** Accepted
> **Date:** 2026-09-08
> **Context:** ADR-005 §7 committed the *principles* for any feature that
> sends user-authored text to an external LLM and reserved this number for
> the *implementation specifics* (§2.3, §7.5): key custody, first provider,
> consent wording, retry / rate-limit / offline policy, caching and telemetry.
> `docs/ROADMAP.md` § Phase 3 row 2 gates the in-app scenario generation
> feature on this ADR merging; the KMP track that preceded it closed
> 2026-09-07 (ADR-023 S5-5, #1685). Issue #1692.
> **Verification basis:** every cited file was read at `9877592f` (this
> branch's fork point from main). Provider-API claims come from Anthropic's
> structured-outputs documentation as read on 2026-09-08 and are marked as
> such; they are re-verified at implementation time, not trusted from here.

## Context

Pastura's whole posture is on-device: simulations run on a local GGUF model,
there is no account, and the App Store listing, the landing page, the README
and `docs/store/review-notes.md` all say so in absolute terms ("fully
offline", "nothing leaves your device", "cloud calls — 0"). v1.0 was rejected
once under Guidelines 5.1.1(i)/5.1.2(i) on the reviewer's false premise that
Pastura sends user data to a third-party AI, and approved on the strength of
that absolute claim (`docs/store/README.md:79-84`). Any cloud feature therefore
touches the brand and the review posture before it touches code.

The feature itself is narrow: the user describes a scenario in natural
language, an external LLM returns a scenario, and the app opens it in the
editor as a draft. Today that flow exists **manually** — the YAML-mode editor
toolbar copies a generation prompt to the clipboard
(`Views/Editor/ScenarioEditorView.swift:163`, text assembled by
`App/ScenarioGenerationPrompt.swift`) for the user to paste into any LLM and
bring the YAML back. ADR-006 automates that round trip; it does not change
what a simulation is or where it runs.

Three constraints shaped the decisions below:

- **ADR-005 §7.3's two layers are binding.** Provider-neutral controls,
  provider-explicit disclosures, per-feature consent, revocation from
  Settings. This ADR may refine, not contradict.
- **No server exists.** Pastura has no identity, quota, or rate-limit
  backend; the marketplace that would justify one (`docs/ROADMAP.md:258`) is
  Phase 3 row 3, sequenced after this feature.
- **The Engine is not involved.** Scenario generation is authoring, not a
  simulation turn. The authoring path stays Swift-side under ADR-023 §4, so
  nothing here crosses the K/N boundary or touches `LLMService`.

## Decision

### 1. Key custody — bring your own key, device-bound

The user supplies their own provider API key. Pastura ships **no** key,
runs **no** proxy, and pays for **no** inference.

- **Storage.** Keychain generic-password item, accessibility
  `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, no iCloud Keychain sync. The
  app has no Keychain code today (no `SecItem` / `Keychain` hit under
  `Pastura/Pastura/`), so a small `App/Cloud/APIKeyStore` wrapper is new. The
  key never enters `UserDefaults`, OSLog (CLAUDE.md § Logger privacy applies —
  never interpolate it, at any level), exported YAML, run records, or the share
  sheet.
- **Foreground only.** `…ThisDeviceOnly` items are unreadable while the device
  is locked. Generation therefore runs only in the foreground; it never rides
  the ADR-003 background task, which exists for simulation continuation. A
  request in flight when the app backgrounds is allowed to complete or fail on
  its own timeout; nothing is re-issued from the background. The key is
  read from the Keychain **once per generation** and held in memory until
  that generation ends, so a retry never re-reads it — a device that locked
  mid-request must not turn a transport retry into a Keychain error.
- **Lifecycle.** Entry and removal live in Settings under a provider-neutral
  section. Saving runs one **probe request**: a Messages call to the
  currently configured model id with the smallest output ceiling the API
  accepts and a one-word prompt. HTTP `200` is the only success. The
  failure classes are mapped to distinct messages — authentication (`401`,
  invalid key) → "check the key"; an unknown-model error → "check the model
  id"; a billing / credit error → "check your provider account"; no network
  → the key is saved as **unverified**, and the probe runs the next time
  Settings opens; a generation never triggers it, so the four-request
  ceiling (Decision 4) holds. An unverified key can still be used to
  generate — the first real request validates it, and a failure maps to
  the same three classes — so the entry-point state table (Decision 3)
  needs no fourth row. The probe is a billed request on the user's account and the
  entry screen says so. The
  same three-way mapping serves a `401`, unknown-model, or credit response
  at any later time: a localized error with a one-tap route to the same
  Settings row. None of them touch the consent flag (Decision 3) — consent
  is about data flow, the key is about billing. Device migration or restore leaves the
  slot empty by design (`ThisDeviceOnly`); the empty state is the same
  first-run UI, not an error.
- **Cost visibility.** Every generation shows the provider-reported token
  usage (input / output) for that request. Pastura keeps **no price table**:
  prices drift, and a pinned table is exactly the mutable inventory
  `.claude/rules/adr-writing.md` §4 warns against. The user's provider console
  is the bill.

A maintainer-key / proxy model is deferred, not rejected — see Options and
Revisit triggers.

### 2. Client contract — provider-neutral, App layer, not `LLMService`

```swift
// App/Cloud/ — App may depend on everything; nothing below App learns of the cloud.
nonisolated protocol CloudGenerationClient: Sendable {
  var provider: CloudProvider { get }              // disclosure-layer identity (Decision 3)
  func generate(_ request: CloudGenerationRequest) async throws -> CloudGenerationResponse
}
// CloudGenerationRequest: system + user text, a JSON Schema the output must satisfy,
//   and an output-token ceiling. Cancellation is the caller's Task cancellation.
// CloudGenerationResponse: the JSON text, provider-reported usage, and the
//   provider's stop reason mapped to a closed enum (completed | truncated | refused).
```

- **Placement.** `App/Cloud/`. `Models/`, `LLM/`, `Engine/`, `Data/` gain no
  cloud dependency and no new types; the client is consumed by a ViewModel
  that hands the result to the editor route. Not KMP-shared.
- **Deliberately not a conformance to `LLMService`.** That protocol
  (`LLM/LLMService.swift:8`) is engine-turn-shaped: `loadModel` /
  `unloadModel` / `isModelLoaded`, an `OutputSchema` translated to GBNF,
  `antiRepetitionSeeds`, and `LLMError.suspended` from `SuspendController`.
  None of it applies to a single authoring request, and forcing the cloud
  client through it would put a network backend on the seam ADR-023 §5 ported
  to Kotlin. The OpenAI-compatible `OllamaService` is not a base either: it is
  compiled out of Release (`LLM/OllamaService.swift:5`, ADR-005 §8.5) and
  Anthropic's structured outputs live on its native Messages API.
- **Provider enum, one conformer at launch.** `CloudProvider` is a closed
  enum whose only case is `anthropic`. Adding a case is the mechanism by which
  a second provider (OpenAI, Gemini) lands later: a new conformer, a new
  Settings key slot, and — the ADR-005 §7.3 hard gate — every disclosure
  surface in Decision 6 updated in the same release. The UI never names the
  provider except on those surfaces, so adding one re-lays-out nothing.
- **Transport.** Raw HTTPS over `URLSession`, the pattern already used by
  `OllamaService` and `App/Community/Gallery/URLSessionGalleryService.swift`.
  Anthropic publishes no first-party Swift SDK (its SDK set on 2026-09-08 is
  Python, TypeScript, Java, Go, Ruby, C#, PHP), and a third-party package would
  need the CLAUDE.md § Confirmation Policy SPM approval for one endpoint's
  worth of JSON. **No SPM dependency is added.**
- **The Anthropic conformer** posts to `/v1/messages` with the key in the
  `x-api-key` header, a pinned `anthropic-version`, and
  `output_config.format = { type: "json_schema", schema: … }` for
  schema-constrained output (Anthropic docs, read 2026-09-08; no beta header
  is required any more). Streaming is not used: the response is one JSON
  object, and the output ceiling is set well under the sizes that need it.
- **Model id is a constant with a default, not an ADR decision.** The default
  lives in one site next to the conformer, changeable without amendment —
  `.claude/rules/adr-writing.md` §2 (mechanism over pinned model). The choice
  is also a billing choice under BYOK: a costlier default lands on the user's
  invoice, which is a reason to keep it a constant the implementation issue
  weighs, not a value this document fixes. The user may override it in
  Settings (free text, validated by the probe).

### 3. Consent — ADR-005 §7.3 made concrete

- **One flag per feature, bound to the recipient.**
  `cloud.scenarioGeneration.consent` in `UserDefaults` (not secret; it is a
  preference) stores the `CloudProvider` the user consented to, not a bare
  `true`. It ships **unset**. Enabling the feature anywhere presents the
  consent screen; the value is written only on explicit accept. If the
  provider a request would go to differs from the stored one — a second
  provider added later (Revisit trigger) — the consent is void and the screen
  is shown again: ADR-005 §7.3's disclosure layer is consent *to a named
  recipient*, and a flag that outlives the recipient would break it.
- **Consent screen — the wording is fixed here** (ADR-005 §7.5 item 1);
  implementation localizes it verbatim through `String(localized:)` and the
  catalog, and any rewording is an amendment because it is a legal
  disclosure, not UI copy:

  > **en — title:** Send your description to Anthropic?
  > **body:** To generate a scenario, Pastura sends the description you type
  > below to Anthropic (Claude) using an API key you provide in Settings.
  > Nothing else is sent: not your simulations, saved scenarios, or device
  > information. Anthropic handles the request under its privacy policy
  > [link]. Simulations always run on this device. You can turn this off at
  > any time in Settings › AI scenario generation; turning it off stops
  > future requests, and what Anthropic already received stays under its
  > policy.
  > **buttons:** Allow and continue · Not now
  >
  > **ja — title:** 入力した説明を Anthropic に送信しますか？
  > **body:** シナリオを生成するために、Pastura は下に入力した説明文を、設定で登録する
  > API キーを使って Anthropic（Claude）に送信します。送信されるのはこの説明文だけで、
  > シミュレーション、保存済みシナリオ、端末情報は送信されません。Anthropic は同社の
  > プライバシーポリシー［リンク］に基づいてリクエストを処理します。シミュレーションは常に
  > この端末上で実行されます。設定 › AI シナリオ生成 からいつでもオフにできます。オフに
  > すると以降の送信が止まります。すでに Anthropic が受け取った内容は同社のポリシーに
  > 従って扱われます。
  > **buttons:** 許可して続ける · 今はしない

  "Not now" dismisses without writing the flag; the entry point stays
  available and re-presents the screen next time.
- **Revocation** is a toggle in the same Settings section as the key.
  Turning it off blocks new requests immediately; an in-flight request may
  complete (ADR-005 §7.3 principle 2). Removing the key does not clear consent
  and vice versa; the two states are shown side by side so neither is
  mistaken for the other.
- **No consent bundling.** There is one cloud feature; an "enable all cloud
  features" affordance would be a lie about the future and is not built.
  ADR-005 §7.5 permits one later only if per-feature revocation survives.
- **UX-layer copy stays neutral**: "Generate with AI" on the entry point,
  "AI scenario generation" in Settings, no provider name outside the
  disclosure surfaces (Decision 6).
- **Entry-point state.** Three independent preconditions resolve in this
  order; the first unmet one decides what the button does:

  | Unmet precondition | Button | Tap leads to |
  |---|---|---|
  | Offline (Decision 4) | Disabled, "needs a network connection" | — |
  | No consent stored for the current provider | Enabled | Consent screen, then the generation sheet |
  | No key stored | Enabled | Settings key row, then back to the generation sheet |

  Consent comes before the key on purpose: the user learns who receives
  their text before being asked to pay for it.

### 4. Request policy — one shot, bounded retries, offline is a closed door

- **One request per generation.** No agent loop, no tool use, no
  multi-turn. A "regenerate" is a fresh request with the same prompt.
- **Input bound.** The user's description is capped at a character limit
  enforced in the UI; the schema and system prompt are fixed-size. Together
  they bound the input tokens per request — the only cost-runaway vector left
  once there is no maintainer key.
- **Input content validation before sending.** ADR-005 §4's
  `ScenarioContentValidator` runs on the user's description *before* the
  request leaves the device. Its entry points today take a `Scenario`,
  a persona, or a phase (`App/ScenarioContentValidator.swift:38`, `:101`,
  `:124`) over a private text check; the generation entry point adds a
  free-text overload over that same check rather than a second blocklist —
  specifically `shouldFlag(_:)` (`:144`), which keeps the existing convention
  that empty text passes and non-empty text is matched by
  `containsBlockedPattern(_:)` (`:245`). A hit blocks the request with the
  same UX as blocked authoring. This is the
  direction §4 was designed for — text the user typed, on its way out.
- **Retries — and the billing ceiling they define.** At most two automatic
  retries, only on `429`, `5xx`, and transport failure, honoring
  `retry-after` when present, with jittered back-off otherwise. Never on
  other `4xx` (bad key, bad request, credit), never after the user cancels.
  The one **repair round** at the validation stage (Decision 5) is a further
  request with **no retries of its own**. So one tap bills at most **four**
  provider requests (1 + 2 retries + 1 repair), and a `429` / `5xx` retry
  bills only if the provider generated output before failing. The
  generation sheet states the ceiling ("up to 4 requests on your key") next
  to the generate control. The retry counts are fixed *here*, unlike the timeout and the character cap below,
  because they are the user's cost ceiling — part of the mechanism contract,
  not a tuning knob.
- **Refusal.** A provider refusal (`stop_reason: "refusal"` on Anthropic)
  surfaces as "the provider declined this request"; not retried, not
  reworded on the user's behalf.
- **Truncation.** A response cut at the output ceiling is a failure (the
  JSON is unusable), reported as such, not silently repaired.
- **Offline.** The entry point is disabled with a reason while
  `App/NetworkPathMonitor.swift` reports no path; a request that loses the
  network mid-flight fails through the transport-failure path. On-device
  simulation is unaffected by any of this — it never consults the monitor.
- **Timeouts and the character cap are implementation constants**, held in
  one place beside the conformer; the ADR fixes the shape, not the numbers.
- **Cancellation** is user-visible and immediate: the caller's `Task` is
  cancelled, which cancels the `URLSessionTask`, and no result is delivered.
  Cancellation stops the *delivery*, not the bill — tokens the provider has
  already generated are charged to the user's account regardless. The
  generation sheet says so next to the cancel control.
- **Error type.** `CloudGenerationError` is an App-layer enum mapped to UI
  copy the way `SimulationError` / `LLMError` / `DataError` are mapped there
  (CLAUDE.md § Error types are per layer lists those three because they are
  the layers below App; this is the App layer's own, not a fourth
  cross-layer type). `errorDescription` literals go through
  `String(localized:)`; tests match with `.contains`.

### 5. Generation schema and validation pipeline — a safe subset, then the normal doors

**The schema is not derived from `Scenario`.** Anthropic's structured
outputs reject, verbatim from the documentation read 2026-09-08: "Recursive
schemas" and "`additionalProperties` set to anything other than `false`".
`Scenario` (`Models/Scenario.swift:11`) carries `extraData: [String:
AnyCodableValue]` (`:106`), an arbitrary-key dictionary over a four-way union,
and `Phase` is recursive through `thenPhases` / `elsePhases`
(`Models/Phase.swift:59`, `:63`). Neither is expressible. So:

1. **`ScenarioDraft` — a hand-authored, closed DTO** in `App/Cloud/`, and the
   JSON Schema is written for it. It is a *safe subset* of `Scenario`:
   `extraData` is not generated; `id` is not generated (the app assigns a
   fresh one at materialization, as the editor's template path does) and
   `language` / `simulationLanguage` are set from the app locale, not by the
   model; `conditional` branches follow the existing depth-1 rule (a branch
   holds any phase type except `conditional` — `Models/Phase.swift:55-59`,
   enforced by `ScenarioValidator` / `ScenarioLoader`). The rule alone does
   not make the *schema* non-recursive — a single draft phase type whose
   branch array holds itself is a self-reference the provider rejects — so
   the draft represents phases as **two types**: `DraftPhase`, which carries
   the branch arrays, and `DraftBranchPhase`, which is `DraftPhase` minus
   those two fields; personas are `DraftPersona`, the persona sub-object. Because the Models rule already forbids depth 2, the
   split loses no expressiveness. Every enum
   (`PhaseType`, `ScoreCalcLogic`, `AssignTarget`, `PairingStrategy`) is
   emitted as a string enum from `allCases` — `PairingStrategy`
   (`Models/Pairing.swift:31`) gains `CaseIterable` for it; the other three
   already conform — so a new case reaches the schema through the same
   declare-once contract that already feeds `ScenarioGenerationPrompt`
   (ADR-022). `additionalProperties: false` on every object.
2. **Drift gate.** A test enumerates the stored properties of `Scenario`,
   `Phase`, and `Persona` with `Mirror` over fully-populated fixtures and
   asserts that each `<Type>.<property>` either appears in `ScenarioDraft`
   or is a key of an exclusion dictionary in the test file, `[String:
   String]` keyed `"Scenario.extraData"`-style with the reason as the value.
   "Appears in" is checked against a fixed Model-to-draft map —
   `Scenario → ScenarioDraft`, `Phase → DraftPhase`, `Persona →
   DraftPersona` — with `DraftBranchPhase` treated as a subset of
   `DraftPhase`. The dictionary starts with the app-assigned fields above
   (`Scenario.id`, `Scenario.language`, `Scenario.simulationLanguage`),
   `Scenario.extraData`, and the two other open-key dictionaries on `Phase`
   that fail the same `additionalProperties: false` constraint —
   `Phase.outputSchema` (`Models/Phase.swift:18`) and `Phase.actionDeltas`
   (`:97`). If generation ever needs either, it is re-expressed as an array
   of key/value pairs, which is a draft change, not a Model change. Adding a
   Model field without deciding its generation fate fails the suite. A second test round-trips a
   full-coverage draft: `ScenarioDraft → Scenario →
   ScenarioSerializer.serialize (Engine/ScenarioSerializer.swift:21) →
   ScenarioLoader.load(yaml:)` and requires `==` on the two materialized
   `Scenario` values. A difference there is a serializer or loader bug to
   fix, never a reason to narrow the draft.
3. **Decode.** The provider's JSON is decoded into `ScenarioDraft`. (Step
   2's rule is about test fixtures; a *runtime* draft the loader rejects is
   a defective provider output, handled here.) A decode failure — or a
   draft that the loader round-trip rejects — triggers **one repair
   round**: the same request plus the validation error as feedback.
   A second failure is reported. This mirrors ADR-021's bounded-retry
   posture for LLM turns without borrowing its machinery.
4. **Content validation.** `ScenarioContentValidator.validate(_:)` on the
   materialized `Scenario`, same as manual authoring; findings block the
   hand-off with the authoring UX.
5. **Lint.** `ScenarioSemanticLinter.lint` (`Engine/ScenarioSemanticLinter.swift:79`,
   ADR-024) findings are shown in the editor as they are for any loaded
   scenario — informational, never blocking.
6. **Hand-off.** `ScenarioSerializer.serialize` → YAML →
   `Router.editor(editingId: nil, templateYAML:)` (`App/Router.swift:27`).
   The result is a **draft**: nothing is persisted until the user saves from
   the editor, and ADR-018's funnel invariant is untouched because the
   editor is entered through its existing template path.

**Engine schema by construction.** The draft is materialized through the
current `Scenario` initializers and serialized by the current serializer, so
generated YAML targets `EngineSchemaVersion.current`
(`Engine/EngineSchemaVersion.swift:63`, `6` at fork) without a version field
of its own. ADR-020's `min_engine_version` governs *shared* scenarios; a local
draft never carries it.

**The prompt is shared with the manual flow.** `ScenarioGenerationPrompt`
remains the copy-to-clipboard path for users without a key or a network, and
its generated phase-type / logic summaries become the cloud system prompt's
reference block, so the two flows describe the format from one source. The
manual flow is kept, not deprecated (Options).

### 7. Caching and telemetry — none, and the prompt is not kept

- No telemetry, analytics, or crash reporting is added; nothing about a
  request is sent anywhere but the provider.
- No request or response is persisted. The produced draft lives in the
  editor's buffer; the user's description is held in memory for the session
  (so "regenerate" works) and discarded with it.
- No provider-side prompt caching at launch — single-shot requests do not
  earn it. A cached system prompt is an implementation optimization the
  conformer may adopt without amendment.
- Failure diagnostics log the error *class* at `.debug` only; never the
  description, the key, or the response body (CLAUDE.md § Logger privacy).

### 8. Rollout — three slices, disclosure first

1. **(a) Key + consent.** `APIKeyStore`, the Settings section, the consent
   screen, the probe. Mergeable and invisible: nothing calls the cloud until
   (b).
2. **(b) Client + pipeline.** `CloudGenerationClient`, the Anthropic
   conformer, `ScenarioDraft` + schema + drift gate, the validation pipeline,
   the editor hand-off, the entry point. Reviewer: Opus (LLM-adjacent,
   `PrivacyInfo.xcprivacy`-adjacent — the sensitive base in `/orchestrate`).
3. **(c) Disclosure release gate.** Every row of Decision 6. This slice
   merges **before the release that carries (b)**; a release branch that has
   (b) without (c) is a blocked release, not a rushed one. The App Store
   Connect halves (App Privacy Details, review notes) are done in the same
   submission.

No feature flag: (a) is inert without (b), and (b) is not released without
(c). A TestFlight cycle with real inference on a real key is the device QA
for (b); it exercises the Keychain path (foreground, locked-device denial)
that the simulator cannot.

### 9. Scope boundary — what keeps this feature inside this ADR

The feature stays inside this ADR only while **all of** the following hold;
a change that breaks one is a new decision (an amendment or a new ADR),
not a per-PR choice:

- Pastura runs **no server** in the path: the device talks to the provider
  directly.
- Pastura ships **no key**: every request is billed to the user's account.
- **No simulation turn** ever goes over the network: the cloud client is
  called from the authoring path only, never from `Engine/` or `LLM/`.
- **Nothing is persisted** from a request or response beyond the draft the
  user sees (Decision 7).

None of the four is enforced by machinery today. The app is one module —
synchronized folder groups, no per-layer targets — so the compiler does not
stop a reference from `Engine/` or `LLM/` into `App/Cloud/`, and no
existing check covers *arbitrary* cross-layer references: the closest is
`scripts/check_naturallanguage_axis.sh` (ADR-010 D8), which guards one
framework import under the same four directories and is the template for
the new gate. Slice (b) adds a pre-commit gate that fails on any
`App/Cloud/` type name appearing under `Engine/`, `LLM/`, `Models/`, or
`Data/` — following that script's line discipline (comment lines excluded)
and placed beside it in `ci.yml` — which mechanizes the third bullet; the
other three stay review-time obligations on any diff that touches this
feature.

## Options considered

| Option | Verdict |
|---|---|
| **BYOK, device-bound Keychain** (chosen) | Costs: a small audience (users with a provider account), a key-entry UX, and a billing question Pastura cannot answer for the user. Buys: no server, no cost exposure, no key to leak, no in-app purchase question, no server-side data flow (so `docs/ROADMAP.md:166`'s standard-EULA posture holds). |
| **Maintainer key embedded in the app** | Rejected. Extractable from the binary, unbounded cost, and the only mitigation is a server — at which point it is the next row. |
| **Maintainer key behind a Pastura proxy** | Deferred, not rejected. It needs identity, quota, and rate limiting — the marketplace backend's infrastructure (`docs/ROADMAP.md:265`) — plus a monetization decision and a server-side privacy posture. Revisit trigger below; the client contract in Decision 2 is written so the proxy is a second conformer, not a redesign. |
| **Apple Foundation Models on-device instead of a cloud call** | Not this feature. `LLM/FoundationModelsService.swift` exists as a spike backend (#1072) that is not production-wired; an on-device generator would be a different ADR with a different quality question, and it would not retire the need for this contract. |
| **Reuse `LLMService` for the cloud client** | Rejected (Decision 2): turn-shaped protocol, K/N-ported seam, lifecycle methods with no cloud meaning. |
| **Share the OpenAI-compatible `OllamaService` transport** | Rejected: compiled out of Release, and the native Messages API is where the schema constraint lives. |
| **Ship two providers at launch** | Rejected for launch: doubles the Decision 6 table and every future re-verification. The enum makes the second one an amendment-sized change. |
| **Return YAML text from the provider** | Rejected: no schema guarantee, so every syntax and shape error becomes a repair loop; the JSON→`ScenarioSerializer` path reuses the app's own formatter. |
| **Derive the JSON Schema from `Scenario` by reflection** | Rejected (Decision 5): the provider cannot accept the recursion or the open dictionary, and a reflected schema would silently drift on every Model change. The hand-authored DTO plus the drift test is the same coverage with a compiler-and-test-enforced boundary. |
| **Save the generated scenario directly, skipping the editor** | Rejected: the user must see the content-validation and lint findings before anything persists, and drafts are the editor's job. |
| **Retire the manual "Copy Gen Prompt" flow** | Rejected: it is the no-key, no-network path and it shares the format reference. Kept as is. |
| **Decline the Cloud API entirely to keep the absolute on-device claim** | Considered and declined by the operator (2026-09-08): the claim is re-scoped to simulation, which stays true and verifiable. |

## Consequences

- **The brand statement changes** from "nothing leaves the device" to
  "simulation is always on-device" across every surface in Decision 6's table. That
  is the largest cost of this ADR. The rewrite lands in slice (c), before
  any user can send a byte; the review conversation it changes recurs on
  every submission after it.
- **Every tap costs the user money, including failures.** Up to four billed
  requests per generation (Decision 4), one billed probe per key save, and a
  cancel that does not refund generated tokens. The UI states each of these
  where it happens; Pastura cannot see or cap the resulting bill.
- **This is the app's first stored secret.** `docs/security/release-checklist.md`
  §4.3 covers a leaked *repository* key; a leaked *user* key is the user's to
  revoke in the provider console, and the Settings row says so. Pastura adds
  no server-side revocation because it has no server.
- **Two external pins need a keeper.** The `anthropic-version` header and
  the structured-output constraints Decision 5 relies on are re-verified at
  implementation and thereafter only when a Revisit trigger fires; a
  provider-side change between triggers surfaces as a generation failure,
  not a build failure.
- **More `ja`-obligated strings.** The consent screen, the entry-point
  states, and the error classes in Decision 4 all land in
  `Localizable.xcstrings` with a `ja` translation; the consent body is fixed
  text (Decision 3), so its translation is reviewed as a disclosure, not as
  UI copy.
- **A new artifact class, `App/Cloud/`**, with three small types and one
  DTO. No layer below App changes; the dependency table in CLAUDE.md is
  untouched.
- **`ScenarioDraft` is a second description of the scenario shape.** The
  drift test makes that a maintained invariant rather than a slow leak: a
  Model field added without a generation decision fails CI. The price is one
  more file every `Scenario` change must consider.
- **Generated scenarios are a subset of what YAML can express** — no
  `extraData`, no per-phase `output_schema` or `action_deltas` (open-key
  maps the provider's schema cannot express); branching depth is the Models
  rule, not an extra cut. A user who wants more edits the YAML, which is
  the editor's normal mode.
- **Reviewer conversations change.** The 5.1.2(i) rebuttal is re-derived: the
  app now *does* send user text to a third-party AI, with explicit consent,
  named provider, and the user's own key. The Airplane-Mode verification
  still holds for simulation.
- **Support surface.** Key-entry mistakes, exhausted credits, and provider
  outages become Pastura-visible failures with provider-side causes. Decision
  4's error mapping keeps them distinguishable; there is no Pastura server to
  fix them from.
- **Revocation is instant but not retroactive**: what the provider already
  received is governed by its policy, which the consent screen links. This is
  the honest limit of a BYOK design and is stated on that screen.

## Revisit trigger

- **The marketplace backend lands** (identity + quota) → amend with the
  proxy conformer and the monetization decision; Decision 1's "no server"
  paragraph becomes the historical basis, not the rule.
- **A second provider is requested** → new `CloudProvider` case, new
  conformer, and every row of Decision 6 in the same release (ADR-005 §7.3
  hard gate). Amendment-sized.
- **The provider changes its structured-output constraints** (recursion or
  open dictionaries become expressible) → reconsider Decision 5's subset;
  the drift test's exclusion list is where the change lands.
- **A first-party Swift SDK ships** → replace the hand-rolled transport only
  if it removes code; it still goes through the SPM confirmation.
- **Apple changes the third-party-AI disclosure rules** (5.1.2(i) wording,
  Privacy Manifest categories) → re-verify Decision 6 row by row before the
  next submission; the release checklist row is the reminder.
- **A second cloud feature is proposed** (result auto-summary is the nearest
  ROADMAP row) → it gets its own consent flag under Decision 3, reuses
  Decision 2's client, and reopens the consent-bundling question ADR-005
  §7.5 left conditional.
- **Users without a key outnumber users with one by enough that the feature
  reads as broken** → that is the proxy trigger above, measured, not the
  feature's failure.
