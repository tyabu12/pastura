# ADR-014: Release Automation Toolchain — fastlane + ASC API Key (local-first, TestFlight scope)

> **Status:** Accepted
> **Date:** 2026-06-13
> **Context:** Pastura has never uploaded a build to App Store Connect (ASC).
> The Apple Developer Program account is registered, but install-base is zero
> and no `.ipa` has ever been ingested. ADR-004 §9.2 deferred **H5 (ASC archive
> upload)** as an executable-but-unexecuted launch-prep action. The
> "Phase 1 shipped via TestFlight" line in `CLAUDE.md` / `docs/ROADMAP.md`
> refers to the Go/No-Go *decision* (conditional Go, 2026-04-13), **not** an
> actual upload. This ADR records how the first — and every subsequent —
> TestFlight upload is performed, and which one-time human steps unblock it.

> **Scope note.** This ADR covers up to **TestFlight upload** only. App Store
> *review submission* (deliver / metadata / screenshots / store-page) is
> deferred to Phase 3. The implementation shipped in two follow-up PRs:
> PR-A (#563) added the mechanism (`scripts/release.sh`, `fastlane/`, the
> `*.p8` secret-handling layers); PR-B (#567) added the `/release` skill and
> flipped this ADR to Accepted. The first live upload is still gated on the
> one-time human bootstrap (§ bootstrap).

---

## Decision

1. **Adopt fastlane** (`upload_to_testflight`, a.k.a. `pilot`) with
   **App Store Connect API Key (`.p8`) authentication** as Pastura's
   release-automation toolchain.
2. **Local-first execution, CI-portable design.** The release runs on the
   maintainer's Mac now. The `Fastfile` is authored so the *same* lanes run
   unchanged from GitHub Actions later — the only CI-specific addition is
   secret injection and `fetch-depth: 0` (see § "Build number").
3. **Three-layer component split** (PR-A shipped layers 1–2, PR-B layer 3):
   - `scripts/release.sh` — deterministic steps (preflight, archive, export,
     Ollama-symbol re-check, fastlane invocation). Reusable from CI.
   - `fastlane/Fastfile` + `Appfile` — API Key auth, version/build wiring,
     `upload_to_testflight`.
   - `.claude/skills/release/SKILL.md` — the judgement + interactive layer:
     version decision, reviewed tester-facing "What to Test" notes (passed to
     `release.sh` via `--notes-file`; commit-log subjects are the fallback
     when absent), pre-flight checklist cross-check, and the
     **mandatory confirmation gate before the irreversible upload**.
4. **Versioning:** `MARKETING_VERSION` is a manual bump, `X.Y` by convention
   (`release.sh` also accepts `X.Y.Z` — see `.claude/skills/release/SKILL.md`
   § Step 1 for when the third component applies);
   `CURRENT_PROJECT_VERSION` (build number) is derived (see § "Build number").

## Why this shape

### Why fastlane over the alternatives

| Option | Verdict | Reason |
|--------|---------|--------|
| **fastlane** | **Adopted** | Same `Fastfile` runs local → CI without rewrite (the long-term win, since the roadmap moves release into CI). First-class ASC API Key support, which is the modern 2026 auth path over Apple-ID + app-specific-password. `upload_to_testflight` absorbs the `xcodebuild -exportArchive` upload-destination limitation below. |
| `xcrun altool` | Rejected | Zero new dependency, but deprecated-leaning, and carries a known multi-app `apple_id` selection bug on Xcode 26 ([fastlane#29698](https://github.com/fastlane/fastlane/issues/29698)). Not the long-term bet. |
| `asc` (community CLI) | Rejected | Lighter setup, but smaller community / less proven for a full upload pipeline. |

**The `xcodebuild -exportArchive` limitation that motivates a wrapper:**
Xcode 15+ added App Store Connect API Key flags to `-exportArchive`
(`-authenticationKeyPath` / `-authenticationKeyID` /
`-authenticationKeyIssuerID`), but the `upload` export-destination and
`manageAppVersionAndBuildNumber` only work with an Apple ID signed into Xcode,
**not** with an API Key. So a pure-`xcodebuild` API-Key upload is fragile;
fastlane `pilot` performs the upload via the API Key cleanly.

**Cost of fastlane:** it adds a **Ruby / `Gemfile` developer-toolchain
dependency**. This is a build-time tool, *not* a runtime SPM dependency — it
does not link into the app binary and does not touch the
`Models → LLM → Engine → Data` dependency rules. Per `CLAUDE.md` the new
dependency is called out here for the record; the `Gemfile` + `Gemfile.lock`
pin the version.

### Release flow (ordered)

`scripts/release.sh` executes these steps. **The annotated git tag is
created and pushed *after* a successful upload**, not before (see rationale):

1. **Preflight** — `git fetch origin`; assert local `HEAD` SHA equals
   `origin/main` SHA; assert **all** required CI checks are `success` on
   that exact SHA. The required-check list is **derived at run time from the
   branch ruleset**
   (`gh api repos/{owner}/{repo}/rules/branches/main` →
   `required_status_checks[].context`), never hardcoded: GitHub names a
   check-run after the job's `name:` field (not the job id), and the
   required set grows as CI jobs are added — a hardcoded list silently rots
   into a vacuous pass. For each derived context, assert exactly one
   successful check-run with that name exists on the SHA (query
   `gh api repos/{owner}/{repo}/commits/<sha>/check-runs`); reject if any
   context is missing, `in_progress`, `queued`, or `pending`, and refuse
   outright if the derived list is empty. (See § "Preflight discipline".)
2. **Version** — bump `MARKETING_VERSION` (manual, if changing);
   compute the build number (see § "Build number"); assert it strictly
   exceeds the latest build already uploaded to ASC for this version
   (via fastlane `latest_testflight_build_number(version:)`).
3. **Archive** — `xcodebuild archive` with `-configuration Release`,
   automatic signing (`DEVELOPMENT_TEAM = 52G26234A3`).
4. **Symbol re-check** — run the ADR-005 §8.5 canonical guard on the
   *archived* binary:
   `nm -a <archived>.app/Pastura | xcrun swift-demangle | grep -i ollama`
   must return zero matches. (Rationale below.)
5. **Export** — `xcodebuild -exportArchive` to an `.ipa` with export method
   **`app-store`** (a `development`/`release-testing` method produces a
   silently un-uploadable `.ipa`). `release.sh` owns archive + export via raw
   `xcodebuild` and generates the `exportOptions.plist` at cut time (not
   committed); fastlane is the **uploader only** (next step).
6. **Upload** — `fastlane upload_to_testflight(ipa:)` via the API Key.
7. **Tag** — on upload success, create the annotated tag
   (`v{MARKETING_VERSION}+{build}`) and push it.
8. **Notes** — the `/release` skill synthesises reviewed, tester-facing
   "What to Test" prose and passes it via `release.sh --notes-file`; absent
   that flag the changelog falls back to the commit-log subjects since the
   previous release tag (`build_notes`).

**Why tag last.** A tag pushed before the upload succeeds
becomes a dangling public marker if archive/export/upload then fails — and
because the build number is commit-derived (next section), a naive "just
re-run" does not change the build number, compounding the failure. Tagging
only after `upload_to_testflight` returns success keeps the tag a faithful
record of "this exact commit is on TestFlight". The `/release` skill documents
the idempotent recovery path (`git tag -d` + re-run) for the failure window.

### Build number — `git rev-list --count HEAD`, with guards

The build number is `git rev-list --count HEAD` (the exact value is read at
cut time): stateless, deterministic, and monotonic along Pastura's **linear,
squash-merged `main`** (verified: `git log --merges origin/main` is empty).
This satisfies ASC's strictly-increasing-`CFBundleVersion`-per-version
requirement *for the normal forward case*. Three edges are load-bearing and
recorded so they fail loudly, not silently:

- **Same-SHA re-cut → duplicate build number → ASC hard-reject.** If an upload
  fails *after* ASC has ingested the build, or any re-cut of the same commit
  is needed, the count is unchanged and ASC rejects the duplicate. **Mitigation
  (chosen):** the preflight (step 2 above) queries ASC for the latest uploaded
  build number for the current `MARKETING_VERSION` and asserts the computed
  number strictly exceeds it — turning a mid-upload silent reject into a clean
  preflight failure. The recovery is then an explicit choice: a no-op commit
  (advances the count) or a `MARKETING_VERSION` bump.
- **Shallow-clone undercount.** `actions/checkout` defaults to `fetch-depth: 1`,
  under which `rev-list --count HEAD` returns 1, not the full commit count.
  **`fetch-depth: 0` is
  a hard prerequisite of the CI-portability claim** (Decision 2) and must be
  set when the lanes move to CI.
- **Topology dependency.** `--count HEAD` is monotonic on a linear first-parent
  history. This currently holds *because* Pastura squash-merges PRs; a future
  switch to merge-commits would break monotonicity. Recorded as a standing
  dependency on the squash-merge discipline.

### Preflight discipline — trust CI green, but only for what CI covers

The preflight does **not** re-run Pastura's content/drift gates
(`build-blocklist.sh --check`, `check_demo_replay_drift.py`,
`check_localization_coverage.py`, `check-gallery-entry.sh --all`,
`check_engine_language_axis.sh`). CI enforces every one of them on every PR
into `main`, so a CI-green `main` SHA guarantees them; re-running is only
slower. **The release discipline is therefore: only ever cut a release from a
CI-green `main` SHA.**

That "trust CI" claim is **scoped to the content/drift gates only**. It does
**not** extend to the archive path: CI's
`release-build` job runs `xcodebuild build -configuration Release
CODE_SIGNING_ALLOWED=NO` (`.github/workflows/ci.yml`), which validates
compilation and the Ollama-symbol guard but **not** code signing,
`xcodebuild archive`, `-exportArchive`, the export-options plist, or
provisioning resolution. ADR-004 §9.2 (H5) independently confirms this:
the signed archive→ASC-ingest path is genuinely unexercised by CI. Two
consequences:

- The Ollama-symbol re-check (flow step 4) is retained **on the archived
  binary** precisely because the archive differs from CI's build product.
- Before the *first* real upload, a **dry-run archive + export (skip upload)**
  is recommended to decouple any signing/export failure from the irreversible
  upload.

## One-time bootstrap (human-only — not scriptable)

These unblock the first upload and are performed once by the operator. None
are repeated per release.

1. **Create the App record** in App Store Connect for bundle id
   **`app.pastura.Pastura`** (confirmed in `project.pbxproj`, which since the
   Debug-suffix change reads `app.pastura.Pastura$(BUNDLE_ID_SUFFIX)` — Release
   expands that to the unsuffixed form, and `scripts/release.sh` is pinned to
   `-configuration Release`, so the ASC record's bundle id is unaffected.
   `Info.plist` no longer carries a bundle-id value at all; matches ADR-004
   §9.2's named action). Register the SKU + primary language.
2. **Generate an ASC API Key (`.p8`)** (App Store Connect → Users and Access →
   Integrations → App Store Connect API). Record the Key ID and Issuer ID.
   Store the `.p8` **outside the repository tree** — fastlane's default search
   path `~/.appstoreconnect/private_keys/` is preferred so it is physically
   impossible to stage. (See § "Secrets" for defense-in-depth.)
3. **Distribution signing.** `CODE_SIGN_STYLE = Automatic` with
   `DEVELOPMENT_TEAM = 52G26234A3` is already set; the first archive still
   needs an Apple ID signed into Xcode to mint the distribution certificate /
   provisioning profile.
4. **Encryption export compliance — already satisfied, verify only.**
   `INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO` is already set for the
   app target's Debug + Release configs (`project.pbxproj`) with
   `GENERATE_INFOPLIST_FILE = YES`, so the key is merged into the built app's
   `Info.plist` at build time. This is recorded in ADR-005 §8.6 (issue #159).
   Pastura uses HTTPS only, so its encryption is export-exempt and `NO` is
   correct. **There is no source-`Info.plist` edit to make** — adding the key
   to the hand-written `Pastura/Pastura/Info.plist` would be redundant (the
   build setting already supplies it; the two plists are merged). The
   build-setting key **auto-answers the ASC
   export-compliance prompt**, so no manual per-upload answer is required;
   confirm this by inspecting the exported `.app`
   (`plutil -p .../Pastura.app/Info.plist | grep ITSApp`).
5. **TestFlight tier.** Initial scope is **internal testing** (up to 100
   internal testers), which skips Beta App Review. *External* testing requires
   Beta App Review plus the Privacy Policy / Support URL wiring and an age
   rating — those URLs are already deployed (`deploy-pages.yml`); the age
   rating (13+, fallback 16+) is set per ADR-005 §3. Choosing external is a
   later decision, not a first-upload blocker.

## Secrets — `.p8` defense-in-depth

A leaked ASC API Key is a high-severity credential exposure, so a single
`.gitignore` line is insufficient. PR-A (#563) added, in layers:

1. **Out-of-tree storage** — the `.p8` lives in
   `~/.appstoreconnect/private_keys/`, never inside the repo working tree.
2. **Global gitignore** — `*.p8` and `AuthKey_*.p8` (not only under
   `fastlane/`), defending against an accidental in-tree copy.
3. **Pre-commit guard** — a `scripts/*-precommit-gate.sh`-style check that
   hard-fails on any staged `*.p8` (defends against `git add -f` and
   non-ignored paths).
4. **Revocation runbook** — the `/release` skill documents key revocation
   (App Store Connect → Integrations → revoke) as the leak-response step.

## Consequences

- The first ASC upload (ADR-004 H5) becomes executable: bootstrap is a fixed
  human checklist, and every release thereafter is a single deterministic
  script + interactive skill.
- A new Ruby/`Gemfile` build-toolchain dependency enters the repo (no runtime
  / SPM impact).
- The release path is reproducible and CI-portable; moving to CI later needs
  only secret injection + `fetch-depth: 0`, not a rewrite.
- `docs/security/release-checklist.md` is the operator pre-submission audit;
  PR-B (#567) extended it with a § 4 cross-referencing this ADR's preflight
  and bootstrap steps.

## Amendment 2026-07-09 — Public GitHub Release promotion

`scripts/release.sh` pushes an annotated git tag `v<version>+<build>` per
TestFlight upload but creates **no** GitHub Release. When a version is
approved and released on the App Store, a **public GitHub Release** is
promoted onto that build's existing tag — titled `Pastura <version>`, marked
`--latest`, carrying the developer-facing changelog (merged PRs, deliberately
kept out of the tester-facing "What to Test" notes).

- **Why a separate step, not per-build:** most TestFlight builds never ship
  publicly, so a Release per build would be pre-release clutter. Promotion is
  keyed to the App Store publish event (which this repo does not observe), so
  it stays a **manual, operator-run** procedure — `scripts/release.sh` is
  unchanged.
- **Scope note:** this ADR's original **Scope note** blockquote covers
  TestFlight upload only; App Store publish sits outside it and stays manual.
  The procedure has been **exercised at v1.0 and v1.1**.
- **Where documented:** the recipe (draft-first, operator review pause before
  publish, `--exclude-drafts` changelog base, the release-note format, and the
  retract edge case) lives in the `/release` skill, **Step 7**
  (`.claude/skills/release/SKILL.md`).
