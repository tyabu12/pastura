# ADR-015: Execution-Log Retention Posture & SQLite iCloud-Backup Decision

> **Status:** Accepted
> **Date:** 2026-06-13
> **Context:** An operational-debt review flagged two deferred storage
> concerns ([#547](https://github.com/tyabu12/pastura/issues/547), DB risks
> #3 and #4): (1) execution logs grow unbounded — there is no expiry, cap,
> or `VACUUM` anywhere in the Data layer; (2) `pastura.sqlite`
> (`Application Support/Pastura/`) carries no `isExcludedFromBackup`, unlike
> model files. The originating issue sketched an automatic retention policy
> (keep last N / older than X days; periodic `VACUUM`) but marked it
> **explicitly tentative** — "finalize the design when this is picked up."
> This ADR is that finalization. It decides the **posture** for both
> concerns; the concrete UI / enforcement code is split to follow-up
> implementation issues (§4). It does not pin a literal cap number or ship
> any retention mechanism itself.

---

## 1. Decision

### D1. No silent automatic deletion of past runs

Pastura will **not** adopt a background policy that silently deletes old
runs (neither "keep last N" nor "older than X days"). Growth is bounded
through **user-driven** deletion plus a **non-silent** safety stop:

1. **Manual purge UI** is the primary bounding mechanism. Per-run delete
   already exists — `SimulationRepository.delete(_:)`
   (`SimulationRepository.swift:107`) removes a `SimulationRecord` and
   cascades to its `turns` and `code_phase_events` rows via the
   `ON DELETE CASCADE` foreign keys (`DatabaseManager.swift` migrations —
   the child cascades date from their creation migrations; v7 changed only
   the `simulations → scenarios` FK to `SET NULL`). A **clear-all**
   affordance is the missing piece (§4).
2. **A high safety cap** is a secondary backstop. When the run count (or
   total DB size) crosses a generous threshold, the app surfaces a
   **non-silent** prompt inviting the user to purge — it never deletes
   without consent. The *decision* (a cap exists; it is advisory, not
   auto-deleting) is firm; the *literal threshold* is a tunable picked by
   the implementation issue (§4), not pinned here.

**Why no auto-delete:** Pastura's product thesis is run-to-run comparison
across many experiments — past runs are the primary asset the user
accumulates, not disposable logs. Silently discarding them works directly
against that core loop. The issue's own sketch flagged this risk by
deferring the design.

### D2. Keep the SQLite database backed up — do **not** exclude it

`pastura.sqlite` holds the user's accumulated experiment history: it is
**user data**, and the correct iCloud / device-restore behavior is to back
it up. We will **not** set `isExcludedFromBackup = true` on the database
file. This reverses the issue's risk-#4 framing: exclusion would be the
*wrong* direction once growth is bounded (D1), which it now is by posture.

This is a deliberate asymmetry with model files. `ModelManager` excludes
**individual GGUF files** from backup
(`ModelManager.excludeFromBackup(_:)`, `ModelManager.swift:892`) because a
2.5–3.1 GB model is large, re-downloadable, and *not* user-authored — the
opposite of the database on every axis.

**No persistent WAL sidecars to exclude.** The database runs on a GRDB
`DatabaseQueue` (`DatabaseManager.swift:8`) whose configuration sets only
`foreignKeysEnabled = true` (`DatabaseManager.swift:54-59`) — it does
**not** enable WAL journal mode. Under the default rollback-journal mode
there is no persistent `-wal` / `-shm`; only a transient
`pastura.sqlite-journal` exists during an in-flight write. So the backup
question collapses to a single file: back up `pastura.sqlite` (yes). The
WAL-sidecar exclusion question is **conditional** on a future migration to
`DatabasePool` (which forces WAL) — recorded as a follow-up gate (§4), not
a present-tense action. `DatabaseManager` already isolates that swap behind
one factory method (`DatabaseManager.swift:10-12`).

### D3. Right-sized scope

The growth concern is **real but not acute** for the shipped app, so the
response is incremental (manual UI + advisory cap), not a background
collector. See §2 for the magnitude reasoning. Implementation is deferred
to the follow-up issues in §4.

## 2. Why this shape

### Growth magnitude — real, not acute (on-device path)

Per-run storage is dominated by two heavy columns:

- `turns.rawOutput` — the **full unfiltered LLM response** for each turn
  (`TurnRecord.swift:7,21`), plus `parsedOutputJSON` alongside it.
- `simulations.stateJSON` — the serialized `SimulationState`
  (`SimulationRecord.swift:25`), which carries the conversation log.

A moderate run (a handful of rounds × several agents × phases) lands on the
order of **~100–300 KB** (rough estimate from the heavy columns above —
not a measured figure). Reaching even 100 MB therefore takes hundreds to
~a thousand runs. Because on-device inference is slow (minutes per run —
the same property the tok/s display exists to surface), run creation is
**human-paced**: a heavy user accumulates that volume over months, not
days. An advisory cap plus manual purge comfortably covers this regime; a
silent background collector would be solving a problem the device's own
throughput already throttles.

**Scope caveat:** this "slow inference bounds growth" argument applies to
the **shipped iOS app** only. The headless macOS factory harness (ADR-013)
can generate runs in bulk, but it is a separate SwiftPM executable that
does **not** write to `pastura.sqlite` — so it does not move the device-app
estimate. If a future pipeline ever points bulk generation at the app's
store, this assumption must be revisited.

### Why an advisory cap rather than a hard auto-purge

A hard cap that auto-deletes is just "keep last N" under another name and
inherits the same D1 objection. An **advisory** cap keeps the user in
control while still preventing the pathological unbounded case — the user
is told growth is large and offered the existing delete tools, and decides.

## 3. Consequences & relations to existing ADRs

- **No code ships in this ADR.** The deliverable is the posture above plus
  the follow-up issues (§4). Per-run delete and the FK cascade are already
  in place and unchanged.
- **Builds on #552 (v7) safe-delete direction.** v7 relaxed the
  `simulations → scenarios` FK to `ON DELETE SET NULL` so deleting a
  scenario orphans (preserves) its runs rather than wiping them. D1's
  "don't silently destroy run history" posture is the same value applied to
  retention.
- **Future Data-layer placement.** When the advisory cap / clear-all lands,
  enforcement (count, bulk delete, optional `VACUUM` after a large purge)
  belongs in the **Data layer** (e.g. a `SimulationRepository` method);
  the *trigger* (launch check, settings action) belongs in **App**. This
  respects the dependency rules — retention logic must not leak into Views
  or Engine.
- **`VACUUM` is opt-in, post-purge only.** SQLite reclaims deleted-row
  space lazily. A `VACUUM` (or incremental vacuum) is worth running *after*
  a large manual clear-all, not on a schedule — it rewrites the whole file
  and would block. Scoped to the clear-all follow-up.

## Amendment 2026-06-23 — advisory metric is past-results content size (#770)

D1 (§1) and §4.2 frame the advisory metric as "total DB size". As shipped
in #770 the metric is the **past-results content size**
(`SimulationRepository.pastResultsByteCount()`): the summed UTF-8 byte
length of the `simulations` / `turns` / `code_phase_events` payload +
snapshot columns. It deliberately excludes the `scenarios` table (bundled
presets are re-seeded on every launch and survive a clear-all) and the
SQLite schema / index / free pages — so the Settings → Past Results storage
caption reaches **0** once every run is deleted, instead of resting on a
~96 KB whole-file floor. The number is strictly ≤ the old whole-DB measure,
so the 250 MB advisory fires *no earlier* than before: a metric-scope
refinement, not a threshold change.

## 4. Follow-up implementation issues (out of scope here)

These were filed as separate issues after this ADR landed — current status
(the decision text in §1–§3 is unchanged; this is a status annotation):

1. **Clear-all / bulk purge UI** — a Settings-level "delete all runs"
   affordance (with confirmation), reusing `SimulationRepository.delete`
   semantics, plus a post-purge `VACUUM`. ✅ **Shipped** — issue #545 / PR #572.
2. **Advisory growth cap** — a non-silent prompt when run count / DB size
   crosses a generous threshold. ✅ **Shipped** — issue #565 / PR #589: the
   implementation chose a **250 MB**, **size-only** advisory (run count is
   not a trigger) surfaced in Settings → Past Results (an always-on storage
   caption plus a non-deleting over-cap warning that routes to the clear-all
   affordance above). The
   literal threshold remains a tunable per D1, not pinned by this ADR.
3. **(Conditional) `DatabasePool` / WAL migration handling** — ⏳ pending,
   conditional (no present-tense action). Only if/when
   the writer migrates from `DatabaseQueue` to `DatabasePool` (which opens
   the DB in WAL mode). Two distinct concerns at that point, only one truly
   migration-gated:
   - **WAL-sidecar backup** *(migration-gated)* — WAL adds persistent
     `-wal` / `-shm` files; exclude them from backup while keeping
     `pastura.sqlite` backed up (D2). No action while on `DatabaseQueue`
     (rollback-journal → no sidecars).
   - **File-protection / suspension** *(baseline, not WAL-specific)* — a DB
     lock held while the device is locked in the background risks
     `SQLITE_IOERR` / `0xdead10cc`. This is a background-execution
     ([ADR-003](ADR-003.md)) interaction that already applies to today's
     `DatabaseQueue`, currently a **non-issue** (app-private store in
     Application Support — no shared container; default
     `CompleteUntilFirstUserAuthentication` protection). A WAL migration
     *sharpens* it, so re-validate GRDB's `observesSuspensionNotifications`
     posture at migration time — it is not a present-tense action.

   The seam is the `DatabaseManager` writer factory; that property's
   doc-comment carries this gate for the implementer who makes the swap.
   The standalone tracking issue was retired (closed via PR #596) once this
   gate lived here in the ADR plus the `DatabaseManager` doc-comment, rather
   than as a permanently-blocked open issue.

## 5. Alternatives considered

- **Automatic "keep last N runs" / "older than X days" (the issue's
  sketch).** Rejected per D1 — silent deletion of comparison history
  contradicts the product thesis. Re-surfaced only as the *advisory* cap,
  which never deletes without consent.
- **Exclude `pastura.sqlite` from backup (risk #4 as literally stated).**
  Rejected per D2 — the database is user-authored data; exclusion would
  lose a user's entire experiment history on device restore. Acceptable
  for re-downloadable model blobs, not for this file.
- **Scheduled background `VACUUM`.** Rejected — `VACUUM` rewrites the file
  and blocks; with bounded growth there is nothing to reclaim on a
  schedule. Reserved for post-clear-all only (§3).
