# ADR-028: Dark-Mode Token Pairing — Trait-Resolving `PasturaDynamicColor`

> **Status:** Accepted
> **Date:** 2026-07-27
> **Context:** Post-v1.0 design debt (#1274). `docs/design/design-system.md` §2.9
> defines nine `night*` dark-mode tokens but describes them as "未使用予約" — no
> mechanism resolved them, and no UI referenced them. Meanwhile the app is built
> from fixed light-mode tokens, so system dark mode flipped only the token-less
> default SwiftUI chrome and produced unreadable mixed-appearance screens. #1273 /
> #1275 stopped the bleeding with a defensive `UIUserInterfaceStyle = Light` lock;
> this ADR decides the permanent mechanism that lock is waiting on.
> **Verification basis:** every `file:line` below was read at `8b90421`, and the
> runtime claims were measured — see § "How the mechanism was verified".

## Decision

Introduce **`PasturaDynamicColor`** (`Pastura/Pastura/Views/DesignTokens+DynamicColor.swift`)
— a `light` / `dark` pair of `PasturaColorValue`s whose `color` is backed by a
`UIColor(dynamicProvider:)` closure that branches on
`traitCollection.userInterfaceStyle`. Point the paired `Color.*` aliases in
`DesignTokens+SwiftUI.swift` at it.

Because every consumer already reads a flat `Color.<token>` alias, redirecting
the alias is the whole adoption: **every existing consumer adapts with no edit**
— 520 `Color.<name>` references in 87 files, of 218 Swift files in `Views/` +
`App/`, at `15f8084` (this change's parent). The figure is `grep`-proxy scale, not
an exact callsite count: it also counts doc-comment mentions and the `UIColor.`
prefix. Reproduce with

```bash
git archive 15f8084 Pastura/Pastura/Views Pastura/Pastura/App | tar -x -C "$TMP"
grep -rhoE 'Color\.[a-zA-Z0-9]+' "$TMP" --include='*.swift' | wc -l   # 520
grep -rlE  'Color\.[a-zA-Z0-9]+' "$TMP" --include='*.swift' | wc -l   # 87
```

A different pattern gives a different number (`\bColor\.[a-z]…` yields 519 / 86),
so quote the command with the figure.

Three bounds are part of the decision, not incidental:

1. **Eight pairs, not nine** — see § "The `nightSurface` double-mapping".
   **Superseded 2026-07-29** (#1282, then #1313): `nightSurface` was deleted
   and 32 more pairs wired, taking the total to 40. The reasoning below is kept
   as the original record; the two Amendments carry what replaced it.
2. **The light alias is the side that becomes dynamic**; `night*` aliases stay
   static, so an explicit dark request remains expressible.
3. **`UIUserInterfaceStyle = Light` stays** (`Pastura/Pastura/Info.plist`).
   The 60 remaining light tokens have no dark counterpart (**28 since #1313**,
   of which 27 still owe gate 1 an answer), so the lock is what prevents a
   half-dark surface. Removing it is gated —
   see § "Rollout". The lock itself is unchanged.

### The `nightSurface` double-mapping

> **Resolved 2026-07-29 (#1282) by deleting `nightSurface`** — the leading
> candidate this section already names. What follows is the original
> analysis, kept because it is the rationale the deletion rests on; read it
> in the past tense. The underlying observation still holds: dark wants a
> background/surface/bubble three-step where light has two. Deleting the
> orphan does not foreclose adding a real light `surface` token later — that
> would be an ordinary new pair rather than a partner retrofitted to an
> existing dark value. Note that the §2.9 table row this section twice points
> at — the one carrying the deferral note — is **gone**, deleted with the token.

§2.9's table (`docs/design/design-system.md` § "2.9 Dark Mode") **mapped**, before
this change, **nine** `night*` tokens onto **eight** distinct day tokens:
`nightSurface` (#232620) and `nightBubble` (#2C2F28) both claimed
`bubbleBackground`. This change replaces `nightSurface`'s day-token cell with a
deferral note, so the table no longer asserts the double mapping. `nightSurface` has no
**UI** consumer: its references are the palette declaration, the
`Color.nightSurface` alias, the test asserting it stays unwired, the pairing
file's own doc comments, the `Info.plist` lock comment, and the doc / CSS rows.

This is an unresolved *design* question, not a typo: dark wants a
background / surface / bubble three-step where light has only a two-step
(`screenBackground` / `bubbleBackground`). Resolving it means choosing among:

- **Add a light `surface` token** — pairs cleanly, but drags the full five-file
  token workflow (`.claude/rules/swiftui-traps.md` § "Adding a `Color` design
  token = 5 files; the 5th fails silently") and adds to the palette, against the closing footer's "トークンを**減らす
  方向**で拡張してください（追加より削除を優先）".
- **Delete `nightSurface`** — consistent with that same footer, and it costs
  nothing today given zero consumers. The leading candidate.
- **Context-dependent pairing** — reject; a token whose partner depends on the
  callsite is not a token.

**Deferred to the palette-completion follow-up**, where the visual judgment
already lives. §2.9's table row carries a matching note so the doc does not keep
asserting a pairing the code declines to implement.

`DesignTokens+SwiftUI.swift` declares 85 `Color` aliases (84 at `8b90421`;

4 §2.11 chart leaves **68** light tokens; 8 are now paired, so **60** remain
light-only — the alert family (12), interactive states (6), avatar palette (17),
meta L1–L4 (12), link (3), header slots (3), the remaining moss steps,

`inkOnAccent` is in that 60 rather than excluded alongside `night*` /

Designing those 60 dark values is **not** mechanical translation — it is brand

## How the mechanism was verified

`adr-writing.md` §1 requires SDK behaviour to be confirmed rather than recalled.
Three channels, deliberately separated because they observe different things:

| Channel | What it establishes | Result |
|---|---|---|
| `UIColor.resolvedColor(with: UITraitCollection(userInterfaceStyle:))` | The mechanism itself. Deterministic, and does not pass through `Color.Resolved`, which `DesignTokens.swift:22-24` documents as linear-light and lossy. | Pass — each side resolves to its own token; `.unspecified` falls to light. |
| `Color.resolve(in: EnvironmentValues)` with `colorScheme` pinned | SwiftUI plumbing, i.e. that the *aliases* are dynamic and not merely that the pair type works. | Pass — all eight aliases resolve to their dark token under `.dark` and their light token under `.light`. |
| Rendered app, lock temporarily lifted, simulator appearance dark | The render path, which neither query above exercises. | Pass — the paired background / ink / rule / accent family visibly switches on Home. Per-token identity is NOT established here (a screenshot cannot separate `nightMuted` from `nightInkSecondary` by eye); the two query channels above establish that. |

A companion assertion checks that five unpaired aliases (`page`,
`promoBackground`, `warning`, `danger`, `mossSoft`) resolve *identically* under
both schemes. Its strength is limited and the test says so: those five are plain
`Color(.sRGB, …)` values with no trait dependency, so invariance holds by *type*
rather than by wiring, and none has a `night*` counterpart — so no plausible edit
to this feature reddens it. It documents the intended light-only boundary; it
does not police it.

**Scope of the render check, stated precisely:** one screen (Home), on the
**iOS 26.5 simulator**, not a physical device. It confirms trait routing reaches
rendering; it is **not** dark-mode QA. Per
`.claude/rules/swiftui-traps.md` § "iOS 26 Liquid Glass toolbar capsule" and
§ "`ImageRenderer` does not inherit the ambient environment", simulator
appearance is not load-bearing for visual sign-off. Real-device QA is a gate in
§ "Rollout", not a claim made here.

That check also produced a finding worth recording: Home is *already* close to
complete in dark, because its dominant tokens all fall inside the paired eight.
The unpaired damage is therefore **concentrated, not uniform** — expect it on
surfaces driven by the alert family, interactive states, promo, and meta L-family
(Settings, download progress, editor), and on the avatar palette, whose
light-cream bodies stay light. Sequencing the follow-up by screen rather than by
token count is the cheaper path.

## Consequences

- **Adoption cost for the eight is zero at the callsite**, and stays zero for
  each remaining token as its dark value lands (60 then, **27** now — this
  predicate is "a dark value lands", so it counts the tokens still *owing* one,
  not the 28 that are merely unpaired): add the
  pair, repoint the alias. #1282 confirmed this — 18 pairs, zero callsite edits.
- **The `tokens.css` mirror gate keeps working.**
  `scripts/check_design_tokens_css.py:37` globs
  `Pastura/Pastura/Views/DesignTokens*.swift` and requires every
  `PasturaColorValue(hex:)` literal to appear in `docs/design/ds/tokens.css`.
  The pairing code introduces **no** hex literal — it composes existing
  `PasturaPalette` tokens — so it is inert to that gate. Since #1313 split the
  pair table out, that property belongs to **two** files:
  `DesignTokens+DynamicColor.swift` (the mechanism) and
  `DesignTokens+DynamicPalette.swift` (the table). Both must stay literal-free,
  and both must keep the `DesignTokens` filename prefix or the glob stops
  reaching them.
- **Component-level token tests keep working.** `DesignTokensTests` asserts
  `PasturaPalette.<token>.red/green/blue`; the pair type wraps those values
  without changing them.
- **`Color.*` now means "the device's appearance" for eight tokens** (26 since
  #1282, 40 since #1313; the hazard widens with each gate-1 slice). Any
  consumer needing a *fixed* appearance must read `PasturaPalette.<token>.color`
  directly. `HighlightShareCard` is the reference consumer and was migrated in
  the same change — it built **both** its light and dark families from `Color.*`
  aliases, so leaving it would have collapsed the two into one and made an
  explicit light or dark export unexpressible. Nothing would have caught that:
  the token tests assert `PasturaPalette` components and the aliases' own
  resolution but never which of the two a *consumer* reads, ADR-009 rules out
  snapshot tests, and
  the light lock suppresses the symptom until whoever removes the lock hits it.
- **Three isolation constraints** under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`:
  - **The type-level `nonisolated` on `PasturaDynamicColor` is a runtime guard,
    not a compile requirement** — measured: deleting it still yields
    `** BUILD SUCCEEDED **`. `UIColor(dynamicProvider:)` takes a non-`@Sendable`
    escaping closure, so without the annotation the closure literal is inferred
    `@MainActor` while UIKit may invoke it off the main actor, and nothing
    diagnoses that. Keep it precisely *because* the compiler is silent here. This is a third sibling of `.claude/rules/swift-isolation.md`
    Patterns 6–7, covered by neither (Pattern 6 is `nonisolated async` executor
    inheritance; Pattern 7 is unannotated-ObjC-protocol conformance); the new
    § "Same cause, two non-test shapes" documents it. Copying the two values into
    locals first is *style* — `self` is a `nonisolated Sendable` struct, so
    capturing it would be equally safe.
  - `PasturaDynamicColor` is **not** `Equatable`. A synthesized `==` needs
    `PasturaColorValue`'s `Equatable` conformance from a `nonisolated` context,
    and that conformance is MainActor-isolated (the target builds with
    `SWIFT_APPROACHABLE_CONCURRENCY = YES`, which enables
    `InferIsolatedConformances`) — Pattern 5, which fails the build with
    `main actor-isolated conformance of 'PasturaColorValue' to 'Equatable'
    cannot be used in nonisolated context`.
  - Conversely `PasturaDynamicPalette` is deliberately **not** `nonisolated`:
    its static initializers read MainActor-isolated `PasturaPalette` statics.
    Marking it `nonisolated` fails with `Main actor-isolated default value in a
    nonisolated context`. The isolation that matters is on the closure.
- **A compile-only probe was insufficient** and this is the generalizable
  lesson: a `swiftc -typecheck` probe that constructed `PasturaColorValue`s
  *inline* passed, while the real code — which reads them from
  `PasturaPalette`'s MainActor statics — failed. A probe must replicate the
  dependency shape, not just the API shape, or it measures nothing.

## Rollout

Landing here: the mechanism, the eight pairs, the `HighlightShareCard`
migration, and the doc/comment sweep. Appearance does not change, because the
lock stays.

Removing `UIUserInterfaceStyle` is gated on **all** of:

1. Every alias in `DesignTokens+SwiftUI.swift`'s `Color` extension that is not
   sourced from `PasturaDynamicPalette` has either a designed dark value with
   visual sign-off, or a recorded decision that it stays fixed in both
   appearances. Stated as a predicate because the count itself moves — deleting
   `nightSurface` or adding a light `surface` both change it. Dated snapshots:
   59 at `8b90421`, **60** at `1215b01` — #1283 added `inkOnAccent`, whose light
   value is settled but whose dark answer is still open (darken `nightMoss`, or
   pair the token), so it owes this gate an answer too — **42** after #1282
   designed the §2.6 alert family and §2.7 interactive states (slice 1 of 4) —
   **27** after #1313 designed the §2.4 meta presets and §2.12 header slots
   (slice 2 of 4). Still open, not met.

   From #1313 on, this gate's count and the count of *unpaired* tokens diverge:
   28 tokens are unpaired but only 27 owe an answer, because `headerMetaSubdued`
   took the second branch of this predicate — recorded as fixed in both
   appearances rather than given a dark value. That branch was written into this
   gate at landing and #1313 is the first change to exercise it, so the two
   numbers are not interchangeable in any mirror from here on.
2. The `nightSurface` question above is resolved. **Met 2026-07-29** (#1282):
   deleted, per the leading candidate this ADR already named.
3. Sites relying on raw SwiftUI default colors are tokenized. **Met 2026-07-28
   (#1283)**: 33 hits across 16 files at `8b90421` → 2 at `1215b01`, both
   carrying an inline exemption comment. Deliberately **no count** is pinned as
   the target: the reading is ambiguous enough to dominate the number (requiring
   the colour to be the modifier's *direct* argument gives 28 at `8b90421`;
   allowing it anywhere inside the parens gives 33 across 16 files). Run the
   predicate instead:

   ```bash
   grep -rEn '\.(foregroundStyle|foregroundColor|fill|background|tint|stroke|shadow)\([^)]*(\.(primary|secondary|tertiary|quaternary|gray|white|black|red|blue|green|orange|yellow)\b|Color\.(primary|secondary|gray|white|black|red|blue|green|orange|yellow)\b)' \
     Pastura/Pastura/Views Pastura/Pastura/App --include='*.swift'
   ```

   The gate is met when every remaining hit is either tokenized or recorded as a
   deliberate exemption. Triage, not zero-ing, is the goal. The two surviving
   hits are `DogMark`'s white illustration body and the white 𝕏 over
   `ShareDestinationFill.xBlack`; two further exemptions sit outside the
   predicate's reach — that `xBlack` declaration and the white glyph on
   `StoryShareSheet`'s Instagram brand ramp. Brand pairs and illustrations, not
   un-tokenized surfaces.

   Two corrections to this gate's original wording, both about the predicate and
   neither touching the decision. The `DogMark` hit was called an
   `ImageRenderer` false positive: it is a `Canvas` `GraphicsContext` fill, and
   no `ImageRenderer` callsite matches the predicate at `8b90421` or at
   `1215b01` (not checked across all history). And `.clear` was cited as a
   legitimately-non-token hit, but `clear` is absent from the alternation above,
   so `.clear` sites never matched in the first place.

   **Portability**: `\b` is a GNU/BSD extension, not POSIX ERE. The command
   above works with system `grep -E`, but `git grep -E` silently returns **zero
   hits** — which reads as "gate met". Use `git grep -P` there, or swap `\b`
   for an explicit `[^A-Za-z]` guard.
4. Real-device dark QA across Home / ScenarioDetail / Demo / Simulation /
   Results / Settings.
5. The dark **share-card** path is re-verified on device. It is unreachable
   while the lock holds, and `ImageRenderer` does not inherit the ambient
   environment, so no automated test observes it (#1274 comment).

Until (1)–(5), a partial merge is safe precisely because the lock makes the
paired tokens unobservable.

## Alternatives considered

- **Asset-catalog color sets (`Contents.json` with Any/Dark appearances)** —
  rejected. This is the platform-idiomatic route and needs no custom type, but
  it moves the hex values out of Swift and **blinds two existing gates**:
  `check_design_tokens_css.py`'s `HEX_RE` extracts
  `PasturaColorValue(hex: 0x…)` from `DesignTokens*.swift`, so the `tokens.css`
  mirror check would silently have nothing to inspect; and `DesignTokensTests`
  asserts sRGB components directly, which a catalog color cannot offer at that
  granularity (`DesignTokens.swift:22-24` explains why the components, not
  `Color.Resolved`, are the assertion surface). Losing a CI gate to gain
  idiomaticity is the wrong trade here.
- **`@Environment(\.colorScheme)`-driven palette struct threaded through views**
  — rejected. It requires touching all 520 callsites (or every view's
  initializer), and it is *worse* than the status quo for `ImageRenderer`
  exports, which do not inherit the ambient environment at all. The one place
  this shape is correct is exactly where Pastura already uses it:
  `HighlightShareCard`, with an explicit `colorScheme` parameter.
- **`Color(light:dark:)` free function at each callsite** — rejected. Pushes the
  decision to 520 sites and loses the single canonical pairing table.
- **Complete all 59 dark values in this change** (the 59 as of `8b90421`; 60 since
  #1283) — rejected as a scope, not as a
  goal. The values need visual judgment per token, and the diff would cross the
  review-scope budget in `.claude/rules/subagent-usage.md` §2 several times over.

## Revisit trigger

- **The lock comes off** — revisit whether `Color.*` being appearance-dependent
  should be enforced mechanically rather than by the doc comment in
  `DesignTokens+SwiftUI.swift` (a lint rule banning `Color.<paired>` inside
  `ImageRenderer` content, say). While the lock holds, that comment is
  sufficient because the failure is unobservable.
- **A second fixed-appearance consumer appears** alongside `HighlightShareCard`
  — at that point the "read `PasturaPalette` directly" convention deserves a
  named helper rather than a doc comment.
- **`PasturaColorValue` gains a second nonisolated caller** — then marking it
  `nonisolated` becomes correct per Pattern 5's fix order, and
  `PasturaDynamicColor` can regain `Equatable`.

## Amendment 2026-07-28 — gate 3 met (#1283)

§ Rollout gate 3 is satisfied: the predicate went from 33 hits across 16 files
at `8b90421` to 2 at `1215b01`, both recorded exemptions. Two errors in the
gate's own wording were corrected in place — see gate 3 itself. This section
records what the work did, which is new material rather than a correction.

**Four exemptions, in two classes.** Brand pairs that must not follow Pastura's
palette in either appearance: `ShareDestinationFill.xBlack` and the white 𝕏 over
it, and the white glyph on `StoryShareSheet`'s Instagram ramp. And one
illustration: `DogMark`'s white body. Only the first and third match the
predicate; the other two sit outside its reach and are recorded anyway so the
next sweep does not re-triage them.

**Three raw-colour families the predicate structurally cannot see** were swept
too, so the new token would not be half-applied:

- White-on-accent held in a named constant (`PasturaPrimaryButtonStyle.foreground`,
  `SimulationPlayButtonMetrics.glyphColor`) or passed as a `tint:` / `.stroke`
  argument. The predicate only matches a raw colour that is a styling modifier's
  direct argument, so these were invisible to it — 9 sites, not the 4 it found.
- `Color.accentColor`, now absent from `Views/` and `App/`. Its asset is
  byte-identical to `moss` (#8A9A6C) but carries a `universal`-only idiom, so the
  swap is a no-op in light and a behaviour change in dark.
- A bare `.background` ShapeStyle, which adapts on its own but to system black
  rather than to `nightBubble`.

A site that merely *omits* a foreground and inherits the system label colour is
**not** in gate 3's scope.

**`Color.inkOnAccent` (#FFFFFF) was added** for the first family. It does not
resolve gate 1 — see § "60 tokens have no dark counterpart": its light value is
settled but its dark answer is a live two-option question, so gate 1's snapshot

**Two deliberate appearance changes** rode along, both contrast fixes rather
than tokenization: `ModelSettingsRow`'s `ActiveBadge` and `PromoCard`'s Retry
fill moved `moss` → `mossDark` (their labels are 9/9.5pt, so the 4.5:1 text bar
applies and white-on-`moss` is ≈3.03:1 — a light-mode AA failure in shipped
v1.0), and the two scenario badges adopted `PhaseTypeLabel`'s token pair.

## Amendment 2026-07-29 — gate 2 met, gate 1 slice 1 of 4 (#1282)

Two of the five rollout gates are now met. Gate 2 is closed by deleting
`nightSurface`. Gate 1 is **not** closed — 18 of the 60 outstanding values are
designed, leaving 42 — but the work established how the remaining ones should
be derived, which is the part worth recording here.

**Sequenced by screen, per this ADR's own render-check finding.** Slice 1 is the
§2.6 alert family (12) and §2.7 interactive states (6), because those drive
Settings, download progress and the editor — the surfaces the check named as
carrying the concentrated damage. Slices 2–4 are meta L1–L4 + GameHeader slots,
the avatar palette, and the §2.1/§2.3/§2.8 remainder plus `inkOnAccent`.

### The derivation is three arms, not one formula

Stated as one transform it would be wrong, and wrong in a way that only shows up
on the tokens it does not fit:

1. **Mid-tone accents on a dark ground** take the deltas measured off this ADR's
   own `moss` → `nightMoss` pair: hue held, HSL lightness +11, saturation +7.
2. **Surfaces (`*Soft`) invert role** rather than transform. Light's pale fill
   becomes a dark tinted fill; applying arm 1 would put a glaring pale card on a
   dark ground, against §1.
3. **Foregrounds (`*Ink`) are placed by target contrast**, not by transform —
   L=78%, verified at 7.7–8.4:1 over their own Soft. This arm is the robust one
   and should be preferred wherever a token's job is legibility on a known
   ground.

**Where arm 1 breaks, stated now so slice 2 does not rediscover it.** The deltas
generalize only to accents near L≈50–60% — that is where `moss` sits. Dark text
tokens (meta L1–L4, `link`, `mossInk`, the header meta slots) need arm 3; +11L on
`link` lands ≈4.5:1 on the night ground, short of the ~7:1 band this slice
established. Light surfaces (`promoBackground`, `page`) need arm 2. And the
**meta L1→L4 ladder inverts direction** in dark — "strong" becomes the brighter
end — so it is not a per-token transform at all.

**The 17-colour avatar palette fits none of the three.** Arm 1 blows out a
cream body (#F2E3C8, L≈87%); arm 2 destroys the character identities the four
body tones carry. It needs a fourth treatment — an overall dimming toward
"moonlit pasture", judged per character, holding the body-vs-nose/eye contrast.
No formula survives it, which is the concrete form of this ADR's claim that the
remaining values are brand work rather than mechanical translation.

### Two values came from review, not from the recipe

Both are recorded because the recipe would have produced the wrong answer and
nothing automated would have caught either.

- **`warning` is #D4B67E, not #DBBF8A.** Preserving luminance *order* inverts
  perceptual *order*. Light's `warning` is the quietest of the four bases against
  its own ground (2.23:1, where info/success/danger are 3.18–3.42); mapping
  luminance faithfully makes it the loudest in dark (9.58:1 vs 6.85–7.24). 8.74:1
  narrows that. The invariant worth preserving is contrast-against-own-ground,
  not luminance.
- **`disabledBackground` is #222420, not #2A2B26.** The first value sat at 1.049
  against `nightBubble` — invisible on the card surface where Settings rows
  actually render it — and it *rose* relative to that surface, while in dark
  "lighter" already means "raised" (it is what the §2.7 washes do). An inert
  surface has to sink.

### The pair-distance note was replaced by an assertion

### The ladder needed three placements, not one

The previous Amendment named the L1→L4 ladder as the one item no per-token
transform covers, and predicted arm 3 (target-contrast placement) would carry
it. Arm 3 carries most of it. It does not carry all of it, and the two places
it fails are the transferable part of this slice.

**The dark ground has a ceiling the light ground does not.** A near-white
surface affords 20.06:1 to near-black text; the dark card surface affords
13.60:1. Light's `metaStrongL3` / `metaBaseL4` sit at 13.11:1 and `metaStrongL4`
at 16.56:1, so the top of the ladder cannot be mirrored with any headroom. What
rescued it was an existing coincidence rather than a new value: both tokens are
`== ink` in light, so the ceiling-compressed answer is `nightInk`, which the
palette already had. Slices 3–4 should expect the same shape wherever a light
token approaches its ground's limit.

**Arm 3 is degenerate at mid-lightness.** Around L≈45% a tone reads at nearly
the same contrast against a pale ground and a dark one, so solving for the light
ratio returns the light value. That is not a failure of the method — it is the
method reporting that the token does not need a pair. `headerMetaSubdued` is the
case: #7B7D68 measures 4.04:1 on `screenBackground` and **4.03:1** on
`nightBackground`. The pair-distinguishability control reddening on such a value
is a signal to stop, not to invent a different one.

That distinction was got wrong first. The initial value mirrored
`design-system.md` §2.12's parenthetical — "midpoint of `metaBaseL1` and
`metaBaseL2`" — and placed #8E907B at 5.20:1. The parenthetical is a derivation
note for the light value, not a constraint the section imposes; §2.12 states the
opposite, that it evolves independently of §2.4. Mirroring it broke the
hierarchy the section actually describes: `headerMetaInk ÷ headerMetaSubdued` is
2.032x in light and 2.031x with the value held fixed, but 1.573x at #8E907B.
Recorded because the error is not detectable from the diff — the invented value
type-checks, passes every gate, and looks like a designed dark token.

**The dot ladder answers to a different invariant than its neighbours.** A lit
progress dot's job is to be distinguishable from an unlit one, and the unlit dot
is `moss` at 38% — a derived, untokenised value whose floor therefore *moves*
when `moss` resolves dark, rising from 1.43:1 against its ground to 2.16:1.
Placing the lit dots by ground contrast, as for the text tokens, drops
lit-vs-unlit to 1.34:1 at L1 and the indicator stops working. Anchoring instead
on `nightMoss` and inverting light's per-step lightness deltas keeps lit-vs-unlit
at or above light's at every step. The cost is real and accepted: the dark dot
is louder than the meta text beside it (6.40:1 vs 3.33:1 at L1) where light's
was slightly quieter. Function over perceptual-weight parity — the same trade
`disabledBackground` took in slice 1, for the same reason.
