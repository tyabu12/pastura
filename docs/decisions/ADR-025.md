# ADR-025: Gallery scenario ordering — curator-pinned + recency

- **Status**: Accepted
- **Issue**: #1117
- **Date**: 2026-07-16

## 1. Context

The shared-scenario gallery (`docs/gallery/gallery.json`, ~44 entries) is a
static file served over GitHub raw with ETag caching — no backend, no
server-side ranking, no telemetry. Until this decision the app applied **no
sort at all**: the Browse (さがす) list rendered the raw JSON array order,
filtered only by category / language / search. New scenarios are appended to
the end of the array, so they sank progressively lower — the newest content was
the least discoverable, the opposite of what a catalog wants.

The stated ideal was popularity / download-count ranking. But the app has no
mechanism to observe global installs: install state is per-device local only.

## 2. Decision

**Order the Browse listing client-side** (`GalleryScenarioSearch.filter`, after
the existing category/language/query filtering):

0. **Installed-and-unchanged last** (§5, 2026-08-27): a scenario the device
   already holds with a local hash equal to the gallery hash sorts after every
   other row, ahead of the `featured` key — the user has it, so it needs no
   promotion. An installed row with a pending update stays in the main group.
1. **Curator-pinned `featured` first**, ascending rank (`nil` sorts last).
   `featured` is a new optional `Int` on `GalleryScenario` / the JSON schema,
   decoded leniently for forward-compat (matching the `agentCount` / `rounds` /
   `minEngineVersion` posture).
2. **Then `added_at` descending** (newest first). The field is a fixed-width
   `YYYY-MM-DD` string, so a raw string comparison is lexicographically ==
   chronological — no `Date` parse (and no `ISO8601DateFormatter`, whose default
   returns `nil` on a date-only value).
3. **Then `id`** as a stable tie-break — `id` is unique, so the order is total
   and deterministic (Swift's `sorted(by:)` is not guaranteed stable).

The curator is the recommendation engine: hand-editing `featured` in the same
JSON that already carries the catalog *is* editorial ranking at this scale. Pins
are meant to stay few (≈3–5); a fully hand-weighted list is a maintenance tax
that goes stale.

A **"New" badge** (新着) marks entries added within 14 days, filling the Browse
card's single badge slot only when it is otherwise unbadged (install-state
wins — New is the useful signal on a not-yet-installed row).

## 3. Alternatives rejected

- **Popularity / DL-count ranking — deferred indefinitely.** It requires a
  count-collecting endpoint (even a Worker + KV is a backend), an App Store
  privacy-label change away from "no data collected", and privacy-manifest
  updates — spending the product's "fully offline, no telemetry" positioning,
  which cannot be un-spent. And at ~44 items with a small user base the signal
  would mostly measure *list position* (position bias × rich-get-richer),
  laundering the old ordering bug into "popularity". **Revisit trigger**: a
  community-submission pipeline pushing the catalog past ~150 items, and then
  only via opt-in collection.
- **Random / daily-shuffle as the list order — rejected.** An unstable order
  destroys spatial memory ("where was that scenario I saw yesterday?") and makes
  the list read as broken. Serendipity, if wanted, belongs in a bounded surface:
  a date-seeded "Today's pick" / curator-driven Featured banner — the Home
  discovery surface tracked in #89 (date-seeded rotation is #89's Phase 2) —
  never the listing itself.

## 4. Consequences

- Newest scenarios surface at the top of the unpinned group immediately; the
  curator can hand-promote a few evergreens via `featured` with a JSON-only edit
  (no app change after the introducing PR).
- The recency default is a treadmill — evergreen entries sink as the catalog
  grows; `featured` pins are the mitigation.
- If real popularity data ever lands (revisit trigger above), `featured` can be
  populated from a measured signal with no further ordering change.
- A `featured` pin does not reach a user who has already installed that
  scenario: the install-state key (§2 item 0) outranks it. Pins are a
  discovery aid for the not-yet-installed; that is the intended scope.

## 5. Amendment 2026-08-27 — install-state sort key (#1565)

**Trigger.** Browsing for something new, a user saw rows they already had
competing with new content. Install state is the one per-device signal the app
does have (§1), so it can rank without any of the popularity machinery §3
rejects.

**Decision.** Item 0 in §2: installed-and-unchanged rows sort last, on a key
that outranks `featured`. Nothing is hidden — the row's own "Installed" badge
already disambiguates it from new content. A row that becomes
installed-and-unchanged behind the list (via `refreshInstalledSnapshot()`)
keeps its current position until the next index `refresh()`, rather than
jumping to the bottom under the user.

**Edge handled.** A row installed from the detail screen would otherwise
vanish from the list on the pop back — directly under the scroll position the
same change restores (`SharedScenariosListView` `.task` re-fire, see
`.claude/rules/swiftui-traps.md`). Ids that become installed-and-unchanged
between two installed-snapshot reads stay visible (`sessionPinnedIds`) until
the next index refresh — and, because the pin is subtracted from the
installed-unchanged set, such a row also keeps its original sort position
rather than dropping to the installed group until then. That is deliberate,
not a sorting bug.

**Rejected.**
- *Hiding installed rows by default* (shipped briefly on the PR branch,
  reverted before merge). Installed scenarios are already reachable from Home,
  so nothing needs to see them in Browse — but hiding them in a second surface
  required a toolbar toggle, a hidden-count footer, and an `allInstalled` empty
  state, and that machinery read as out of place for a problem the sort alone
  already solves.
