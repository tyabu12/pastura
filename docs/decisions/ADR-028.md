# ADR-028: Dark-Mode Token Pairing — Trait-Resolving `PasturaDynamicColor`

> **Status:** Accepted
> **Date:** 2026-07-27
> **Context:** Post-v1.0 design debt (#1274). `docs/design/design-system.md` §2.9
> defines nine `night*` dark-mode tokens but describes them as "未使用予約" — no
> mechanism resolved them, and no UI referenced them. Meanwhile the app is built
> from fixed light-mode tokens, so system dark mode flipped only the token-less
> default SwiftUI chrome and produced unreadable mixed-appearance screens. #1273 /
> #1275 stopped the bleeding with a defensive `UIUserInterfaceStyle = Light` lock;
> this ADR decides the permanent mechanism that lock is waiting on.
> **Verification basis:** every `file:line` below was read at `8b90421`, and the
> runtime claims were measured — see § "How the mechanism was verified".

## Decision

Introduce **`PasturaDynamicColor`** (`Pastura/Pastura/Views/DesignTokens+DynamicColor.swift`)
— a `light` / `dark` pair of `PasturaColorValue`s whose `color` is backed by a
`UIColor(dynamicProvider:)` closure that branches on
`traitCollection.userInterfaceStyle`. Point the paired `Color.*` aliases in
`DesignTokens+SwiftUI.swift` at it.

Because every consumer already reads a flat `Color.<token>` alias, redirecting
the alias is the whole adoption: **every existing consumer adapts with no edit**
— 520 `Color.<name>` references in 87 files, of 218 Swift files in `Views/` +
`App/`, at `15f8084` (this change's parent). The figure is `grep`-proxy scale, not
an exact callsite count: it also counts doc-comment mentions and the `UIColor.`
prefix. Reproduce with

```bash
git archive 15f8084 Pastura/Pastura/Views Pastura/Pastura/App | tar -x -C "$TMP"
grep -rhoE 'Color\.[a-zA-Z0-9]+' "$TMP" --include='*.swift' | wc -l   # 520
grep -rlE  'Color\.[a-zA-Z0-9]+' "$TMP" --include='*.swift' | wc -l   # 87
```

A different pattern gives a different number (`\bColor\.[a-z]…` yields 519 / 86),
so quote the command with the figure.

Three bounds are part of the decision, not incidental:

1. **Eight pairs, not nine** — see § "The `nightSurface` double-mapping".
   **Superseded twice on 2026-07-29** (#1282, #1313) **and twice more on
   2026-07-30** (#1319, then slice 4 / #1325): `nightSurface` was deleted and 59
   more pairs wired, taking the total to 67 **at that point** (68 since #1327,
   69 since #1408 — neither of which is a slice). The reasoning below is kept as the
   original record; the four gate-1 slice Amendments carry what replaced it (14
   `## Amendment` headings exist; the gate-3 one, the gate-4/5 one, the three
   2026-08-05 ones, the 2026-08-06 one, the 2026-08-08 one, the 2026-08-12 one
   and the two 2026-08-13 ones are not slices).
2. **The light alias is the side that becomes dynamic**; `night*` aliases stay
   static, so an explicit dark request remains expressible.
3. **`UIUserInterfaceStyle = Light` stays** (`Pastura/Pastura/Info.plist`).
   The 60 remaining light tokens have no dark counterpart (**1 since slice 4**,
   and it owes gate 1 nothing — see gate 1). So the lock is no longer holding
   back a half-dark surface for want of values; **it stays for gates 4 and 5**,
   the two real-device checks. Removing it is gated —
   see § "Rollout". **Superseded 2026-07-31 (#1284): both gates met, key
   removed.** The reasoning is kept as the original record.

### The `nightSurface` double-mapping

> **Resolved 2026-07-29 (#1282) by deleting `nightSurface`** — the leading
> candidate this section already names. What follows is the original
> analysis, kept because it is the rationale the deletion rests on; read it
> in the past tense. The underlying observation still holds: dark wants a
> background/surface/bubble three-step where light has two. Deleting the
> orphan does not foreclose adding a real light `surface` token later — that
> would be an ordinary new pair rather than a partner retrofitted to an
> existing dark value. Note that the §2.9 table row this section twice points
> at — the one carrying the deferral note — is **gone**, deleted with the token.

§2.9's table (`docs/design/design-system.md` § "2.9 Dark Mode") **mapped**, before
this change, **nine** `night*` tokens onto **eight** distinct day tokens:
`nightSurface` (#232620) and `nightBubble` (#2C2F28) both claimed
`bubbleBackground`. This change replaces `nightSurface`'s day-token cell with a
deferral note, so the table no longer asserts the double mapping. `nightSurface` has no
**UI** consumer: its references are the palette declaration, the
`Color.nightSurface` alias, the test asserting it stays unwired, the pairing
file's own doc comments, the `Info.plist` lock comment, and the doc / CSS rows.

This is an unresolved *design* question, not a typo: dark wants a
background / surface / bubble three-step where light has only a two-step
(`screenBackground` / `bubbleBackground`). Resolving it means choosing among:

- **Add a light `surface` token** — pairs cleanly, but drags the full five-file
  token workflow (`.claude/rules/swiftui-traps.md` § "Adding a `Color` design
  token = 5 files; the 5th fails silently") and adds to the palette, against the closing footer's "トークンを**減らす
  方向**で拡張してください（追加より削除を優先）".
- **Delete `nightSurface`** — consistent with that same footer, and it costs
  nothing today given zero consumers. The leading candidate.
- **Context-dependent pairing** — reject; a token whose partner depends on the
  callsite is not a token.

**Deferred to the palette-completion follow-up**, where the visual judgment
already lives. §2.9's table row carries a matching note so the doc does not keep
asserting a pairing the code declines to implement.

## How the mechanism was verified

`adr-writing.md` §1 requires SDK behaviour to be confirmed rather than recalled.
Three channels, deliberately separated because they observe different things:

| Channel | What it establishes | Result |
|---|---|---|
| `UIColor.resolvedColor(with: UITraitCollection(userInterfaceStyle:))` | The mechanism itself. Deterministic, and does not pass through `Color.Resolved`, which `DesignTokens.swift:18-20` (`PasturaColorValue`'s doc comment) documents as linear-light and lossy. | Pass — each side resolves to its own token; `.unspecified` falls to light. |
| `Color.resolve(in: EnvironmentValues)` with `colorScheme` pinned | SwiftUI plumbing, i.e. that the *aliases* are dynamic and not merely that the pair type works. | Pass — all eight aliases resolve to their dark token under `.dark` and their light token under `.light`. |
| Rendered app, lock temporarily lifted, simulator appearance dark | The render path, which neither query above exercises. | Pass — the paired background / ink / rule / accent family visibly switches on Home. Per-token identity is NOT established here (a screenshot cannot separate `nightMuted` from `nightInkSecondary` by eye); the two query channels above establish that. |

A companion assertion checks that the unpaired aliases resolve *identically*
under both schemes — five at this ADR's landing (`page`, `promoBackground`,
`warning`, `danger`, `mossSoft`), **one after slice 4** paired every remaining
member (`headerMetaSubdued`, which is unpaired by decision and so is the only
one never expected to leave). Its strength is limited and the test says so: the five at landing were plain
`Color(.sRGB, …)` values with no trait dependency, so invariance holds by *type*
rather than by wiring, and none has a `night*` counterpart — so no plausible edit
to this feature reddens it. It documents the intended light-only boundary; it
does not police it.

**Scope of the render check, stated precisely:** one screen (Home), on the
**iOS 26.5 simulator**, not a physical device. It confirms trait routing reaches
rendering; it is **not** dark-mode QA. Per
`.claude/rules/swiftui-traps.md` § "iOS 26 Liquid Glass toolbar capsule" and
§ "`ImageRenderer` does not inherit the ambient environment", simulator
appearance is not load-bearing for visual sign-off. Real-device QA is a gate in
§ "Rollout", not a claim made here.

That check also produced a finding worth recording: Home is *already* close to
complete in dark, because its dominant tokens all fall inside the paired eight.
The unpaired damage is therefore **concentrated, not uniform** — expect it on
surfaces driven by the alert family, interactive states, promo, and meta L-family
(Settings, download progress, editor), and on the avatar palette, whose
light-cream bodies stay light. Sequencing the follow-up by screen rather than by
token count is the cheaper path.

## Consequences

- **Adoption cost for the eight is zero at the callsite**, and stays zero for
  each remaining token as its dark value lands (60 then, **0** now — this
  predicate is "a dark value lands", so it counts the tokens still *owing* one,
  not the 1 that is merely unpaired): add the
  pair, repoint the alias. #1282 confirmed this — 18 pairs, zero callsite edits;
  slice 4 confirmed it a fourth time and exhausted the predicate's subject.
- **The `tokens.css` mirror gate keeps working.**
  `scripts/check_design_tokens_css.py:37` globs
  `Pastura/Pastura/Views/DesignTokens*.swift` and requires every
  `PasturaColorValue(hex:)` literal to appear in `docs/design/ds/tokens.css`.
  The pairing code introduces **no** hex literal — it composes existing
  `PasturaPalette` tokens — so it is inert to that gate. Since #1313 split the
  pair table out, that property belongs to **two** files:
  `DesignTokens+DynamicColor.swift` (the mechanism) and
  `DesignTokens+DynamicPalette.swift` (the table). Both must stay literal-free,
  and both must keep the `DesignTokens` filename prefix or the glob stops
  reaching them.
- **Component-level token tests keep working.** `DesignTokensTests` asserts
  `PasturaPalette.<token>.red/green/blue`; the pair type wraps those values
  without changing them.
- **`Color.*` now means "the device's appearance" for eight tokens** (26 since
  #1282, 40 since #1313, 57 since #1319, 67 since slice 4, 68 since #1327,
  **69 since #1408** —
  the hazard widened with each gate-1 slice, and slice 4 exhausted the tokens
  there were to pair. It resumed twice anyway: #1327 and #1408 each added a *new*
  token, born paired, for a contrast fix rather than as pairing work. So the count is
  bounded by the palette's size, not closed — read "nothing left to pair" as a
  statement about the backlog, never about the total. See § Amendment
  2026-08-08). Inside an `ImageRenderer` export `Color.*` means the
  *injected* scheme, and light when nothing is injected, so a consumer needing a
  fixed appearance must inject one and read the raw palette — both halves stated
  as invariants below. `HighlightShareCard` is the reference consumer and was
  migrated in the same change: it built **both** its light and dark families from
  `Color.*` aliases, which would have collapsed the two into one and left the
  caller's choice inert. Nothing would catch that — the token tests assert
  `PasturaPalette` components and the aliases' own resolution but never which of
  the two a *consumer* reads, and ADR-009 rules out snapshot tests.
- **Three isolation constraints** under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`:
  - **The type-level `nonisolated` on `PasturaDynamicColor` is a runtime guard,
    not a compile requirement** — measured: deleting it still yields
    `** BUILD SUCCEEDED **`. `UIColor(dynamicProvider:)` takes a non-`@Sendable`
    escaping closure, so without the annotation the closure literal is inferred
    `@MainActor` while UIKit may invoke it off the main actor, and nothing
    diagnoses that. Keep it precisely *because* the compiler is silent here. This is a third sibling of `.claude/rules/swift-isolation.md`
    Patterns 6–7, covered by neither (Pattern 6 is `nonisolated async` executor
    inheritance; Pattern 7 is unannotated-ObjC-protocol conformance); the new
    § "Same cause, two non-test shapes" documents it. Copying the two values into
    locals first is *style* — `self` is a `nonisolated Sendable` struct, so
    capturing it would be equally safe.
  - `PasturaDynamicColor` is **not** `Equatable`. A synthesized `==` needs
    `PasturaColorValue`'s `Equatable` conformance from a `nonisolated` context,
    and that conformance is MainActor-isolated because `PasturaColorValue` takes
    the target's default isolation (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`) —
    not `SWIFT_APPROACHABLE_CONCURRENCY = YES` / `InferIsolatedConformances`,
    which an earlier revision credited: measured 2026-08-13 (#1439), the error
    reproduces with those flags absent **and** with the feature explicitly
    disabled, and stops only when `-default-isolation MainActor` is dropped.
    (Whether that feature is baseline in this toolchain was not isolated; what is
    established is that the build setting is not what isolates the conformance.)
    This is Pattern 5 § "Same cause, two non-test shapes" row 1 — the
    synthesized-witness side, not its located test shape — which fails the build
    with `main actor-isolated conformance of 'PasturaColorValue' to 'Equatable'
    cannot be used in nonisolated context`.
  - Conversely `PasturaDynamicPalette` is deliberately **not** `nonisolated`:
    its static initializers read MainActor-isolated `PasturaPalette` statics.
    Marking it `nonisolated` fails with `Main actor-isolated default value in a
    nonisolated context`. The isolation that matters is on the closure.
- **A compile-only probe was insufficient, and the operative variable is the
  compilation *stage*** — not the dependency shape, which this bullet originally
  named as the cause and which `swift-isolation.md` § Pattern 8 then recorded as
  unexplained. `[#IsolatedConformances]` reaches SIL generation — and prints with
  no source location — when the isolated conformance is used only through a
  compiler-**synthesized** witness, as it is here; `swiftc -typecheck` never
  reaches that stage, so the probe stayed clean while the target errored. (Used
  **from source** the same error is a located type-check-stage diagnostic — both
  measured, as a one-toggle control in a single program.) Re-measured 2026-08-13
  on Xcode 26.6 / Swift 6.3.3 (#1439): compiling (`-c -o /dev/null`, plus `-wmo`
  for a multi-file probe) rather than type-checking reddens the probe with the
  target's verbatim diagnostic, while replicating the dependency shape (reading
  from MainActor-isolated statics instead of building values inline), splitting
  the type across files, adding a use site of the *synthesized* `==`, and passing
  the target's `-enable-upcoming-feature` flags **all** leave `-typecheck` green.
  Recipe, and the location cue that recognizes this family: `swift-isolation.md`
  § Pattern 8.

### Standing invariants the pairing created

Two rules were settled in amendments but are **not** amendment-scoped — they bind
every future token and consumer, so they are stated here per § "How to read this
ADR"'s placement convention. Each amendment keeps its derivation; this is the
claim, not a second copy of the reasoning.

- **An occlusion layer — shadow or scrim — must be darker than every ground it
  covers.** Not "fixed": fixed is merely how you satisfy it when one value sits
  below all of them. Every §4.3 / §4.3.1 shadow and the scrim are therefore

## Alternatives considered

- **Asset-catalog color sets (`Contents.json` with Any/Dark appearances)** —
  rejected. This is the platform-idiomatic route and needs no custom type, but
  it moves the hex values out of Swift and **blinds two existing gates**:
  `check_design_tokens_css.py`'s `HEX_RE` extracts
  `PasturaColorValue(hex: 0x…)` from `DesignTokens*.swift`, so the `tokens.css`
  mirror check would silently have nothing to inspect; and `DesignTokensTests`
  asserts sRGB components directly, which a catalog color cannot offer at that
  granularity (`DesignTokens.swift:18-20` (`PasturaColorValue`'s doc comment) explains why the components, not
  `Color.Resolved`, are the assertion surface). Losing a CI gate to gain
  idiomaticity is the wrong trade here.
- **`@Environment(\.colorScheme)`-driven palette struct threaded through views**
  — rejected. It requires touching all 520 callsites (or every view's
  initializer), and it is *worse* than the status quo for `ImageRenderer`
  exports, which do not inherit the ambient environment at all. The one place
  this shape is correct is exactly where Pastura already uses it:
  `HighlightShareCard`, with an explicit `colorScheme` parameter.
- **`Color(light:dark:)` free function at each callsite** — rejected. Pushes the
  decision to 520 sites and loses the single canonical pairing table.
- **Complete all 59 dark values in this change** (the 59 as of `8b90421`; 60 since
  #1283) — rejected as a scope, not as a
  goal. The values need visual judgment per token, and the diff would cross the
  review-scope budget in `.claude/rules/subagent-usage.md` §2 several times over.

### The derivation is three arms, not one formula

Stated as one transform it would be wrong, and wrong in a way that only shows up
on the tokens it does not fit:

1. **Mid-tone accents on a dark ground** take the deltas measured off this ADR's
   own `moss` → `nightMoss` pair: hue held, HSL lightness +11, saturation +7.
2. **Surfaces (`*Soft`) invert role** rather than transform. Light's pale fill
   becomes a dark tinted fill; applying arm 1 would put a glaring pale card on a
   dark ground, against §1.
3. **Foregrounds (`*Ink`) are placed by target contrast**, not by transform —
   L=78%, verified at 7.7–8.4:1 over their own Soft. This arm is the robust one
   and should be preferred wherever a token's job is legibility on a known
   ground.

**Where arm 1 breaks, stated now so slice 2 does not rediscover it.** The deltas
generalize only to accents near L≈50–60% — that is where `moss` sits. Dark text
tokens (meta L1–L4, `link`, `mossInk`, the header meta slots) need arm 3; +11L on
`link` lands ≈4.5:1 on the night ground, short of the ~7:1 band this slice
established. (**Superseded by slice 4**, which placed the three §2.8 tokens at
4.631 / 5.378 / 6.340 by arm 3 holding each token's own light ratio. The ~7:1
band is this slice's Ink-over-Soft relation and was never a target for links;
slice 2 then refined arm 3 to "solve for the light ratio". Annotated rather than
rewritten, per this file's convention for a superseded prediction.) Light surfaces (`promoBackground`, `page`) need arm 2. And the
**meta L1→L4 ladder inverts direction** in dark — "strong" becomes the brighter
end — so it is not a per-token transform at all.

**The 17-colour avatar palette fits none of the three.** Arm 1 blows out a
cream body (#F2E3C8, L≈87%); arm 2 destroys the character identities the four
body tones carry. It needs a fourth treatment — an overall dimming toward
"moonlit pasture", judged per character, holding the body-vs-eye contrast *as
far as the floor allows*. No formula survives it, which is the concrete form of
this ADR's claim that the remaining values are brand work rather than mechanical
translation.

**Corrected in place 2026-07-30 (#1319), twice, both factual.** This paragraph
originally said "holding the body-vs-nose/eye contrast". (1) That contrast is
**not holdable**: light's body-vs-eye runs 9.48–10.85, and on the night ground
even a pure-black eye caps at 8.67–9.86 per character, so the shipped values
land at 78–79% of light. **That** is the floor-bearing figure: the ceiling is
per-character, and unlike 85.94% the shortfall is not forced by the algebra —
it varies 78.1–79.2%, because each character's own light ratio differs.

correction did. It is 85.94% for all four characters — but that uniformity is
arithmetically forced, not evidence: `cr(face, eye) / cr(face, black)` reduces

### The ladder needed three placements, not one

The previous Amendment named the L1→L4 ladder as the one item no per-token
transform covers, and predicted arm 3 (target-contrast placement) would carry

surface affords 20.06:1 to near-black text; the dark card surface affords
13.60:1. Light's `metaStrongL3` / `metaBaseL4` sit at 13.11:1 and `metaStrongL4`

token approaches its ground's limit.

ratio returns the light value. That is not a failure of the method — it is the
method reporting that the token does not need a pair. `headerMetaSubdued` is the
case: #7B7D68 measures 4.04:1 on `screenBackground` and **4.03:1** on

### The fourth arm: dim the family, keep each character's interior

The four bodies move down **as a family**, each holding its hue and its
absolute chroma; face and horn then follow from *that character's* own light
body-to-part contrast ratio. The sheep dims without being recoloured, and the
interior structure is preserved rather than transformed.

Three things make it work, and each is a place a plausible alternative fails:

- **Absolute chroma, not HSL saturation.** Holding `S` while lightness drops
  turns a pale cream (#F2E3C8 at L=87%, S=62) into vivid ochre (#D3A045 at
  L=55%): the same saturation is a tint high up and paint low down. Absolute
  chroma is the dial that keeps wool looking like wool.
- **Per-character ratios, not one global curve.** A single monotone compression
  fitted to the endpoints squeezes the *middle*: Alice's face-vs-body fell
  1.76 → 1.49 and the face merged into the wool. Each character occupies a
  different band of the light range, so any global curve flatters the wide ones
  and crushes the narrow ones.
- **Identity is perceptual, so it is measured perceptually.** The four light
  bodies sit within 1.03–1.14 contrast of each other; what tells them apart is
  hue. A contrast metric would report them as nearly identical and assert
  nothing, so the guard uses CIEDE2000.

### The on-ground ratio is a consequence, not a target

The body family **spans** a **7.0–8.0:1 window** on `nightBackground` — Alice at
7.99 essentially on the ceiling (`nightMoss` is 8.00), Dave at 7.02 on the
floor, so there is no slack in either direction and any hex tweak crosses a
bound. `nightAvatarBodiesSitInsideTheDesignedWindow` asserts it, reading the
ceiling from `nightMoss` itself rather than from a literal 8.0. The window is the designed object: below ~7:1 Dave's
interior collapses (his eye-on-face is the palette's thinnest step and drops
under 1.8), above ~8:1 the wool overtakes `nightMoss` at 7.999:1 and decoration
starts out-shouting the brand accent.

Recorded because the tempting way to write this is "placed at 7.5:1 on the
night ground" — which is **arm 3**, target-contrast placement, applied to a
token whose job was never legibility on a ground. The values would be identical
and the reasoning wrong, and the next slice would cite §2.5 as precedent for
contrast-targeting a decorative token, where the resulting number would not be
accidentally right.

### The floor is the mirror of slice 2's ceiling

Slice 2 recorded that the dark ground has a **ceiling** the light ground does
not. The same thing happens at the **floor**, and it binds harder. Light's
near-white ground affords 20:1 of downward headroom, so light can afford a horn
5.95× below its body and an eye 13:1 below its ground. The night ground *is*
the floor.

So eye-on-face is the one relation that cannot be preserved: it compresses
(Dave 2.45 → 1.93), and body-vs-eye lands at 78–79% of light against a
per-character pure-black ceiling of 8.67–9.86. Every character also sits at
85.94% of its own black-limit on eye-on-face, but that is constant by
construction for a shared eye token and carries no evidence — see the
correction in the #1282 Amendment. Expect this shape
wherever a light token's job is "much darker than the thing it sits on".

### `inkOnAccent` was a system choice wearing the shape of a colour

This ADR named it as a two-option question — darken `nightMoss` so white keeps
working, or pair the token — and left it open across three slices. The
arithmetic settles it decisively, and the reason is worth recording because the
options look symmetric until measured: **darkening `nightMoss` would have
invalidated three shipped slices.** §2.7's four washes are literally built from
its RGB; §2.4's dot ladder is anchored on it and its unlit floor is `nightMoss`
at 38%; and §2.5's body window reads its 7.999:1 against `nightBackground` as a
**ceiling**, with Alice at 7.99 sitting essentially on it. Lowering that ceiling
puts all four bodies above it, which reddens
`nightAvatarBodiesSitInsideTheDesignedWindow` and, worse, breaks the design
premise that the wool must not out-shout the brand accent. So a one-token
question would have re-opened seventeen values that had already had visual
sign-off.

Pairing costs nothing by comparison — `inkOnAccent` was already in the ten.

The value is **chosen, not derived**, and the ADR should say which. Material 3
flips `on-primary` from tone 100 to tone 20 when `primary` moves 40 → 80, which
is exactly what `moss` → `nightMoss` does; that fixes the *band*. Within it the
value is placed to clear **WCAG AAA (1.4.6, 7:1 normal text)**, because the
smallest consumers are 9pt and 9.5pt mono labels — `PromoCard`'s Retry and
`ModelSettingsRow`'s Active badge. It measures 7.117 on `nightMossDark` and
6.395 on `nightMoss`, against light's 4.737 / 3.035.

**It lands on `nightBubble`'s hex, and the order of the reasoning matters.**
Light carries the same coincidence (`inkOnAccent` and `bubbleBackground` are
both #FFFFFF), but slice 3's rule licenses carrying a coincidence only when both
tokens keep the same *job* across the flip, and a foreground and a surface do
not. The AAA target picks the value; the equality is a consequence, pinned by a
test. Read in the other order it would imply that a future change to
`nightBubble` should drag this token along. It must not.

### §2.3 is the ceiling phenomenon again, at the other end

Slice 2 found the dark ground has a **ceiling** the light ground does not, and
slice 3 found the same at the **floor**. §2.3 shows a third face of it: the
family **compresses because its anchor was placed by a different arm**.

`nightMoss` came from arm 1 (hue held, HSL lightness +11, saturation +7) and
therefore sits at 7.999 against `nightBackground`, where light's `moss` sits at
2.908 against its own ground. Every sibling must be consistent with that anchor
rather than with light's ratios. So `mossDark` — light's emphatic step, which
must stay emphatic — is necessarily *above* `nightMoss` and therefore
necessarily above 8:1 (measured 8.902). The moss → mossDark step narrows from
1.561 to **1.113**.

**Arm 3 is degenerate for a ladder step whose direction inverts.** Solving
`mossDark`'s own 4.538 on the night ground returns a value *below* `nightMoss` —
it would make the emphatic step the quiet one. So `nightMossDark` is placed by
holding its proportional HSL-lightness position between `moss` and `mossInk`
(0.400 of the way — exactly, in both appearances), which is the anchor-on-`nightMoss`-and-invert move slice 2
used for the dot ladder. Arm 3 *is* right for `mossInk` and `mossSoft`, whose
jobs are legibility and quietness against a ground rather than ladder
membership. **The generalisation: check whether a token's job is "be a step in a
ladder" or "read against a ground" before choosing an arm — the two arms
disagree by more than rounding when the ladder's anchor came from arm 1.**

### Borders and quiet lines invert direction, and the reason is measurable

Light draws a hairline *darker* than the surface it sits on. Holding that
direction in dark fails, and not marginally: a `promoBorder` keeping light's
1.204 on the dark side of its card lands at #1A1C17, which measures 1.207
against the card — passing, if that were the only check — and **1.010 against
the ground behind it**. The card edge would dissolve exactly where it has to
read.

So `promoBorder` and `mossSoft` keep their magnitude and flip direction. This is
not new: the original eight already did it with `rule` → `nightRule` (light 1.324
*below* the ground, dark 1.425 *above*). What slice 4 adds is the measurement
that makes it a rule rather than an aesthetic preference, and the guard's
predicate takes a **ground** as well as a surface for that reason.

`mossSoft` also moved **hue**, to the moss family's 80.9° rather than light's
47.7°. A pale cream-moss is cream *because* it is pale; at 5% luminance the same
hue reads as amber and would collide in meaning with `nightWarningSoft` (#383124,
hue 39°). Slice 3's absolute-chroma lesson, applied downward instead of upward.
Its magnitude is preserved for its **line** job, which is 7 of its 10 call sites across 9 files (by rendering
role; by API it splits 5 `strokeBorder` / 5 `fill`, because two of the lines are
thin filled rectangles rather than strokes);
its other job is a tinted fill under `mossDark` text, which gains contrast in
dark (2.911 → 5.685) exactly as §2.6's Soft/Ink pairs do.

of magnitude tighter than the rest`. Repointing the ground makes the margins

the step an edit flips first — by **3.28×** against the widest margin, 2.50×
against the next-tightest.

**And the inference was already false before the ground moved**, which is the part
worth recording. Under the stand-in the same first-to-last ratio was 5.42×, so
"an order of magnitude" overstated it there too. A first pass at this correction
said repointing the ground "changed which of the two is true" — it did not. It
changed the numbers; the overstatement was independently wrong and is retired
rather than re-explained. That mistake is the shape `knowledge-layering.md`
§ "Claims you author are assertions too" describes, one level up: the *same*
comment carried a measurement and an inference from it, and re-measuring the
figures made the stale inference look freshly derived. **When re-measuring a
self-quoted figure, re-check the inference against the OLD numbers too** — if it
was already wrong, retire it instead of restating it.

A tooling note that caused a round of wrong figures here: the test's `composite`
helper works in **Double** and does not quantise to 8-bit, so a verification
script that rounds each channel to an integer produces margins that differ in the
second decimal (0.918 vs 0.915). Match the helper, not the display.

### What is now asserted rather than written down

Sixteen tests in `DesignTokensTests+NightRemainder`, over four pure predicates

a **matched pair** per predicate — shipped values satisfy it, a
deliberately-broken input violates it — and slice 4's review found that shape is
not enough: **a predicate with N independent clauses needs N controls**, one
failing each clause *alone*. A single fixture that trips several at once is no
evidence that any one of them is separately enforced. The four predicates
therefore carry **seven** controls, not four.

Two of the seven are the alternatives this slice actually rejected rather than
invented inputs: holding `inkOnAccent` white in dark (≈2.13:1 over `nightMoss`,

`#FBFBFB` clears the 4.5 text bar over `mossDark` while missing the 3.0 non-text

`#323232` sits just above `nightBubble` and reads 1.327 against the ground but

it being the quietest of the five pairs.

by the fills' own luminance ratio — and `nightMossDark`/`nightMoss` sit only 1.113
apart, under the 4.5/3.0 = 1.5 the bars demand. No colour clears one and misses
the other in dark. The §2.3 dark ladder's tight rungs show up here as a limit on
what is constructible, not a coverage gap.

### The review split was still too coarse, and the failure was silent

Slice 4's diff was reviewed in five passes rather than the four planned, because
production Swift came to 15 files against `subagent-usage.md` §2's 12-file hard

## Amendment 2026-08-05 — the sheet question, answered (#1336)

Slice 4 left exactly one value flagged: `nightPage` #11130F filling
`ViewerPredictionSheet`, the palette's darkest token on a surface iOS convention
says should rise. A device pass has answered it — **it is not a hole, and the
conflict the arithmetic predicted never reaches the screen.** The value stands.

Answering it took two passes, because the first measured a screen that was not
rendering the ground this ADR designed.

### The ground was not `nightBackground`

`SimulationView` set **no screen background at all** — its `body` is
`ZStack { baseLayer; scrim }` and the `awaitingScenario` arm is an explicit
`Color.clear` — while `Color.screenBackground.ignoresSafeArea()` had twelve other
call sites in `Views/`. The ground fell through to the system background: black in
dark. In light it landed on #FFFFFF against the intended #FCFAF4, a gap small
enough to survive every pass this ADR records. Gate 3's raw-colour sweep could not
have found it, because the defect is an **absent** modifier, which has no syntax to
grep for.

Enumerating the class rather than the instance found a second site: `ResultDetailView`
set none either. Both were fixed in #1336, which made every `Route`-resolved screen root
and every tab root carry one.

That is the narrow predicate, and review found it is not the whole class. Five roots
attached their ground to the *loaded* sub-view rather than the outer container, so their
loading / empty / error arms still rendered the system colour — `ResultsView`'s empty
state was the sharp one, being a tab root and what a fresh install sees. The predicate
that actually bounds the defect is **"a rendered state shows the system colour"**, not
"a screen has no background". It was tracked in #1354 rather than swept here, because
each hoist is a visual change on a screen this pass did not measure — and this pass is
the record the amendment exists to make.

**#1354 has since swept it, and re-deriving from that predicate found two more the
five-site list had missed** — the list was itself enumerated by "ground attached to the
loaded sub-view", which is a *third* predicate, narrower again. `HomeView` already had
its ground on the container but no frame pin, so its `ProgressView` arm got a patch
rather than a screen; and `ModelDownloadHostView+StateFallbacks`' `plainContainer` had
no ground at all, taking six states with it including `checking`, the first screen a
fresh install renders. The second was invisible to any grep seeded on existing
`screenBackground` hits, because that file contained none. Fifteen call sites now
(fourteen outside `#Preview`) — a *count*, not a predicate: what bounds the class is
that every rendered branch has a ground behind it, and no grep expresses that.

It was also breaking something already asserted. `SimulationScrimStyleTests` checks
the scrim against "the grounds it actually sits on" and iterates
`[screenBackground, nightBackground]` — but on this screen in dark the ground was
system black, which is in neither list and which **no** fill can be darker than. The
test's stated premise was false on `main`; this change is what makes it true, which
is why the test needed no edit.

The screenshot is what exposed it. Sampling a flat region of the ground behind
the sheet returned pure #000000 across 3600 px; a dimmed `nightBackground` cannot,
since the same presentation reads #0E0F0C once the background is applied.

### What the composite does to the designed relation

Measured off two device screenshots (iPhone 16e, dark, `先取りゲーム`, first vote
phase), sampling flat interior regions only — mode over ≥3600 px, 100% agreement
in every unbroken window:

| | Value | Relation to the sheet |
|---|---|---|
| Sheet fill, both passes | #121310 (raw #11130F; +1 on R and B, G unchanged — colour management) | — |
| Ground behind, before the fix | #000000 | 1.126, sheet **above** |
| Ground behind, after the fix | #0E0F0C (≈0.52 × `nightBackground`, per channel in sRGB bytes — on luminance it is ≈0.39) | 1.031, sheet **above** |
| The token pair as designed | `nightPage` vs `nightBackground` | 1.099, sheet **below** |

The sheet fill arrives at its raw token value (+1 on two channels) while the ground arrives at
≈0.52 of its own, so the dimming lands **behind** the sheet and not on it. (The
sheet fill being byte-identical across both passes shows something weaker and also
worth having — that it is unaffected by the ground fix. It cannot establish the
asymmetry: a dimming that applied to the sheet too would apply in both passes
equally and leave the fill identical across them regardless.) That asymmetry
**inverts the relation §2.9 designed**: `nightPage` is placed 1.099 below
`nightBackground`, and
arrives on screen 1.031 *above* its own backdrop. The sheet does not sink against
its surroundings, because its surroundings are dimmed and it is not.

What it also does not do is *rise*. At 1.031 the sheet is flush; what carries its
edge is the grabber, the corner radius, and its own candidate cards at 1.372
against the fill. The operator's verdict was "flush, but fine" — neither of the two
readings slice 4 posed, which is the honest answer to record.

### What this changes about judging a surface token

**A token-pair ratio is not a prediction about a presented surface.** The comparand
is the composited backdrop, and presentation dimming moves it independently of the
palette — here far enough to flip the sign. Slice 4 reasoned from `nightPage`
against `nightBackground` and reached a worry that the screen does not contain.
Promoted to `.claude/rules/swiftui-traps.md` § "Adding a `Color` design token",
which is where the next author of a dark counterpart will be reading.

Two limits on the above. It is one device, one iOS version, one scenario, and
system presentation dimming is not a contract — a future iOS that dims less would
narrow 1.031 toward parity. And the 0.52 factor is *read off* the ground pair, not
derived; an attempt to corroborate it against the speech bubbles was abandoned
after the bubble fill turned out to be opaque (`BubbleShape().fill(fill)`,
`ChatBubble.swift`), which falsified the model being fitted. The ordering does not
rest on it: it is read directly off the composite.

away with `ink` because it is drawn against local surfaces rather than the app

That exemption is false, and it is the whole defect. It is now corrected in place
at its two loci (defect 3's paragraph and the scrim paragraph).

### The value, and a justification that did not survive review

The binding ground is **`nightBackground` #1B1D17**. Every screen carries it since
the #1354 sweep, and the family reuses `PasturaPalette.scrim`'s **#0B0C0A** so the

A first draft of this Amendment justified the value differently, and **the
justification was false**: it argued the pill is a root `.overlay` on

Recorded rather than quietly rewritten, because it is the same failure this
Amendment is about — a plausible claim about what a component sits on, asserted
without checking, load-bearing for a decision. It is also the shape § "A
self-quoted figure whose *claim* broke" already named: the overstatement was
independently wrong, so it is **retired rather than re-explained**. The chosen
value stands on the ground above; the tests assert `nightBubble` and `nightPage`
as deliberate margin, and say so.

### Two things that follow, and one that does not

**The moss tint cannot be kept.** Preserving the light-mode composite's G−B
(≈14.8) at α 0.10 needs a tint with G−B = 94. The same tint must sit below
#1B1D17 per channel, so G ≤ 28 and B ≥ 0 — **G−B cannot exceed 28 even at the
theoretical extreme**, more than three times short. So
§4.3's `彩度は苔系` gets an explicit exception (new §4.3.1) rather than a silent
violation. **(Superseded 2026-08-05 by #1378: the general recipe took the same
near-black, so an "exception" covering every member of §4.3 stopped being one.
The rule was dropped and the requirement moved up to §4.3 — see § Amendment
2026-08-05 (#1378).)** Light lightness is preserved — alphas solved on the red channel:
0.22→0.10, 0.45→0.36, 0.12→0.10 — and light hue goes neutral. Visually signed off
against before/after captures in both appearances.

**In dark the shadow darkens little, and that is the ground's fault.** The night
ground sits at relative luminance 0.0117, so there is little room below it: over
#1B1D17 these tints reach −1.6 sRGB steps at α 0.10 and −5.8 at α 0.36. Elevation
in dark is carried mostly by the surface being lighter than the ground plus the
hairline stroke — confirmed on the post-fix capture, not assumed. The change
removes a wrong glow first and adds a shadow second.

**`PasturaShadows` is *not* fixed by this, and not because it is small.**
`rgba(90,100,60)` is above the night ground too, across four consumers carrying
five shadow layers. Measured over `nightBackground` #1B1D17: `.tight` (0.04)
lifts +2.5/+2.8/+1.5 and `.soft` (0.2) **+12.6/+14.2/+7.4**, against the
+24.4/+27.5/+18.7 of the ModelPicker card this Amendment calls a visible glow.
`.soft` is half that error, not a tenth — an earlier draft said "an order of
magnitude lower alpha" and that was wrong twice over (0.2 is 2× the card's new
0.10). It is deferred on **blast radius**: correcting the tint re-opens §4.3's
`彩度は苔系` rule for all four consumers and wants its own amendment. Tracked as
**#1378**, with the measurement, so its survival is not read as endorsement —
the next element that floats on the ground must reach for §4.3.1, not `.tight`.

> either/or no longer applies: reach for either family, and pick between them
> on geometry. See § Amendment 2026-08-05 (#1378).

### What the guard does and does not certify

The rule as first written — then named `shadow_color_paired_alias` — keyed on a
leading-dot `Color.*`, so it was blind to the shape that shipped three times and
stayed blind after this fix. **#1377 widened it** and renamed it
`shadow_color_occluder_family`: it is now an
allowlist — a shadow tint must name `PasturaOccluderShadows` or
`PasturaShadows`, anything else is flagged — carrying the control pair this ADR
requires of a new rule. `match_kinds` was replaced by `excluded_match_kinds`
rather than tuned, because the allowlist form cannot enumerate in advance which
kinds its short match spans, and `match_kinds` fails open on an unlisted one.

Its control pair, recorded here because § "The three defects, and what each says
about the gates" above predates the widening and its violation arm is the *old*
paired-alias shape: the rule
fires on a raw `PasturaPalette.moss.color.opacity(0.22)` (the #1373 shape), on
both paired-alias forms, and on an unknown local binding; it stays silent on
`PasturaOccluderShadows`, on `PasturaShadows`, and across all 8 sanctioned call
sites in 6 files. Two deliberate negative controls back the mechanism: stripping
the regex's trailing `\S` turns the silence arm 8/8 **red** (`\s*` backtracks and
the lookahead then succeeds inside the whitespace), and dropping
`excluded_match_kinds` makes `DesignTokens.swift:156`'s
`.shadow(color:radius:x:y:)` doc comment fire.

**The remaining gap is mostly not syntactic — but "mostly" is the word.** Two
shapes stay unreached, both measured at 0 violations against a control that
fires on the same defect without them: an intervening comment between
`.shadow(` and `color:`, and the `ShapeStyle` form `.shadow(.drop(color:))`.
Neither exists in the tree today. Past those, the gap is a semantic one, and
**#1378 narrowed what it is without closing it.** This section originally located
it in `PasturaShadows` specifically — allowlisted while measured *above* the night
ground — but that family now meets the requirement, so the allowlist is no longer
a concession. What survives is the general form: the rule matches a family
**name**, so a member added to *either* family with a too-light tint passes it.
`PasturaShadowsTests` and `PasturaOccluderShadowsTests` carry the actual
requirement, against **hand-maintained** ground lists: a future night ground
darker than #0B0C0A would not be covered automatically. The scrim shape still has
no lint guard — one instance, no stable syntax to key on.

The instruction this section's config counterpart carried — *remove
`PasturaShadows` from the lookahead when #1378 lands* — is **not** what followed
from it, and is retired rather than executed. Dropping the name flags the
family's five legitimate call sites; measured 0 → 5 → 0 with the mutation's
anchor asserted, against this worktree's config alone.

## Amendment 2026-08-05 — the same defect, in the general recipe (#1378)

The Amendment above fixed three ad-hoc occluder sites and **deferred**
`PasturaShadows.tight` / `.soft` on blast radius, recording the measurement so
the deferral would not read as endorsement. This closes it: both layers now
carry the scrim's **#0B0C0A**, at alphas **0.03** and **0.13**.

### The premise check the issue demanded, and what it changed

#1373's retracted `nightPage` claim taught that a component's ground must be
established, not assumed. Done here for all four consumers, and none turned out
to be excludable — moss (90,100,60) is lighter than *every* dark surface in the
palette, `nightBubble` (44,47,40) and the art-tile `moss`-wash (56,61,50)
included:

| consumer | dark ground | layers | lift (R/G/B) |
|---|---|---|---|
| `PromoCard` — bottom safe-area inset of `ModelDownloadHostView`, body `Color.screenBackground` | #1B1D17 | tight + **soft** | +2.5/+2.8/+1.5 and **+12.6/+14.2/+7.4** |
| `GalleryCatalogRow` — card on `SharedScenariosListView`'s `screenBackground` | #1B1D17 | tight | +2.5/+2.8/+1.5 |
| `ResultsView+Timeline` — card is `bubbleBackground`, but radius 2 / y 1 puts the shadow outside it | #1B1D17 | tight | +2.5/+2.8/+1.5 |
| `ScenarioArtTile` — badge circle overhanging the tile corner | art-tile wash (56,61,50) / `nightBubble` | tight | +1.3/+1.6/+0.4 and +1.8/+2.1/+0.8 |

What it *did* change is the blast radius the deferral rested on. **"Four
consumers, five layers" is a count of sites, not of error**: `.soft` — the layer
carrying the whole visible defect — has exactly one consumer. The other three
are `.tight` alone, at ≤ +2.8, and two of them sit on a lighter local surface
that shrinks it further. So the deferral was sound on effort and overstated on
risk.

### Pairing was the real question, and it answers itself

The obvious alternative to a fixed near-black is to **pair** the tint — light
keeps moss, dark gets a counterpart — which would preserve §4.3's `彩度は苔系`
at zero light-mode change. It was rejected on one fact: **a dark counterpart is
a near-black anyway.** It must sit below #1B1D17 per channel, so `G ≤ 28` and
`B ≥ 0` cap its **G−B at 28**. Reproducing the light composite's hue at the
re-solved alphas needs a tint with G−B of **51** (`.tight`) to **58** (`.soft`)
— and **40** even if the alphas were left alone, since 40 is moss's own G−B and
a tint reproduces a hue at any alpha only by carrying it. Short under every
reading. (The #1373 Amendment states this as 94 against a target of 14.8; those
are that family's numbers at its own α 0.10, not transferable here — see
§ Amendment 2026-08-05 (#1373) § "Two things that follow, and one that does
not".) Pairing therefore buys *nothing in dark* and *only the light hue* — so the
decision was never "paired vs fixed", it was "is light's moss cast worth
keeping", and pairing is a mechanism that pre-answers that question without
looking.

Two secondary costs confirmed it rather than carried it: `PasturaShadows.*.color.color`
is the negative control `shadow_color_paired_alias` is verified against
(§ "Defects 2 and 3 are now mechanically prevented"), and making the canonical
card shadow the design system's only *paired* occlusion cue would hollow that
control out and complicate #1377's widening.

**Recorded because the first recommendation went the other way.** The draft
argued for pairing on the grounds that "light is unchanged, so QA halves" —
which is not a saving, it is the question restated as a premise. The captures
below then showed the light change is imperceptible, so pairing's entire
purchase was worth approximately nothing. Same shape as the two retractions in
the Amendment above: an argument that flattered the option it was defending.

### Controls

- **On the direction test**: setting the tint back to moss #5A643C reddens
  `tintIsDarkerThanEveryGroundItCanCover` with exactly **9** issues — 3 channels
  × the 3 dark grounds — and stays green against `screenBackground`, where moss
  genuinely is darker. The count is the discriminator: 12 would have meant the
  arm was firing on something other than direction. The geometry arm stays
  green. `tintIsTheScrimTint` also reddens, being a sibling arm reachable by the
  same fixture; the verdict was read off *which* test fired, not the exit code.
- **On the CSS mirror**: before `tokens.css` was updated the gate failed with
  `rgba(11, 12, 10, 0.03) missing` — which is what writing the tints as
  `hex:opacity:` rather than composing them from a token buys. Re-probing it on
  the final tree found **the reach it does not have**: the gate asks whether a
  Swift value appears *somewhere* in `tokens.css`, and each of these alphas is
  written twice there (a `--shadow-tint-*` var and the `--shadow-card`
  composite), so mutating one of a pair leaves it green. Mutating both, or the
  Swift side, reddens it. Recorded at the duplication in `tokens.css`, where the
  next editor acts on it. The probe that found this had been written expecting a
  redundant confirmation — a green probe is a finding about the fixture, not a
  spare guard.

### What this does not do

It does not close the semantic gap #1377 left. That issue landed first (#1380,
merged mid-flight here) and inverted the rule to an allowlist over family names,
which closes the *syntactic* gap. Naming a family still says nothing about the
value, so the tests remain the only check on darkness — see § "What the guard
does and does not certify" above, whose `PasturaShadows`-specific framing this
change narrowed to the general form.

**#1380 also left an instruction addressed to this change** — *remove
`PasturaShadows` from the lookahead when #1378 lands* — written on the premise
that the family's allowlist membership was a concession to a known-defective
tint. The premise is discharged, but the instruction does not follow from its
discharge in either direction: executing it would flag the family's five
legitimate call sites. Retired, with the config comment rewritten to say why. The
shape worth carrying: **a deferred instruction encodes the author's guess about
what the deferred change will look like.** This one guessed the two families
would merge; they did not, because their difference was never the tint.

Two carve-outs, both stated **before** the enumeration they qualify, because
each carries an α .2 that "every remaining … at α .2" would read straight past:
`docs/design/tab-identity/*lookbook.html` keep the moss shadow deliberately
(frozen exploration artifacts, not living references), and
`scripts/check_design_tokens_css.py`'s self-test fixture holds the *pre-#1378*
`PasturaShadows.soft` literal as a parser input — inert, but the shape a future
sweeper would want pointed at rather than declared absent.

**Outside those two**, every remaining `rgba(90,100,60,…)` in the tree is the DL
progress-dot unlit colour at α .38 / .2 / .28 — an unrelated token that a bulk
substitution on the tint would have corrupted.

## Amendment 2026-08-06 — the ImageRenderer half, measured then guarded (#1337)

§ "Revisit trigger" bullet 1 has now refused three mechanical guards. PR #1343
(which closed #1337's first half — bullet 1 and INDEX cite it by the *issue*
number, so both point at the same work) refused two of them for reasons of
expressiveness — a SwiftLint rule cannot state
the predicate, and an enumeration guard over palette types cannot redden on
#1319, its own motivating incident. This amendment records the third refusal,
which has a different and stronger cause — the A/B render-invariance probe #1337
proposed **has no reachable failure to detect** — and then the fourth shape,
which survives because the measurement told it what to look for (§ "What the
measurement left, and what now guards it").

### The axis the issue proposed was the wrong one

The issue asked for the production render "under ambient light and ambient dark".
But `PasturaDynamicColor` is fed by two disjoint channels — the SwiftUI
environment, which `.environment(\.colorScheme, …)` drives, and
`UITraitCollection.current`, which CG-time `UIColor` materialization reads. That
`ImageRenderer` ignores ambient state is the *premise* this whole trap rests on
(`HighlightCardImageRenderer.swift:11-12`), so an ambient-flip gate could not
distinguish "the flip never landed" from "the renderer ignored it by design". It
would have returned green either way, and the plan of record would have read that
green as "the threat model is narrower than stated".

Flipping the **injection** instead has no such ambiguity, and it is the axis the
#1319 question actually turns on: *does the explicit injection reach an alias that
`GraphicsContext` resolves?*

### Nine arms, on iPhone 17 Pro / iOS 26.5

| arm | what it renders | result |
|---|---|---|
| 0 | identical content, identical injection, twice | byte-identical — PNG bytes are a stable observable |
| V | the `ink` / `nightInk` pair, resolved directly | the two sides differ, so a null result cannot be blamed on the values |
| N | a **raw** `PasturaPalette` fill, injection flipped | unchanged — nothing else in the render environment is appearance-sensitive |
| P | a paired alias in plain `View` content, injection flipped | **changes** — the apparatus can observe movement |
| C | a paired alias filled by `GraphicsContext` in a `Canvas`, injection flipped | **changes** |
| T | the runner's own ambient style | **dark** |
| U | no injection at all | matches the injected-**light** bytes, differs from injected-dark |
| A | injection pinned `.light`, ambient flipped via `performAsCurrent` | unchanged |
| — | the production `render()` | green under every hypothesis; kept only as a smoke check |

Arm T is what makes P and C conclusive rather than suggestive: they ran under
ambient **dark**, and their injected-`.light` arm still came out light. Arm N is
the negative control that makes a red arm attributable, and arm P the positive
control that makes a green arm C meaningful — without it, "the `Canvas` did not
move" and "nothing moves in this harness" are the same observation.

**Scope: this ran on the iOS 26.5 simulator, not a device**, and this ADR is
elsewhere emphatic that the simulator misleads on appearance work. The
distinction § "How the mechanism was verified" already draws is the one that
licenses it: what the simulator *does* establish is that **trait routing reaches
rendering**, and every claim below is about which trait the dynamic provider is
handed — plumbing, not how a colour looks. A device would be required to conclude
anything about the *appearance* of a share card, and nothing below does. One
device / one OS minor either way, so treat a future SDK change as able to
invalidate this rather than as covered.

### What follows

1. **`GraphicsContext` resolves a paired alias against the injected
   `colorScheme`,** exactly as the view tree does. `SheepAvatarPalette`'s doc
   comment called this "a behaviour nothing in this repo verifies and no test here
   could"; the second clause was false. That doc comment is **rewritten**; the
   ADR's own copy of the same claim, in § Amendment 2026-07-30 (#1319), is
   **marked superseded rather than rewritten** — a shipped amendment is the record
   of what was known then, so the correction goes at its head as a pointer here.
   The slice's design choice stands on the reason that survives — a fixed palette
   keeps the export independent of a platform behaviour Apple owns — not on
   unverifiability.
2. **Ambient cannot override an explicit injection** (arm A), and an export that
   omits the injection resolves **light** regardless of ambient (arms U + T).
3. **Therefore the hazard is an omitted injection, not an alias read.** That
   inverts what § "Revisit trigger" bullet 1 and `swiftui-traps.md` had been
   pointing reviewers at, and both are updated. It also **supersedes § Amendment
   2026-07-30 (#1319)'s closing heuristic** — "ask not 'does a fixed-appearance
   consumer read this token' but 'does one read a *view* that reads it'". That
   line is left standing there as the record of what was decided then; the reach
   observation behind it holds, but the hazard it points at is now known covered,
   so `SheepAvatar` was never rendering wrong. The question that replaces it is
   whether every fixed-appearance export injects at all.
4. **So the probe is not shipped.** Every read inside the export is covered by the
   injection, so a production-path A/B probe is green by construction — the green
   non-guard the issue itself warned against. The nine arms live in the commit
   titled *"🧪 test: measure whether a Canvas alias escapes a fixed-appearance
   export"*, on the branch of the PR closing #1337, and are recoverable from that
   PR's commit list. Cited by **subject rather than SHA**: main squash-merges, so
   the commit is absent from main's history either way, and a SHA additionally
   does not survive a rebase — this citation was pinned to one and was dead
   within the hour. Nothing was left in the suite, so **no ADR-009 carve-out was
   needed** and none was written.

### What the measurement left, and what now guards it

The measurement renames the thing to look for; it detects nothing by itself. So
the same PR shipped the detector for what it renamed: `check_imagerenderer_injection.py`
(pre-commit + CI) fails any **app-target** file that constructs an `ImageRenderer`
without injecting `\.colorScheme`. It is a co-occurrence tripwire aimed at the
*next* export file rather than a fit to the one that exists, and it is verified by
mutation — deleting `HighlightCardImageRenderer`'s injection reddens it — not by
its success case. The three earlier refusals do not transfer, because this is
neither an enumeration nor a reachability question.

What it still cannot see is in its header, and is what keeps bullet 1 armed:
whether the injected value is the *right* one, and whether a drawn component
reached by some other path needs its own pin. Bullet 1's re-arm thresholds are
otherwise unchanged apart from the app-target scoping noted there — which this
amendment's own measurement spike motivated, having built an `ImageRenderer` in
the **test** target.

## Amendment 2026-08-08 — a role token, solved from the target ratio (#1327)

Moss-family label text over a translucent moss-family wash sat under WCAG AA in
**light** at all seven of its shipped sites. Every **seven-site range** below
uses the convention `DesignTokensTests+MossOnWash.swift` asserts — each wash
composited over the **worst-case ground for its appearance** (`screenBackground`
in light, `nightBubble` in dark) rather than each site's own — so light ran
**3.74–4.07** against a 4.5:1 bar. (§ "Why not `mossInk`" is the one place that
departs from it, and says why: comparing two elements for *hierarchy* only means
anything on the ground they actually share.) The
answer is a new token, `mossOnWash` #535D40 / `nightMossOnWash` #BDC6A4, placed
beside the §2.3 ladder rather than inside it. The values and the standing
invariant are in the body (design-system §2.3, and `PasturaPalette.mossOnWash`'s
doc comment); what follows is the derivation, and two controls that turned out
not to be controls.

### Which arm, and why the ladder position is only corroboration

§ Amendment 2026-07-29 (#1282) named three arms, and § "§2.3 is the ceiling
phenomenon again, at the other end" generalises: check whether a token's job is
*be a step in a ladder* or *read against a ground* before choosing an arm. This
token's job is the latter, so the justification is **arm 3** — solve the value
from the target contrast on the composited washes — and the light half was
placed that way. Result: the seven sites move to **5.51–6.00** in light.

The proportional-lightness position is *corroboration*, and the order matters
because an earlier draft had them reversed. `mossOnWash` lands at **0.700** of
the way from `moss` to `mossInk` on HSL L (51.37 → 21.96, giving 30.78), and it
holds `mossDark`'s hue and saturation almost exactly — H 80.7 / S 18.5 against
H 80.5 / S 18.8 — so only lightness moved. Had arm 3 and the ladder position
disagreed, arm 3 would have won.

### Two things that look like controls and are not

**Endpoint reproduction.** The dark half is that same 0.700 applied to the night
ladder: `nightMoss` L 62.75 → `nightMossInk` L 74.51 gives **70.98**, i.e.
#BDC6A4. The tempting check on that construction — confirm the mapping
reproduces the endpoints — is **pass-by-construction**. Any endpoint-anchored
interpolation reproduces its endpoints at t=0 and t=1 whatever it does between
them, so a green run certifies hex transcription and nothing about the value.

**The 0.400 coincidence.** The replacement control drafted for this amendment was
that `mossDark` sits at 0.400 of `moss`→`mossInk` *and* `nightMossDark` sits at
0.400 of `nightMoss`→`nightMossInk` — two shipped values, chosen slices apart,
landing on the same fraction and thereby establishing that the two ladders are
proportional. **That reading is wrong, and this ADR already says so.**
§ Amendment 2026-07-30 (#1325) records that `nightMossDark` was *placed by*
holding exactly that proportional position, because arm 3 is degenerate for a
ladder step whose direction inverts. The two values agree because the second was
constructed from the first. It is the same structural pass as endpoint
reproduction, one level up, and it survived a draft precisely because it looks
like an independent measurement.

So the dark half rests on **precedent plus measurement**, not on a control:
#1325 already established proportional-position transfer as the technique for
this specific ladder, and #1327 reuses it — then checks the result by arm 3 in
dark as well as light. The check is what has teeth:
`DesignTokensTests+MossOnWash.swift` asserts every site in **both**
appearances (dark 4.70–6.03 — the floor being the category
chip, where
`nightSelected` re-bases the wash alpha 0.18 → 0.24).

Residual, stated rather than papered over: **#BDC6A4 is a derived value that no
device has been looked at.** The tests bound its contrast; they say nothing about
how it reads. Real-device dark QA is therefore a genuine gate on this change, not
a formality — the standing position of § "How the mechanism was verified" that
the simulator misleads on appearance work applies with full force here.

### Why not `mossInk`, when a shipped pill already uses it on a moss wash

`mossInk` is the obvious candidate: the existing darkest step, no new token, and
`ResultsView.pillForeground(.completed)` already ships it on a `moss` @0.16 wash
at **9.15:1**. The rejection therefore needs a reason, or it reads as arbitrary.

The reason is **hierarchy, not contrast**. On a gallery catalogue card a `mossInk`
badge would measure 8.80:1 while the card's own description (`inkSecondary` on
`bubbleBackground`) measures 6.93:1 — the badge would out-contrast the copy it
annotates, and a supporting element would become the loudest thing in the row.
The results pill inverts that relation: it *is* its row's primary status, so
9.15:1 is the element carrying the row rather than a label shouting over one.
Same token, same family of wash, opposite roles — which is why the answer is a
token whose job is named rather than a fifth rung.

Three narrower rejections, recorded so they are not re-attempted:

- **Retune `mossDark`.** It is read at three dozen-odd sites across the Views
  layer, as fills and as text both; moving it to fix a handful of *text* sites
  moves every fill too.
- **Reuse `metaStrongL1` #5D6848.** Close in value, but §2.4 gives it a different
  job (a DL-progress preset step), and borrowing it would couple two families.
- **Lighten the washes.** Not solvable at any opacity: `mossDark`'s ceiling — the
  alpha→0 limit, i.e. the bare token on pure white — is **4.737:1**, so every
  wash with a visible tint puts it under the bar. That ceiling is asserted
  alongside the sub-AA half in `mossDarkCannotClearTheBarOnAnyOfThoseWashes`;
  pinning only the failing half would have invited exactly this attempt.

### What is not covered

The site enumeration in `DesignTokensTests+MossOnWash.swift` is
hand-maintained — its size pin is the authority on how many, deliberately not
restated here — and it composites over the worst-case ground per appearance
rather than each site's true ground. A *new* label placed on a moss wash over
some third ground is outside it, and nothing detects one. Two same-cause sites
this token deliberately does not reach were split out: **#1407** (an opaque
`mossSoft` ground, where `mossOnWash` measures only 4.29 — **closed**, see
§ Amendment 2026-08-12) and **#1408** (the `inkSecondary` family, whose gap is on
the dark side instead — **closed**, see § Amendment 2026-08-13 (#1408)).

### The count mirror went stale a third time

§ "A count mirror that a count-keyed sweep structurally cannot find" (§ Amendment
2026-07-30, #1325) recorded `INDEX.md`'s entry surviving
two slices at stale numbers. It went stale a third time here: the 67→68 sweep in
this change's first commit touched eighteen files and reached none of
`INDEX.md`, `docs/qa/dark-mode-qa.md` or `docs/design/screenshots/README.md`,
all three of which asserted 67 in prose — and, as the review of *this* amendment
found, **this ADR's own body** was a fourth, at § Consequences' "67 since slice
4 … nothing left to pair", a clause this change falsified outright. That bullet
is edited in place per § "Where new amendment content goes" (a standing
invariant lives in the body; the amendment records why). So the list of three
was itself drawn from an enumeration that understated itself — the section's
thesis arriving one level up, on the very amendment citing it.

The section's own diagnosis predicts this exactly — a sweep keyed on the number
finds only the places that already carry it in the shape you grepped for — and
the three misses share a further property worth adding to it: none is a *token*
document. They are an index, a QA walkthrough and a screenshot README, i.e. files
whose authors had no reason to expect a pairing change to reach them. So the
residual is not "the grep was too narrow" but "the mirror set is not enumerable
from the token files", and the honest position is that the **next** pair will
need the same manual sweep. Nothing here changes that; recording the three so the
next sweep starts from a longer list is the whole remedy.

**Correction (#1433):** `INDEX.md` has since left that sweep list — its ADR-028
entry was rewritten to carry no counts at all rather than re-synced, on this
section's own reasoning. The other two still assert counts in prose and still
need the manual pass. The generalisation is now `.claude/rules/adr-writing.md`
§4, a rule for every INDEX entry rather than a per-entry fix.

## Amendment 2026-08-12 — an opaque ground takes the §2.6 pairing (#1407)

**The standing invariant lives in design-system §2.3 and `mossOnWash`'s doc
comment, not in this file's body** — per § "How to read this ADR", token-level
values and their scoping are design-system's, and this is the same placement
#1327 gave `mossOnWash`'s own translucent-only scope. Stated once here for the
reader who arrives via the index: `mossSoft` used as an **opaque** fill is a
sanctioned text ground when the foreground is `mossInk`. That is the
`<family>Soft` + `<family>Ink` shape §2.6 already defines for the alert
families, and it measures **6.537** light / **6.505** dark, clearing the 4.5:1
bar with room in both. It does **not** land inside the band those four occupy —
it sits *above* it in light (5.389–5.976) and *below* it in dark (7.689–8.374),
which is the asymmetry § "A relative claim was retired" is about.

Three views rendered `mossDark` on that ground and measured **2.911** in light
against the 4.5:1 bar (`ContradictionBadge`, `PredictionOutcomeBadge`'s hit arm,
`HighlightCandidatesSection`'s `.revealed` chip; all under WCAG "large text").
Dark was already passing at 5.685, so this is a light-only fix — the opposite
asymmetry from #1408.

**Why not the role token.** § Amendment 2026-08-08 scoped `mossOnWash` to
*translucent* washes and named this ground as out of reach at 4.29. That holds:
the role token was solved from 4.5:1 on composited washes, and an opaque fill is
a different, darker ground. The answer here needed no new value because the

**A relative claim was retired, not retargeted.**
`mossBadgeStaysTheQuietestOfTheFiveInBothAppearances` pinned `mossSoft` +

that the holding was an *unaimed* consequence. Once the foreground is chosen by
solving for 4.5:1 the position becomes a byproduct of an aimed choice, and it
stops holding symmetrically — light inverts to loudest, dark stays quietest. The
pairing it described renders nowhere now, so the test had no subject.

That test **stayed green** through the repoint, because it read `PasturaPalette`
constants rather than the views it named. Worth carrying: an assertion about a
*pair* is not an assertion about the consumers listed in its doc comment. The

**Residue — closed by § Amendment 2026-08-13 (#1427).** This amendment left the

moss-family change) and named the streak one as the counter-example to reading
its site enumeration as "every label on `mossSoft` clears the bar". Both are

This amendment retires the badge-control claims in § Amendment 2026-07-30

## Amendment 2026-08-13 — the quietude tier is ground-relative (#1427)

`PredictionOutcomeBadge`'s last two `muted` labels move to tokens that clear the
bar: the miss arm to `inkSecondary` on `bubbleBackground` (3.475 / 3.021 →
**6.934 / 5.975**), and the streak sub-label to `mossInk` on the opaque
`mossSoft` capsule (2.136 / 2.413 → **6.537 / 6.505**). No new value — the pair
count stays **68**.

**The defect was the application, not the token.** design-system §8 records
`muted` as a deliberately sub-AA quietude tier, exempt from 4.5:1, with a
standing instruction not to place must-read information there. Both labels were
must-read: "Missed" is the badge's only label in that state, and a streak count
appears nowhere else on the screen.

**What §8 did not say, and now does.** Its exemption is justified with one
measurement — «#FCFAF4 上で ≈ 3.3:1», the `screenBackground` ground — but `muted`
runs 2.136–4.152 across the twelve grounds the app actually ships (six per
appearance). So the tier is **ground-relative**: a label legitimately ambient on
the page ground can sit at 2.136 on a tinted capsule and still read as
sanctioned. `DesignTokensTests+MutedAsContent` pins all twelve, and pins the
narrowest margin **by name** (`nightMuted`/`nightPage` at 4.152, 8% under the
bar) rather than as a range that hides which ground moves first. The app-wide
sweep of the remaining sites is #1448 — **94 `Color.muted` references across 44
files** after this change, counting code only (`grep -rn "Color\.muted"
Pastura/Pastura --include="*.swift"` returns 97 lines, three of them
doc-comment mentions).

**Why not §8's own remedy.** §8 routes must-read meta info to the §2.4 L3
preset, and `metaBaseL3` does clear the streak ground (5.272 / 6.518) while
keeping colour-based subordination that `mossInk` gives up. It is refused on the
rule § "Three narrower rejections" already states for `metaStrongL1`: a §2.4 rung
has a DL-progress job and borrowing it couples two families.
`DesignTokens+ExtendedPalette.swift` is the precedent — when a non-DL slot needed
exactly #4A4E3D it minted `headerMetaInk` at the same hex rather than collapse
the roles. **§8's binding requirement is the ratio; the family that owns the
ground supplies the token.** On an opaque `mossSoft` fill that is §2.3's
`mossInk` pairing, the same answer § Amendment 2026-08-12 reached for #1407.

The miss arm is a hierarchy call rather than a convention one. `metaBaseL3`
would clear it too, at 8.577 / 8.161 — but that puts the *failure* state above
the hit arm's 6.5, and § "Why not `mossInk`, when a shipped pill already uses it
on a moss wash" holds that a supporting element must not become the loudest
thing in the row. `inkSecondary` lands at parity instead.

### The accepted cost, and the one thing device QA decides

Streak and hit label are now the same token, so subordination rides on weight
(`.caption.weight(.medium)` vs `.semibold`), not colour. The recorded rule
forbids a supporting element being *louder*, not *equal*, so this is inside it —
but "equal contrast still reads as subordinate" is a visual claim no test holds.
Gate 4 QA in **both** appearances decides it, against a falsifiable criterion:
*the streak must still read as secondary to "Correct!", with weight alone
distinguishing them.* If it reads as a co-equal second label, the remedy is to
re-ground it off the capsule onto `bubbleBackground` with `inkSecondary`
(6.934 / 5.975) — deliberately **not** carried as an in-PR fallback, because it
is a layout change to a shipped component and would land after review without
its own critique.

### Two verifications worth carrying

The badge's colours moved out of `body` into accessors so
`PredictionOutcomeBadgeTokenTests` can pin them — closing the gap
`DesignTokensTests+MossSoftGround` recorded, where only the
`HighlightCandidatesSection` chip was reachable. **That extraction creates its
own failure mode**: accessor and `body` can diverge, and the pin cannot see
`body`. It is held by keeping `body` free of `Color.` references, checkable by
grep, not by the pin.

Both new guards were verified by mutation rather than by their success case.
Reverting either accessor to `Color.muted` reddens exactly the three pins for the
repointed roles while the untouched hit-arm pin stays green; dropping `nightPage`
from the ground fixture reddens the count pin *and* the by-name margin
assertion. The second is not hypothetical — an earlier draft of this change
enumerated five dark grounds, omitted `nightPromoBackground`, and reported a
worst case that was wrong as a result.

## Amendment 2026-08-13 — the ink-family role token, and the other asymmetry (#1408)

**Discharges § Amendment 2026-08-08's "What is not covered" → #1408**, which
split this out as the sibling `mossOnWash` deliberately did not reach and left
open; that entry is marked closed in place.

`inkOnWash` #5A5A55 / `nightInkOnWash` #BAB7A9 join as the **69th** pair. Four
sites paint `inkSecondary` as both a label and the translucent capsule under it
— a *self-wash* — and in dark that measured 4.413 (`PhaseEditorSheet.fieldPill`),
4.501 (`ScenarioBadgeStyle.secondary`), 4.501 (`PhaseTypeLabel`), 4.773
(`ResultsView`'s paused pill). The role token takes them to 4.991 / 5.090 /
5.090 / 5.397. Worst-case grounds per appearance, per § Amendment 2026-08-08's
convention.

**The asymmetry runs the opposite way from #1327, and that is the whole reason
this is a second token rather than a wider one.** There, moss-family label text
failed in *light* and dark already passed, so the answer darkened the light half.
Here light clears at 5.270–5.595 and dark is the failing appearance, so the
answer lightens the dark half. `mossOnWash` could not be stretched over these
sites — wrong family — and a token cannot be both.

**The light half is `inkSecondary` copied verbatim, not aliased.** Light was
never broken, so the pair exists to give dark independent control, and the copy
is what makes that possible. Consequence worth stating plainly: on a light
device this change is invisible by construction, so light-appearance QA cannot
confirm or refute it.

**Two `4.501`s are not a passing grade.** They clear 4.5 by 0.001 — arithmetic
green with no margin for a later wash tweak. `ScenarioBadge.swift`'s doc comment
already recorded that figure and called it "the designed value, measured", which
was true and still left the pattern one edit from red. The guard therefore
asserts a *marginless band* for the three sub-bar / on-bar sites rather than
"under the bar", which would have had to drop two of them and lose the finding.

### Why not a rung that already exists

Two separate questions hide here, and an earlier draft ran them together by
citing §8 for both. Splitting them:

**That a new pair is needed at all is structural, not a judgement.** Only the
*light* alias is repointed to a `PasturaDynamicColor`; every `Color.night*` alias
stays fixed (bound 2, above). So "leave light alone and raise only dark" is
inexpressible at a callsite — no existing pair has this light value with a
different dark one. Any dark-only fix that does not retune `nightInkSecondary`
across its 93 sites therefore *forces* a new pair. §8 has nothing to do with it.

**Which value the dark half takes is the judgement**, and it is where the
alternatives live. `nightInk` reaches 7.955–8.602 on these washes and **would**
clear the bar, so unlike `mossOnWash` there is no impossibility proof. It is
refused because it is the body-text rung and these are subordinate badges — each
of the four is the non-accent arm of a two-way choice, and `ScenarioBadge`
documents its `installed` arm as "quieter" in as many words. Adopting it would
also move light from 5.350 to ≈10.6 where nothing is wrong. **Note what §8 does
and does not say**: its rule is that the replacement comes from the family owning
the ground, which `nightInk` and `nightInkSecondary` both satisfy — §8 does not
discriminate between rungs *within* a family, and reading it as if it did would
be over-reading. The nearer precedent is §2.9's `nightHeaderMetaInk`, which
duplicates `metaBaseL3`'s light hex and then diverges in dark precisely because
"乗る面が違うので同じ目標比を別の地で解くと別の答えになる".

That refusal only means something if the cheaper answer really does work, so
`nightInkWouldAlsoClearTheBarAndIsRejectedOnRoleNotContrast` asserts that it
does — a future reader has to argue about hierarchy rather than rediscover the
arithmetic.

Lowering the dark wash alpha was the other lever, and the honest statement is
that it is **cheap and still wrong** rather than expensive — the lever works,
which is exactly why the rejection has to rest on something else.

The self-wash ceiling (alpha→0) is 5.975, and `fieldPill` needs only
0.16 → **0.150** to reach 4.5010. But 0.15 is the alpha two of its sibling rows
already ship, so that buys exactly the marginless state this change exists to
leave; matching the role token's 4.9908 instead needs alpha ≈**0.097** — and the
same ≈0.097 applies to `PhaseTypeLabel`'s own 0.15 row, whose 15% fill is
documented as load-bearing, so this is a class-wide figure rather than one
site's. The rejection therefore rests on the fill being load-bearing, not on the
size of the edit.

Retuning `nightInkSecondary` itself was refused on reach — **93
`Color.inkSecondary` lines across 43 files** on `main`, of which four are
self-washes. Reproduce with
`git grep -c 'Color\.inkSecondary' main -- 'Pastura/Pastura/'`: the
directory-prefix pathspec is load-bearing, because `Pastura/Pastura/**/*.swift`
silently skips the top-level `PasturaApp.swift` and returns 90 instead — a
"correction" of this figure that lands on 90 was measured with the wrong glob.

### Out of scope, deliberately

`ResultsView`'s `pending` pill is a `muted`-on-`muted` self-wash (2.602 dark).
That is §8's quietude tier, swept app-wide by #1448, not this bug class.

**`GameHeaderStatus` is only partly that** — its `background` is
`foreground.opacity(0.14)`, so every arm is a self-wash, but only three of seven
(`paused` / `cancelled` / `error`) are `muted`. The other four are **moss-family**:
`moss` for `simulating` / `demoing` / `replaying` and `mossDark` for `completed`,
measuring **2.561** and **3.832** in light at 9pt — worse than anything this
change repaired. Those four fall through both nets: #1327's `mossWashSites`
fixture does not list them, and #1448 is scoped to `muted`. Tracked separately
rather than bundled here, since it is a different family, a light-side defect,
and not something this branch introduced — **#1455**, closed by § Amendment
2026-08-14.

`ShareDestinationTab` looks like a fifth site and is not:
its `ink` @0.08 wash is the icon **circle**, carrying `icon()` alone, so WCAG
1.4.11's 3:1 applies there — and its `Text(label)` sits *beneath* the circle on
the plain card ground, not on the wash at all.

### What the guards buy, and one that fired

Every claim above is asserted by `DesignTokensTests+InkOnWash`, and each was
verified by mutation rather than by its success case: collapsing
`nightInkOnWash` onto `nightInkSecondary` reddens five arms naming the right
figures, dropping a fixture row reddens both size pins, and perturbing the light
half reddens both light clauses. `ResultsPillTokenTests` and
`ScenarioBadgeStyleTokenTests`'s repointed arm were probed the same way.

**One probe failed to fire, and that is the entry worth carrying.** The negative
control excludes `ResultsView.paused` by *name string*; a probe that replaced
that row with a duplicate of another left the filter matching nothing and the
whole suite green — the exclusion had silently stopped excluding. A
`failing.count == 3` pin is what makes it falsifiable. Any loop whose scope is
carried by a string needs the filtered size asserted, not just the fixture's.

Checked and found clean, recorded because that is otherwise indistinguishable
from not checked: `ResultsView+Timeline` needs **no** edit — its node fills from
`pillForeground` precisely so a pill retint repaints it in lockstep, and the dot
is non-text, so 1.4.11's 3:1 applies and every candidate clears it.

## Amendment 2026-08-14 — the header status pill, and when the Ink step outranks the role token (#1455)

`GameHeaderStatus` derived `background` from `foreground` at 0.14, so every arm
painted a label on a wash of its own token. The four moss-family arms were under
the 4.5:1 bar in light at 9pt: **2.561** for `simulating` / `demoing` /
`replaying` (`moss`) and **3.832** for `completed` (`mossDark`) — worse than
anything #1327 or #1408 repaired. § Amendment 2026-08-13 (#1408) named them and
deferred them; this closes that.

The fix separates the two roles the single token was serving. `washToken` keeps
every capsule fill byte-identical — `moss@0.14`, `mossDark@0.14`, `muted@0.14` —
and only the labels move: the three active arms to `mossOnWash` (**5.891** light
/ 5.783 dark) and `completed` to `mossInk` (**8.604** / 6.047). The `muted` arms
stay; they are §8's quietude tier, swept by #1448.

### The `mossInk` rejection resolves the other way here

§ "Why not `mossInk`, when a shipped pill already uses it on a moss wash"
rejected exactly this token for exactly this shape. That rejection stands, and so
does this decision, because its discriminator is **hierarchy**: a `mossInk` badge
out-shouting the copy it annotates is the failure; `ResultsView`'s completed pill
is fine precisely because it *is* its row's primary status.

A header status pill is the results pill's case, not the badge's. It carries the
screen's run state, and the header's own title still out-contrasts it — **13.147
vs 8.604** in light and **10.769 vs 6.047** in dark, so nothing is being shouted
over. That relation is the exception's load-bearing condition and it is now
executed, in `theCompletedPillDoesNotOutShoutTheHeaderTitle`; a retune that
inverts it invalidates the exception rather than merely reddening a test.

**The two sections quote different figures for the same site and both are
right**: that one composites over `bubbleBackground` (9.15 for
`ResultsView.completed`, the card it sits on), while the guard fixtures use
`screenBackground` as the light worst case (8.807 for the same site). That
departure is not new here — § Amendment 2026-08-08 already carves it out, on the
grounds that comparing two elements for hierarchy only means anything on the
ground they actually share. Do not reconcile the pair by editing either number.

### What was rejected

- **Both moss arms to `mossOnWash`**, i.e. §8's default with no exception. Clears
  the bar (5.891 / 5.649) but collapses the active-vs-completed distinction to
  the wash alone, and the two washes differ by **1.043** in light and **1.022**
  in dark — no longer a distinction. The header exists to signal run state at a
  glance.
- **Both to `mossOnWash`, with `completed`'s wash raised to 0.22** to rebuild the
  distinction from the fill instead. Reaches 1.155 / 1.221 of wash separation but
  drops dark to **4.738**, and 0.26 breaks it outright at 4.335 — a margin this
  thin on the appearance that was never broken is the wrong trade, and it changes
  the capsule's visual weight.
- **Raising the wash alpha with the labels left alone.** Not solvable at any
  opacity, and for the active arm not even in principle: `moss`'s alpha→0 ceiling
  on `screenBackground` — the bare token with the capsule erased — is **2.908**.
  `mossDark`'s is 4.538, i.e. it clears only in that same degenerate limit. Both
  halves are pinned, because asserting only the failing one invites the attempt.

### What this costs, and the one thing device QA decides

`background` no longer derives from `foreground`, and a test pinned that it did
— on the stated grounds that "a future override cannot drift the background tone
away from its foreground". That invariant predates the `*-on-wash` role tokens,
when label and wash genuinely were one token, and holding it is what produced the
defect. Every other translucent-wash site in the app had already split them. What
survives is the weaker, still useful pin: one declared token at one declared
alpha, not a hand-set colour per case.

The residual gap is the ground. Every other row in `mossWashSites` sits on an
opaque surface, which is what makes its worst-case-per-appearance convention a
real bound; `GameHeader` composites `screenBackground.opacity(0.78)` over
`.ultraThinMaterial` with the screen's content scrolling beneath. So for that row
the pinned ground is **nominal**, not a bound — at the pathological limit
(arbitrarily dark content, ignoring the material's lightening) the active arm
measures 3.690 rather than 5.891. It is still a large strict improvement there,
from 1.604. Light-appearance device QA with dark content under the header is what
covers the difference, and no test can.

### Count-mirror sweep

§ "The count mirror went stale a third time" predicted the next pair would need a
manual pass. It did. The mirrors of `mossWashSites`' size were
`DesignTokens+NightPalette.swift`'s `nightMossOnWash` doc, three prose claims in
this ADR, and two in the fixture's own file; all are rewritten to carry no number
and defer to the size pin, which is the only mirror a test can enforce. The cited
*ranges* were checked and survive unchanged — the new row is 5.891 light (inside
5.51–6.00) and 5.397 dark (inside 4.77–5.62).

Two same-word decoys were left alone deliberately, and a future sweep must not
move them: `GameHeaderStatus`'s **seven enum arms** in § Amendment 2026-08-13
(#1408), and **#1354's seven-site ground sweep** in § Amendment 2026-07-31 and
`docs/qa/dark-mode-qa.md`. Neither counts moss washes.
