# ADR-029: Shared-Scenario Highlights — Static Curated Excerpts on Web Landing and In-App Detail

> **Status:** Accepted
> **Date:** 2026-08-05
> **Context:** Shared scenarios are hard to evaluate without running them. The
> `/s/<id>/` landing pages (#1071) render only `gallery.json`'s title +
> description, and `GalleryScenarioDetailView` shows metadata plus a phase
> sequence — neither surface shows what a simulation actually *feels* like.
> On-device inference (Gemma 4 E2B class) is near-deterministic for a given
> model + scenario version, so the play pattern worth selling is "copy it and
> tweak it", not "run it to see a different outcome". Issue #1381.
> **Verification basis:** every cited file was read, and every count measured,
> at `3a056fc0` (this branch's fork point from main).

## Context

A highlight is a short, curated excerpt of a real simulation run — a few
exchanges of dialogue, the YAML fragment that produced them, and an invitation
to edit — published alongside a shared scenario. Two consumption surfaces:

- **Web**: the `/s/<id>/` and `/ja/s/<id>/` landing pages (Astro, build-time).
- **App**: `GalleryScenarioDetailView` (fetch-time; implementation split to a
  follow-up issue, but the policy and data contract are fixed here so the
  parallel session inherits decisions, not open questions).

Constraints that shaped the decisions: highlights are LLM-generated text
published on the open web (content-safety surface, ADR-005); scenario YAMLs
are versioned by `yaml_sha256` in `gallery.json`, so highlights can go stale;
and ROADMAP defers "Replay gallery / Shared Scenarios integration" to
Phase 3, so this feature must be — and stay — distinguishable from replay.

## Decision

### 1. Data contract — sibling files, index-anchored

One JSON file per gallery entry: `docs/gallery/highlights/<id>.json`.

```jsonc
{
  "schema_version": 1,
  "scenario_ref": { "id": "...", "yaml_sha256": "..." },   // pins the scenario version
  "source": { "model": "...", "run_id": "...", "generated_at": "YYYY-MM-DD" },
  "excerpt": [ { "agent": "...", "round": 2, "phase": "speak_each",
                 "phase_index": 0, "source_field": "statement", "text": "..." } ],
  // phase_index = position in the scenario's phases list; it disambiguates
  // repeated phase names so the gate can check the within-round bound
  // mechanically (Decision 3), not just the phase's class
  "yaml_hook": { "fragment": "...", "caption": "..." },    // the YAML that produced the excerpt
  "teaser": "...",                                          // one line, ending withheld
  "window_override": false,                                 // true iff Decision 3's late-round flag was used
  "content_filter_applied": true                            // audit attestation (Decision 2)
}
```

- **`excerpt` is capped at 8 entries** (schema `maxItems`, enforced by the
  extractor and the gallery gate). The cap is what keeps a highlight an
  authored enumeration rather than something that scales with run length —
  that property is load-bearing for the Phase-3 boundary (Decision 6).
- **Hashing is raw-byte, `shasum -a 256`-equivalent** (`hashlib.sha256` over
  bytes read in binary mode). This matches the existing gallery trust chain —
  `scripts/check-gallery-entry.sh` (shasum) and
  `URLSessionGalleryService.fetchScenarioYAML(from:expectedSHA256:)` — and is
  explicitly **not** `scripts/jsonl_to_demo_replay.py`'s `sha256_hex`, which
  hashes UTF-8 *text* (newline-translating) because its consumer is the
  demo-replay drift check. The two conventions serve different trust roots;
  the extractor documents which one it serves.
- **Staleness is a repo-side concern**: a highlight whose
  `scenario_ref.yaml_sha256` no longer matches `gallery.json`'s entry fails
  the gallery gate (Decision 2) at commit/CI time. Consumers do not
  re-derive staleness — they verify content hashes against the index
  (Decision 4) and trust the gate for freshness.

### 2. Generation pipeline — harness in, audited JSON out

`scripts/gallery_highlight_extract.py` converts a pastura-harness JSONL
transcript (`run_start` / `event` / `run_end` lines, ADR-013) plus a curated
turn selection into a schema-valid highlight file. Non-negotiable properties:

- **Curation is human judgment; extraction is mechanical.** The tool never
  chooses excerpts — it slices, validates, pins hashes, and audits. Manual
  curation is a deliberate constraint, not a missing feature: spoiler and
  quality judgment are taste calls the blocklist audit cannot make (the audit
  is necessary, not sufficient), and each batch also gets an explicit human
  sign-off before commit.
- **Content-safety audit built in**: every published string (`excerpt[].text`,
  `yaml_hook`, `teaser`) is checked against the terms in
  `ContentBlocklist.json` (`patterns[].term` — what
  `ContentBlocklist.outputPatterns` exposes on the Swift side; schema per
  ADR-005 §4.4/§5.2), with the same match semantics the demo-replay
  procedure pins: case- and diacritic-insensitive substring, all categories.
  `content_filter_applied: true` attests the pass — the attestation-flag
  precedent is `scripts/jsonl_to_demo_replay.py`'s `--filter-applied` header
  procedure. The web surface has no runtime `ContentFilter`, so publish-time
  audit is the only filter it gets.
- **Hard-fail on the untested branch**: if the scenario YAML declares the
  secret mechanism (`secret:` persona fields), the extractor refuses. Zero
  gallery entries use it today (only the bundled `souzoku_kaigi*` presets do),
  so the spoiler rules below are unvalidated for it; refusing keeps the gap
  loud instead of silently shipping a spoiler.
- **Hard-fail on unknown phase names**: a transcript phase outside the
  `PhaseType` catalog at the extractor's last sync means a new phase type
  landed (ADR-022 extension contract) — its visibility and outcome
  classification (Decision 3) must be assigned before the tool runs again.
  ADR-022's compile-time gates cannot see this file, so the extractor carries
  its own tripwire.
- **The gate, not the extractor, is the enforcement point.** A hand-edited
  `highlights/<id>.json` never runs the extractor, so every rule that only
  lives there is bypassable. `scripts/gallery-precommit-gate.sh`'s trigger
  regex is relaxed (its own header pre-authorizes exactly this) and
  `scripts/check-gallery-entry.sh` re-derives, per highlight: schema
  (including the `excerpt` cap and `source_field` allowlist), sha freshness
  against the sibling YAML and `gallery.json`, the
  `highlight_url` ⟺ `highlight_sha256` ⟺ file three-way pairing
  (Decision 4) — stated so it also catches the inverse orphan: a
  `highlights/<id>.json` **not referenced by a paired
  `highlight_url`/`highlight_sha256` entry fails**, whether the id is absent
  from `gallery.json` or present without the fields — plus the spoiler
  mechanics of Decision 3 (phase eligibility and the within-round bound
  checked via `phase_index` against the entry's `phases` list — the index
  must name an eligible phase with no outcome-class phase before it — and
  the round window recomputed from `gallery.json`'s `rounds` honoring
  `window_override`) and the blocklist re-audit. The extractor keeps the same
  checks as fail-fast convenience; the gate's copies run ungated in CI. The
  web build trusts the gate rather than re-validating (it builds from repo
  state that passed it).
- One mechanical note: harness `agent_output` lines carry no `round` field —
  the extractor derives it from the preceding `round_started` line.

### 3. Spoiler policy — keyed to event visibility, not phase position

The full `PhaseType` catalog (`Pastura/Pastura/Models/PhaseType.swift`):
speak_all, speak_each, vote, choose, reflect, whisper, score_calc, assign,
eliminate, summarize, conditional, event_inject, relationship_update, narrate.

- **Excerpt-eligible events: a persona's public, in-fiction utterance** —
  `speak_all` / `speak_each` output, and within it the **`statement` field
  only** (the `source_field` allowlist in Decision 1; speak phases also emit
  `inner_thought`, so field-level selection must be recorded to be
  checkable). Every other phase's output is ineligible, in any round and at
  any position:
  - **Outcome disclosures** — `vote`, `eliminate`, `score_calc`, `choose`,
    `summarize` results, interim or final.
  - **Private in-fiction content** — `reflect` output (a private memo,
    never appended to `conversationLog`; see `ReflectHandler`'s doc comment),
    `whisper`-phase messages, and `inner_thought` fields from any phase.
    Hidden agendas surface there first.
  - **Out-of-fiction commentary** — `narrate`. It is not a persona's
    utterance; the narrator prompt template gets `{scoreboard}` injected, so
    author-supplied prompts make it structurally outcome-disclosing; no
    gallery entry uses it today; and a narration line carries no `agent`, so
    the excerpt schema cannot even represent one. Designed-untested like the
    secret branch: the extractor refuses `narrate` excerpts until a
    narrate-bearing gallery entry motivates designing them.
  - **Setup and control flow** — `assign` (its distributed values are
    additionally banned from captions and teaser, not just excerpts: a hidden
    role is a spoiler wherever it appears), `conditional`,
    `relationship_update`, and `event_inject` (a mid-run twist is
    spoiler-adjacent; excluded conservatively).
- **Position rule, two parts.** The engine runs the phase list once per
  round, so per-round `summarize` — present in all 45 gallery entries —
  makes any single whole-run cutoff useless; position must be judged both
  within and across rounds:
  1. **Within a round**: an utterance is eligible only if no outcome-class
     phase precedes it in that round's phase list. Dialogue *reacting to* an
     in-round outcome is how outcomes leak even when the outcome event itself
     is excluded (`detective_scene_v1`'s post-vote `speak_each` is the live
     case).
  2. **Across rounds**: default window is rounds 1 through ⌈N/2⌉. The
     extractor accepts later-round utterances only behind an explicit
     override flag, which is recorded in the file as
     `window_override: true` so the sign-off stays auditable; the
     within-round bound applies regardless. Every excerpt — windowed or
     overridden — passes the human sign-off from Decision 2.
- **Feasibility, measured at `3a056fc0`**: under the two-part rule, 24 of 27
  ja entries (40 of 45 overall) have a non-empty eligible set. The 5 that do
  not — `tengoku_jigoku_v1`, `chinwaza_saiyo_v1`, their `_en` siblings (pure
  assign/choose/vote/score_calc/summarize scenarios), and `share_house_v1`
  (its phase list opens with `summarize`, so no dialogue precedes an
  outcome-class phase in any round) — are **not excerptable under this
  policy and get no highlight**, rather than an outcome-leaking one.
- **The ending is teased, not shown.** `teaser` is one line and must not state
  the outcome. Full-transcript publication (collapsed, non-secret categories
  only) is recorded as a **future option**, not part of this decision.
- The secret-mechanism branch of this policy is **untested** (no gallery
  entry exercises it) and mechanically unreachable via Decision 2's
  hard-fail until it is designed for real.

### 4. App-side trust model — the index stays the single trust root

- `gallery.json` entries gain two optional fields, **both-or-neither**
  (gate-validated): **`highlight_url`** — declared like `yaml_url`, resolved
  against the same base (including the DEBUG `PASTURA_GALLERY_BASE_URL`
  override), so the path is index-declared rather than convention-derived —
  and **`highlight_sha256`**, the raw-byte hash of the highlight file.
- **Fetch is unconditional, size-limited, and hash-verified** — the same
  shape as `fetchScenarioYAML(from:expectedSHA256:)`. **No ETag sidecar and
  no persistent cache**: per-entry gallery artifacts have never been cached
  (only the index is, with its `gallery.json.etag` sidecar), the file is
  small and fetched only when the detail screen shows, and inventing a new
  per-entry cache layer is not this feature's job. Revisit if detail-screen
  traffic ever makes the refetch wasteful.
- **`highlightSizeLimit` = 65,536 bytes (64 KiB)**, alongside the existing
  `indexSizeLimit` (1 MiB) and `yamlSizeLimit` (256 KiB) in
  `URLSessionGalleryService`. An excerpt is a few KB; the limit is a defense
  bound, not a design target.
- **Verification failures hide the section.** Hash mismatch, size overflow,
  unparseable JSON, unknown `schema_version`, or `content_filter_applied`
  absent/false — all render as "no highlight", never as a warning. Rationale:
  a security warning the user can't act on is worse than absence, and the
  repo-side gate keeps legitimate mismatch windows short (CDN propagation
  between an index update and its highlight). The failure must not be
  *silent to developers*, though: log an `.info`-level Logger line naming
  the failed check, annotated `privacy: .public` — the check name is a
  static literal, not user content, and `.info` (unlike `.debug`) survives
  into TestFlight/Release where a field failure would need diagnosing.

### 5. Web rendering — shared component, both locales

- **The web build reads `docs/gallery/highlights/<id>.json` directly from
  repo state** (which passed the gate) — it does not resolve
  `highlight_url`, which exists solely for the app's index-anchored fetch.
  The gate's pairing rule (Decision 2) is what keeps the two surfaces
  agreeing on whether a highlight exists.
- The highlight section lives in `web/src/components/ScenarioLanding.astro`,
  shared by `/s/[id]` and `/ja/s/[id]`. It renders on **both** routes
  regardless of the scenario's `language`, following the component's existing
  "the title is user content" precedent — a ja highlight under en chrome is
  labeled content, not a bug. Chrome strings (section headings, captions, CTA)
  are added to the component's `t` dictionary in **both ja and en** even
  while highlight content is ja-only.
- The edit-invitation CTA is worded **open-in-app-and-edit**. It must not
  imply submitting a scenario back to the gallery — user submissions are the
  Phase 3 marketplace (ROADMAP).
- Scenarios without a highlight file render exactly as before.

### 6. Phase-3 boundary

ROADMAP defers "Replay gallery / Shared Scenarios integration" to Phase 3.
Highlights stay outside that deferral **only if all of** (necessary
conditions — meeting them does not automatically clear other Phase-3
deferrals):

- no execution, playback, seek, or event-stream — static text only; nothing
  constructs a replay source (`YAMLReplaySource` or successors) or feeds
  events into the simulation UI;
- consumption is a static file read: build-time on web, a single
  hash-verified fetch per display in the app — no streaming or incremental
  delivery;
- the excerpt is a fixed authored enumeration (schema-capped at 8 entries,
  Decision 1) that does not scale with run length or round count;
- no community function rides along: no submission, rating, or listing of
  user-created content (that is the Phase 3 marketplace regardless of how
  static its rendering would be).

Of the four, only the excerpt cap is mechanically enforced (schema +
gate); the other three are review-time obligations on any diff touching
this feature. A change that violates any bullet is Phase-3 work and stops
at the roadmap. The ROADMAP row carrying the deferral gets a one-line
pointer to this boundary so the next reader does not re-litigate it.

### 7. Rollout — ja first

Initial content: 2–3 featured ja scenarios. ja goes first because curation is
the bottleneck and it requires native-quality reading of nuance — the ja
inventory is the field-tested one. English highlights additionally require
separate en runs — ja transcript quality does not transfer to en at either
the prompt or sampler layer — so en is a later, separately-generated batch,
not a translation task.

## Options considered

| Option | Verdict |
|--------|---------|
| **Embed highlights inside `gallery.json`** | Rejected. The index is fetched by every app session (1 MiB cap, ETag-cached); multi-KB excerpt bodies would bloat it for users who never open a detail screen. Sibling files keep the index a manifest. (Index *churn* does not discriminate: the chosen option's `highlight_sha256` also touches the index on every content edit.) |
| **Sibling files + `highlight_url`/`highlight_sha256` in the index** (chosen) | Costs: one extra fetch on the detail screen, a three-way pairing (index fields ⟺ file) the gate must police, and a new artifact class every gallery edit has to consider. Accepted for keeping the index the single trust root at two optional fields per entry. |
| **Full transcript publication** | Deferred, recorded as a future option for non-secret categories. It maximizes web-side content (and search surface) but removes the in-app payoff for outcome-driven scenarios, and the near-determinism argument cuts per-model, not universally (models are runtime-selectable; LiteRT-LM migration will shift outputs). |
| **Trust by TLS + same-host only (no index hash)** | Rejected. It would make highlights the only gallery artifact whose content the app cannot verify against the index, and the parallel implementation session would inherit an open question instead of a decision. |
| **Locale-gated rendering (`language === locale`)** | Not chosen. The shared component's design intentionally shows user content in its own language under either chrome; gating would fork the two routes' markup for the first time. Cheap to revisit — it is one conditional. |

## Consequences

- The gallery gains a second artifact class. `check-gallery-entry.sh` and the
  pre-commit gate must know about `highlights/`; the gate's trigger regex
  relaxation is the pre-authorized one from its own header comment.
- `deploy-pages.yml` and `web-check.yml` gain `docs/gallery/gallery.json` +
  `docs/gallery/highlights/**` trigger paths — narrowed to the build's actual
  inputs. This also closes a pre-existing hole: a `gallery.json`-only commit
  previously deployed nothing (and was never build-checked at PR time),
  because both workflows watched `web/**` only.
- **The spoiler policy bounds supply.** 5 of 45 entries are un-excerptable by
  design (Decision 3's measured feasibility), and the two-part position rule
  bounds how much of the rest is quotable. That is the accepted price of a
  policy that fails closed; scenarios it excludes simply keep today's
  landing page.
- Highlights are **pinned snapshots**: scenario version via
  `scenario_ref.yaml_sha256`, generation context via `source.model`. Editing
  a gallery YAML now obligates regenerating (or deleting) its highlight —
  enforced by the gate, paid by the editor.
- The app-side implementation (follow-up issue) starts from fixed decisions:
  index-declared URL + hash, unconditional verified fetch, no cache,
  hide-plus-info-log on any verification failure, size limit, spoiler rules.
  Divergence from these is an ADR amendment, not a per-PR choice.
- en landing pages may show ja highlight content under en chrome (labeled).
  Accepted trade-off; revisit is one conditional (see Options).
- Curation cost is real and recurring: each highlight needs a harness run, a
  human excerpt selection, a blocklist audit, and a sign-off. This is why the
  initial batch is 2–3 scenarios, not 45.

## Revisit trigger

- **A new `PhaseType` case lands** → classify its output's visibility
  (public / private) and outcome-disclosure status in Decision 3 before the
  extractor accepts transcripts containing it. The unknown-phase hard-fail
  makes this mechanical for highlight-bearing runs; ADR-022's cross-cutting
  note covers the manual re-check.
- **A secret-mechanism scenario is proposed for the gallery** → design and
  test the secret branch of the spoiler policy first; then lift the
  extractor's hard-fail. Until then the branch stays documented-untested.
- **A narrate-bearing gallery entry lands** → design narrate eligibility
  before excerpting it: attribution (no `agent` on narration lines), the
  `{scoreboard}` outcome-disclosure constraint, and schema representation.
  Same designed-untested posture as the secret branch.
- **A second consumption surface wants richer data** (full-transcript
  collapse, replay integration) → that is the Phase-3 boundary in Decision 6;
  it goes through the roadmap, not through widening this schema.
- **en highlight batch** → new generation runs per Decision 7; no schema
  change expected (`excerpt[].text` language follows the scenario entry's
  `language`).
- **No observable pull after the initial batch has been live for ~a quarter**
  (no highlight-attributable lift in landing→install interest, en batch still
  not worth starting) → reconsider the feature before expanding it; the
  recurring curation cost in Consequences is only justified while highlights
  earn attention.
- **Detail-screen traffic makes the uncached fetch wasteful** → add the
  per-entry cache layer Decision 4 deliberately omitted.
