# ADR-017: Simulation Focus Mode & Deferred Cross-Screen Continuation

> **Status:** Accepted
> **Date:** 2026-06-18
> **Context:** After the bottom-tab IA shipped ([ADR-016](ADR-016.md),
> #602), switching tabs while a simulation runs **cancels the run and
> resets it to round 1** on return (#646). The run is owned by
> `SimulationView`'s view-scoped `@State` and driven by `.task`; a tab
> switch makes the hosting tab's content disappear → `.task` cancels →
> `runTask.cancel()` → on return `.task` re-fires `loadAndRun()` → a fresh
> `SimulationViewModel` restarts from the top. PR #675 (#673) made that
> teardown *lossless* (a `.paused` row survives via the terminal ladder),
> but it did not stop the restart. #646's issue body proposed the
> heavyweight fix — lifting run ownership above the per-tab view. This ADR
> records a deliberately lighter posture for **Phase A** and defers the
> ownership lift to **Phase B**.

---

## 1. Decision

### D1. Simulation focus mode — hide the tab bar during a run

While `SimulationView` is on top of a tab's stack, hide the bottom tab bar
with `.toolbar(.hidden, for: .tabBar)`. The modifier is applied to the
whole view, so it covers **both** the `.simulation` and `.resumeSimulation`
routes (both resolve to `SimulationView` via `RouteResolver`).

Consequence: there is **no tab affordance** during a run, so a foreground
tab switch — the only path that tore the view-scoped run down and reset it
— **cannot be triggered**. #646 is resolved by *removing the trigger*, not
by making the run survive the switch. Run ownership stays view-scoped and
the `cancel-on-disappear` invariant (one shared-`LLMService` `run()` at a
time) is preserved unchanged.

### D2. `.tabBar` is a separate toolbar surface from the navigationBar matrix

The toolbar-hide trap matrix in
[`.claude/rules/swiftui-traps.md`](../../.claude/rules/swiftui-traps.md)
is **navigationBar-only**: `.toolbar(.hidden, for: .navigationBar)` (and
`.navigationBarBackButtonHidden(true)` on iOS 26) disable the
`interactivePopGestureRecognizer`. `.toolbar(.hidden, for: .tabBar)` is a
**different placement** and does **not** touch the back chevron or the
swipe-back gesture. Verified empirically: the focus-mode UI test
(`SimulationFocusModeTests`) pops the simulation via an interactive
edge-swipe *after* the modifier is applied, and the swipe-back succeeds.
The iOS-26 *visual* of the hide/restore transition (Liquid Glass
flicker / half-render) is **not** simulator-load-bearing and is gated on
real-device QA (the #646 C-1 gate).

### D3. Exits and the confirm-on-leave machinery

The only exits from a focused run stay **back-button** and **swipe-back**,
both in-stack pops on the current tab's `AppRouter`. The back-button
confirm-on-leave dialog (#673, `PendingLeave.back`) and the swipe-back
`.paused` terminal-ladder safety net are unchanged.

The PR #673 **tab-switch** defer machinery
(`TabCoordinator.hasUnsavedInFlightRun` / `pendingTabSwitch` /
`commitPendingTabSwitch` / `cancelPendingTabSwitch`, and the `.tab`
`PendingLeave` arm) becomes **structurally unreachable** under focus mode:
its sole reader is `TabCoordinator.handleSelection(_:)`, which only fires
from the native tab bar's selection binding — and the bar is hidden. It is
**removed** (no dormant code, per ADR-016 D4's discipline). The
`shouldGuardLeave` predicate and its unit tests survive — they still back
the kept `.back` arm.

### D4. #646 acceptance-criteria reinterpretation

| #646 AC | Phase A disposition |
|---|---|
| #1 — tab switch does not cancel/reset the run | **Satisfied** — tab switch is impossible during a run. |
| #2 — returning to the sim tab shows live in-flight state | **Superseded** — there is no tab-switch-and-return under focus mode; this capability moves to Phase B. |
| #3 — single-active-`run()` invariant preserved | **Satisfied** — run stays view-scoped; cancel-on-disappear unchanged. |
| #4 — verified on real devices (iOS 17–26) | **Required** — the C-1 device-QA gate. |

**#646 closes with Phase A.** The ownership lift its body proposed is
re-scoped to Phase B (a separate issue).

### D5. `isSimulationOnTop` any-tab fold is retained

`TabCoordinator.isSimulationOnTop` folds `path.last == .simulation /
.resumeSimulation` over **all four** routers and gates the deep-link drain
+ warm-splash suppression. Focus mode blocks multi-tab **switching**, but
the fold's correctness rests on multi-tab **hosting** — a simulation can be
the top of any single tab's stack (Search run, Home-resume, History-resume)
— and on the **scenePhase-background** path (app backgrounded, [ADR-003](ADR-003.md)),
neither of which focus mode removes. The fold **stays** and must not narrow.
The justification is re-anchored in [ADR-016 § Amendment 2026-06-18](ADR-016.md).

### D6. Phase B — opt-in cross-screen continuation (deferred)

When a user genuinely wants the run to continue while they use another
screen, expose it as an **opt-in**: a Setting ("keep the simulation running
when I leave the screen") **or** a per-leave choice (a third dialog option,
"leave & keep running", alongside "pause & leave" / "stay"). When active,
leaving the sim screen keeps the run progressing and re-shows the tab bar.

Phase B is genuinely heavier and is **not** implemented here:

- **Ownership lift.** The run must move from `SimulationView`'s `@State` to
  an app-level live owner (e.g. a `SimulationSession` held by
  `TabCoordinator` / `AppDependencies`) so it survives view teardown.
- **Hard single-run guard.** Today the one-`run()`-per-shared-`LLMService`
  invariant is enforced *only* by cancel-on-disappear (a new
  `SimulationView` cannot start while the old one's `runTask` is still
  cancelling). `SimulationActivityRegistry` is **observational** — its sole
  consumer is the Settings model-switch lock. Lifting ownership removes
  cancel-on-disappear, so Phase B must promote the invariant to a real
  start-time guard.
- **In-flight indicator must be built.** There is **no** existing
  in-flight indicator UI on non-simulation screens to reuse — `isActive`
  has exactly one consumer (the Settings model-switch lock). Phase B builds
  the indicator from scratch (driven by `simulationActivityRegistry.isActive`).

**Resurface trigger (load-bearing).** Phase A's "prevent the trigger"
holds only while no feature needs background tab activity *during* a run.
The moment one does — a notifications drawer, a "compare two runs" flow, a
multi-run queue, any cross-tab surface meant to coexist with a live sim —
focus mode's premise breaks and Phase B's ownership lift is **forced**.
This is recorded so a future contributor does not "fix" focus mode by
re-hiding more chrome when the real need is the lift. (It also means a
future contributor should **not** delete the retained `isSimulationOnTop`
any-tab fold (D5) as "now redundant" — Phase B re-loads it.)

## 2. Why this shape

**Prevent-the-trigger over solve-the-mechanism.** Making a view-scoped run
survive a tab switch requires inverting ownership (app-level live session)
and replacing the cancel-on-disappear safety with a hard mutex — a large,
cross-cutting change to load-bearing, well-tested code. Hiding the tab bar
is one modifier with a blast radius of a single view plus a dead-code
removal. For the *observed* user need (don't lose my run when I glance at
another tab), removing the glance affordance during a run is sufficient and
far cheaper.

**Product intent.** The simulation screen is meant to be watched — the live
log, typing, thinking indicators, tok/s. Hiding the tab bar yields an
immersive, lower-noise surface the user commits to, consistent with the
"depth over first-impression polish" product posture. A run is a bounded
activity with a clear exit (back), not a place to multitask from.

**Coherent without Phase B.** Phase A alone is shippable: focus mode +
back-confirm (lossless `.paused`) means leaving is never data loss, only an
explicit, confirmed exit. The only gap is *expectation* — a user who wanted
to multitask must wait or back out — which Phase B fills additively.

## 3. Consequences & relations to existing ADRs

- **[ADR-016](ADR-016.md) (bottom-tab IA)** — amended (§ Amendment
  2026-06-18) to re-anchor the `isSimulationOnTop` fold on multi-tab
  *hosting* + scenePhase-background rather than tab-switch backgrounding
  (which focus mode makes impossible). The fold is unchanged in code.
- **[ADR-003](ADR-003.md) (BG execution)** — orthogonal. App-background
  (`scenePhase = .background`, home button / app switcher) is a *different*
  lifecycle event from a foreground tab switch: it does **not** fire
  `onDisappear`, so the `BGContinuedProcessingTask` + `SuspendController`
  continuation path is untouched by focus mode. A run still continues (or
  parks) across app-background exactly as before.
- **[`.claude/rules/navigation.md`](../../.claude/rules/navigation.md)** —
  updated with the focus-mode posture + a PR-review-checklist line.
- **[`.claude/rules/swiftui-traps.md`](../../.claude/rules/swiftui-traps.md)**
  — its hide matrix remains navigationBar-scoped; D2 records that `.tabBar`
  is out of that matrix's scope.

## 4. Alternatives considered (all re-scoped to Phase B)

These were evaluated as the *direct* "make the run continue across tabs"
fixes and deferred behind the opt-in (D6):

- **Lift ownership, keep inference running off-screen.** True D5.4-style
  continuation, but runs full GPU inference with no visible output during a
  foreground tab switch — questionable battery/thermal cost and exposed to
  iOS foreground throttling.
- **Warm checkpoint-resume (no lift).** On tab switch, tear down + save
  `.paused`, then resume from the last round checkpoint on return. Smallest
  blast radius of the three, but continuity is **round-granular** (mid-round
  turns are pruned and re-run) and return pays a model-reload + resume
  latency. Contradicts "live in-flight on return".
- **Lift ownership + `SuspendController` park-on-hide.** Best fidelity —
  in-memory state preserved (instant reconnect, no lost progress, mid-generate
  park via the existing ADR-003 mechanism) with no off-screen GPU. Carries
  the ownership-lift blast radius plus a second suspend trigger (view-hide
  alongside scenePhase) whose composition must be designed.

Phase A chose **focus mode** over all three: it resolves #646's user-visible
AC at a fraction of the cost, and the opt-in (D6) reaches for one of these
only for the users who explicitly want cross-screen continuation.
