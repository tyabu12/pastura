# ADR-022: Scenario Semantic Lint Layer — surfacing silent no-ops at load time

- **Status**: Accepted
- **Issue**: #994
- **Date**: 2026-07-08

## 1. Context

The scenario DSL has accumulated semantic constraints that are *documented, not
enforced* — a scenario that violates them parses, validates, and runs to
`status=ok` while silently doing the wrong thing. Known classes:

- **Producer–consumer phase ordering**: `eliminate` needs a `vote` earlier in the
  round (`EliminateHandler` silently no-ops on empty `voteResults`, and — because
  `SimulationRunner`'s per-round reset clears only `conversationLog`/`pairings` —
  a mis-ordered `eliminate` runs on the *previous round's* tally).
  `score_calc` logics have analogous hidden dependencies (`prisoners_dilemma` →
  round-robin `choose`; `wordwolf_judge` → `assign random_one` + `vote`;
  `event_reactive` → dict-shaped `event_inject` with default `as:`;
  `vote_tally` → `vote`). `relationship_update` placement was documented in
  `.claude/rules/engine.md` as "documented, not enforced — a violation is a
  silent no-op".
- **Silently-inert configuration**: `choose` without `options` leaves the action
  unconstrained; an empty `assign` source list silently assigns nothing / `""`
  (the validator shape-checks `assign` but did not emptiness-check it, unlike
  `event_inject`).
- **Placeholder resolution**: `PromptBuilder.expandTemplate` leaves unknown
  `{placeholders}` verbatim, and per-phase availability (`{candidates}` is
  vote-only, `{opponent_name}` is choose-round-robin-only, …) was modeled
  nowhere the author could hit at load time (#920, #862/#890 history).
- **Condition expressions**: `ConditionEvaluator` only treats `"` as a string
  delimiter — `vote_winner == 'Alice'` resolves `'Alice'` as an (absent)
  identifier and silently takes the else branch with `status=ok`. Bare
  identifiers that are typos or persona names behave the same way. Short-circuit
  evaluation additionally hides typos in never-evaluated sub-expressions.
- **Log window**: `log_window < agentCount` truncates same-round earlier
  speakers out of `speak_each` prompts (documented in engine.md only).

As the shared-scenario gallery grows, the cost of "someone else's YAML is
quietly wrong" grows with it. Runtime `.summary` warnings (the only existing
non-fatal channel besides the inference-count warning) fire mid-run — too late
for an author, and invisible to a gallery curator.

### Existing gates this must coexist with

| Gate | Nature | Lane |
|---|---|---|
| `ScenarioLoader.load` | throwing parse; **non-validating** (#665 boundary) | structure / type mapping |
| `ScenarioValidator.validate/-ForCommit` | throwing, fail-fast, single error | hard structural limits & phase shapes |
| `ScenarioValidator+EventInject` | intentional curator leniency: shape/reachability only, never content taste | structural |
| `ScenarioContentValidator` (App) | findings array, blocklist content screening (ADR-005) | content safety |
| ADR-020 compat gate | capability/version (`phases ⊄ PhaseType.allCases`, `min_engine_version`), pre-download | can this engine run it at all |

## 2. Decision

### D1 — New `ScenarioSemanticLinter` (Engine layer), findings-based

A `nonisolated public struct ScenarioSemanticLinter` in `Engine/`, separate from
`ScenarioValidator`:

```swift
public func lint(_ scenario: Scenario) -> [LintFinding]
// LintFinding: ruleID (stable), severity (.error/.warning/.info, Comparable),
//              message (String(localized:), ruleID-prefixed + fix hint),
//              phaseIndex (Int?, nil = scenario-level)
```

**Why not extend `ScenarioValidator`**: its contract is fail-fast single-error
throwing, consumed at four call sites that expect exactly that; retrofitting
multi-finding severity semantics would change every call site's error handling.
The findings-array shape follows the `ScenarioContentValidator` precedent.
`ScenarioValidator` stays frozen — all new rules live in the linter, even ones
(like assign-emptiness) that would fit the validator's style, so there is one
place to look for semantic rules and the validator's fail-fast contract never
gains severity nuance. (`ScenarioValidator` was widened `internal → public`
for cross-module reuse by the harness `lint` subcommand — an access change
only, mirroring the already-`public` `ScenarioLoader`.)

Rule groups live in sibling `nonisolated extension` files
(`+Ordering` / `+Config` / `+Placeholders` / `+Conditions`), mirroring the
`ScenarioValidator+X.swift` convention; tests mirror 1:1.

### D2 — Severity contract (the three-tier boundary)

- **`.error`** — statically provable that, as authored, a phase can never take
  effect or a branch can never be selected (guaranteed silent no-op or
  guaranteed-wrong semantics; no deliberate-authoring reading exists).
  Blocking: treated with the same strength as `ScenarioValidator` errors at the
  commit gate (editor Save) and the run gate (`SimulationRunner`).
- **`.warning`** — probably unintended, but a deliberate reading exists
  (stale-value ordering that a curator might exploit, log-window truncation,
  placeholder availability where injection paths are conditional). Never
  blocks. Surfaced at run start through the existing `.summary("⚠️ …")` event
  channel alongside the inference-count warning (editor findings display is
  the follow-up PR's scope).
- **`.info`** — advisory only. The tier exists so future rules don't get
  force-fitted into warning; v1 ships zero firing info rules (see R16).

**Rule-addition / promotion policy** (the "ran yesterday, errors today" guard):
v1's error rules block from day one *because* the zero-false-positive batch
run over the full shipped inventory was a merge prerequisite (§ D6). Any rule
added or promoted to `.error` after v1 ships as `.warning` for at least one
release, and promotes only after (a) the D6 batch gate passes and (b) a release
of field observation surfaces no false positives. Error findings always carry
their `ruleID` and a fix hint, so a blocked scenario is actionable, not a dead
end. (ADR-020 solved the sibling "engine changed under installed content"
problem with `min_engine_version`; the linter's equivalent safety is this
warn-first window — lint errors are about content that was *never* doing what
it claimed, so blocking with guidance beats silently burning minutes of
on-device inference.)

**Leniency boundary** (per `ScenarioValidator+EventInject`'s curator-leniency
doc): the linter judges *reachability and effect*, never content quality,
thematic fit, or style. It must not re-flag anything the structural validator
already accepts as a deliberate curator choice (e.g. a single-event
`event_inject` list) nor anything ADR-020's compat gate owns (unknown phase
types / enum values never materialize as a `Scenario`, so the linter cannot see
them by construction).

### D3 — Rule catalog v1

IDs are stable. "engine.md" marks constraints that were documented before
enforcement existed.

| ID | Rule (violation → pre-linter behavior) | Sev | engine.md |
|---|---|---|---|
| R1a `eliminate-needs-vote` | `eliminate` with no `vote` anywhere → silent no-op | error | — |
| R1b `eliminate-after-vote` | `eliminate` ordered before the `vote` → runs on prior-round tally | warning | — |
| R2 `pd-needs-round-robin-choose` | `score_calc: prisoners_dilemma` without a preceding round-robin `choose` → empty pairings, scores never change | error | — |
| R3 `wordwolf-needs-assign-and-vote` | `score_calc: wordwolf_judge` without `assign random_one` + `vote` earlier → judges `"?"` / no-op | error | — |
| R4 `relationship-update-placement` | not (after its vote/choose producer, before a pairings-clearing `prisoners_dilemma` `score_calc`, no `lastOutputs`-overwriting speak/choose between the vote and it; `reflect`/`whisper` safe) → silent no-op | warning | ✓ |
| R5 `event-reactive-needs-event-inject` | `score_calc: event_reactive` without dict-shaped `event_inject` keeping default `as:` → favored var never written, zero reward | error | — |
| R6 `vote-tally-needs-vote` | `score_calc: vote_tally` with no `vote` earlier → no-op or re-adds stale tally | warning | — |
| R7 `choose-should-declare-options` | `choose` without `options` → unconstrained free-text action | warning | — |
| R8 `assign-source-nonempty` | empty `assign` source list → nothing assigned / all `""` | error | — |
| R9 `summarize-pairing-placeholders` | `{agent1}`-family in `summarize` template without round-robin `choose` → literal braces in output | warning | — |
| R10 `unresolvable-placeholder` | `{token}` not in engine-supplied set ∪ reserved prefixes ∪ declared keys → literal passthrough to the LLM prompt | warning | — |
| R11 `placeholder-phase-availability` | producer-gated placeholder used with no producer at an earlier-or-same index → empty/stale | warning | — |
| R12 `per-persona-placeholder-in-summarize` | `{assigned}`/`{my_notes}`/etc. in `summarize` (no `inject*` there) → literal passthrough | warning | — |
| R13 `single-quoted-literal-in-condition` | `'Alice'` in `if:` tokenizes as identifier → always-else | error | — |
| R14 `bare-identifier-looks-like-literal` | unquoted operand matching a persona name (`vote_winner == Alice`) → always-else | error | — |
| R15 `unknown-condition-identifier` | identifier ∉ known set (below) → resolves absent, warning only mid-run | warning | — |
| R16 `short-circuit-hidden-typo` | typo in a never-evaluated `&&`/`||` sub-expression never surfaces at runtime | info (documented no-op) | ✓ (evaluator doc) |
| R17 `log-window-below-agent-count` | `log_window < agentCount` with `speak_each` present → same-round speakers vanish from prompts | warning | — (engine.md documents the trap) |

Ordering semantics (R1–R6, R11): compare **top-level phase-list indices**;
producers inside `conditional` branches count at the conditional's index
(may-run suffices), and a producer at the **same** index as a branch-nested
consumer counts as satisfied (`<=` — a producer→consumer pair ordered inside
one branch shares the conditional's index; strict `<` false-positived on
gallery `kasei_sanso_touban`). Known imprecision, accepted to avoid false
positives. No runtime behavior changes anywhere — the never-reset
`voteResults`/`lastOutputs` staleness stays as-is and is linted around, not
fixed (same posture as #920's "guard + hint only" scope).

**Rule-precision notes** (false-positive guards found at design review and
batch verification):

- **R15 known-identifier set** = derived vars (`current_round`, `total_rounds`,
  `eliminated_count`, `active_count`, `max_score`, `min_score`, `vote_winner`)
  ∪ `scores.<persona>` ∪ declared `extraData` keys ∪ **engine-injected
  reserved state-variable names** (`wolf_name`, `vote_results`,
  `assigned_topic`, per-persona `assigned_/notes_/whispers_/relationships_<name>`
  forms, and each `event_inject` event variable — default `current_event` or
  custom `as:` — plus its `__favors` companion). Without the reserved names,
  shipped `word_wolf.yaml` (`vote_winner == wolf_name`, `current_event != ""`)
  would fire day-one false positives. Prompt-only tokens (`scoreboard`,
  `candidates`, `my_notes`, …) are deliberately NOT condition identifiers.
- **R13 inspects the parsed `phase.condition`**, never raw YAML text — YAML
  scalar quoting (`if: 'current_event != ""'` in word_wolf) is stripped by the
  parser; a raw-text grep would false-positive on it.
- **R14 is the persona-name match only** (comparison operand that is an unknown
  identifier AND exactly matches a persona name → error). All other unknown
  identifiers are R15's lane — one token yields one finding, no double-fire.
- **R10/R11/R12 are one classifying scan** with precedence R12 > R11 > R10 per
  distinct token per phase (single-fire). The token pattern is
  identifier-only (`\{[A-Za-z_][A-Za-z0-9_]*\}`), so JSON examples in prompts
  (`{"statement": …}`) never match. `{vote_winner}` is *not* a prompt
  placeholder (derived condition var, never in `state.variables`) — R10
  catching it in gallery `detective_scene` was a true positive.
- **R8's predicate mirrors `AssignHandler`'s shape branches**: `random_one`
  needs non-empty `.arrayOfDictionaries`; `all` needs non-empty `.array` *or*
  a `.string` source (a single-string source is legitimate, not empty).
- **R7 stays uniformly warning** (no escalation when a `prisoners_dilemma`
  score_calc consumes the choose): with `options` absent the prompt may still
  elicit `cooperate`/`betray` from its own wording, so "wrong" is probable,
  not statically provable — unlike R2, where empty `pairings` gives
  `PrisonersDilemmaLogic` literally nothing to iterate.
- **R16 is implemented as a documented no-op**: R13–R15 walk the full parsed
  AST, statically resolving BOTH sides of every `&&`/`||` — which already
  surfaces the typo the runtime's short-circuit walker hides. A *separate*
  info finding would require constant-folding runtime state absent at lint
  time. The rule ID is reserved; the no-op rationale lives in the code.

### D4 — #920 absorption: availability map is linter-owned

The per-phase placeholder availability map (R10–R12's data) is a single source
of truth owned by the lint layer (`PlaceholderAvailability`, Engine):
`PhaseType`-keyed supplied sets **plus one narrow qualifier** for the only
known intra-phase split (`choose` round-robin vs individual — round-robin
additionally supplies `{opponent_name}` and, matching a real handler
asymmetry, the whisper channel), resolving #920's open model-shape question in
favor of "PhaseType key + narrow qualifier" rather than a full descriptor
type. A producer relation (`producers(of:)`) covers the R11 ordering facet.

- The map's union is asserted in tests against `PromptPlaceholders.engineSupplied`
  **plus an explicit named delta** (`tokensBeyondEngineSupplied`, 10 genuinely
  handler-injected tokens the curated coverage-guard subset never registered —
  `my_notes`, `my_whispers`, whisper in-phase tokens, the `{agent1}` pairing
  family). Per-phase correctness cannot be derived from that phase-blind set
  and is instead pinned by handler-anchored unit tests (one per map row).
- #920 (A) — tightening `BundledPresetPlaceholderCoverageTests` — is
  **subsumed**: R10/R11 + the batch gate (D6) are strictly stronger.
- #920 (B) — phase-aware `PhaseEditorSheet` hint — stays open, retargeted to
  read the linter-owned map. #920 gets a scope-update comment, not a close.
- #919 (authoring-style guideline: field counts, agent counts) is *taste*, not
  reachability — per D2's leniency boundary it is **not** absorbed; it stays a
  docs task.

### D5 — Boundary and call-site placement (unchanged #665 posture)

`ScenarioLoader.load` stays non-validating. The linter runs wherever
`ScenarioValidator.validate` already runs:

| Site | Behavior |
|---|---|
| `ScenarioEditorViewModel.validate()` / `save()` | lint errors → `validationErrors` (blocking, as today); warning/info display deferred to the follow-up PR |
| `ScenarioDetailViewModel.load` | lint errors gate `canRun` like validation errors |
| `SimulationRunner.executeSimulation` | lint errors emit `.error(.scenarioValidationFailed)` and no round runs; warnings → `.summary("⚠️ …")` events (existing channel) |
| Preset ingest / gallery install | unchanged (no load-time gate today; the run gate + D6 batch verification cover these — installing stays cheap and the ADR-020 gate already ran) |

Finding messages are user-facing → `String(localized:)` with ja catalog
entries in the same PR (the `localization-coverage` CI gate is unconditional,
so i18n cannot be deferred to a follow-up).

### D6 — Batch verification: `pastura-harness lint` subcommand + CI

An inference-free `lint` subcommand on `pastura-harness` (reuses
`ScenarioLoader` + `ScenarioValidator` + `ScenarioSemanticLinter`; no
`--model`):

```
swift run pastura-harness lint Pastura/Pastura/Resources/Presets docs/gallery
```

Per file: parse → validate → lint. Exit non-zero on any parse failure,
validator failure, or error-severity finding; warnings listed but non-fatal.

**Acceptance (met before merge)**: the 46 shipped YAMLs (8 presets + 38
gallery) produce **zero false positives**. The initial batch fired 6 warnings:
4 were one true positive class (`{vote_winner}` literal leak in
`detective_scene` ja/en — YAML reworded in this PR) and 2 were one false
positive class (R11's strict `<` on a same-conditional producer/consumer pair
in `kasei_sanso_touban` ja/en — rule tuned to `<=` with a regression test).
Final result: **46 files, 0 errors, 0 warnings**.

Coverage caveat: no shipped YAML uses `score_calc: event_reactive` (R5) or
`relationship_update` (R4), so those rules are unexercised by the inventory —
R5 carries synthetic clean/violating fixture YAMLs through the full
load→lint harness path, R4 through unit fixtures, so "zero findings on the
inventory" is not mistaken for "rule verified". A CI job invoking the batch
lint over both globs lands in the follow-up PR and pins zero-regression.

## 3. Consequences

- Authors and curators hit silent-no-op traps at edit/validate time instead of
  reading a clean transcript that quietly did nothing. The gallery batch
  already caught one real shipped bug (`detective_scene`).
- Two findings channels now exist (`ScenarioContentValidator`, linter); they
  stay separate — content safety (App, MainActor, blocklist) vs semantics
  (Engine, nonisolated). A future unification of finding types is possible but
  not needed now.
- New rules must pass the D2 leniency test before admission — the catalog is
  the contract, and severity promotions (warning → error) follow the D2
  warn-first policy and re-run the D6 batch gate.
- The availability map adds a maintenance point: a new handler-supplied
  placeholder must update the map (union test + handler-anchored row tests
  fail otherwise).

## 4. Alternatives considered

- **Severity-aware `ScenarioValidator` rewrite** — rejected: churns four call
  sites and the fail-fast contract for no expressiveness the separate linter
  doesn't provide.
- **Runtime-only enforcement (upgrade handler `.debug` logs to `.summary`
  warnings)** — rejected: fires mid-run, after the author walked away; useless
  for gallery curation and batch verification.
- **Fixing the runtime instead (reset `voteResults` per round, error on empty
  producers)** — rejected for this ADR: behavior changes ripple into shipped
  scenarios and ADR-020 semantics-bump policy; lint-first is additive and
  reversible.
