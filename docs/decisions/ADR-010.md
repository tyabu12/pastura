## Decision

Eleven decisions, organized lowest-level (data shape) → highest-level
(cross-cutting policy). Decisions 7, 9 are inherited verbatim from the
stub (PR #279); D1 retains the stub's field name / values but **revises
the absence semantics** (now mandatory, was BC-filled to `"ja"`); D2 is
**replaced** (Phase 1 BC rule → device-locale-derived seed); D3, D4,
D5, D6, D8, D10, D11 are new — five of them close stub Open Questions,
D8 makes the dependency-rule guarantee normative, D11 documents the
Phase 1 → Phase 2 migration policy that replaces the rescinded BC
rule.

### D1. Scenario YAML `language` field — mandatory attribute

**(revised from stub)** The field is named `language` and accepts an
ISO 639-1 lowercase code (`ja`, `en`). The field is **mandatory in
all scenario-shaped YAML data** (bundled presets, gallery seed YAML,
shared-scenario distribution payloads, user-authored YAML,
DL-time demo replay YAML); absence is a **validation error**, not a
default-fill trigger. The stub's "absent → `ja`" Phase 1
backward-compat rule is **rescinded** (see D2 for the replacing
policy and Alternatives row κ for the rejection rationale).

The field is **parsed by `ScenarioLoader` and acted upon by the
Engine at runtime** (see D7). It is not "parse-only" — Step C-1's
DoD requires `scenario.language = "ja"` to drive Japanese Engine
output and `"en"` to drive English. Contrast with D5
(`simulation_language`), which *is* parse-only in C-1.

Storage shape: extends `Models/Scenario.swift` with
`public let language: String` (non-optional). `Scenario.init(...)`
takes `language` as a **required named argument** — no default
argument. This is a deliberate compile-surface change: every
fixture / preview / stub callsite must spell out the language,
making test data self-describing and preventing accidental locale
divergence between fixture intent and runtime. D11 documents the
migration of existing callsites.

`ScenarioLoader` raises a `SimulationError.scenarioValidationFailed`
on `language`-absent YAML, with the same idiom as other validation
errors (`name is required`, `agentCount must match personas.count`).

### D2. Device-locale-derived default — runtime seed only

**(revised from stub — replaces the Phase 1 backward-compat rule)**
Pastura derives a **device-locale-based default language** from
`Bundle.main.preferredLocalizations.first`:

- device's effective Pastura locale = `"ja"` → seed value `"ja"`
- any other effective locale (incl. `"en"`, `"fr"`, `"zh-Hans"`, …)
  → seed value `"en"`

The "effective Pastura locale" is the value Apple's resolver returns
given Pastura's `knownRegions = {en, ja}` (already in
`Pastura.xcodeproj/project.pbxproj`, verified at ADR authoring time)
and the device's `preferredLanguages` list —
`Bundle.main.preferredLocalizations` already does the narrowing.

The resolver lives at the **fixed path
`Pastura/Pastura/App/LocaleResolver.swift`** (App layer). It **MUST
NOT** live in `Engine/`, `LLM/`, `Models/`, `Data/`, or `Utilities/`:

- `Engine/` / `LLM/` / `Models/` / `Data/`: D8's normative
  `Bundle`-prohibition forbids it; these layers must reject
  `language`-absent YAML rather than fall back via the resolver.
- `Utilities/`: per CLAUDE.md `## Dependency Rules`, Utilities depends
  on nothing — including Foundation `Bundle` is technically allowed,
  but placing a locale-resolving utility there blurs the App-vs-pure
  utility line. App layer is the right home: the resolver is an
  app-level policy artifact, not a stateless helper.

**This default is consumed only at runtime data-creation seams**
(see D6 for the precise consumer table). It is **not** a fallback
for missing fields in stored YAML — D1 makes such absence a
validation error. The two intents are explicitly separated:

| Concern | Mechanism |
|---|---|
| "What language does this scenario speak?" | `scenario.language` field (mandatory per D1) |
| "What language should a *newly created* scenario start as, or which *of multiple available variants* should the picker surface first?" | This device-locale default seed (D2) |

The stub's Phase 1 BC rule (silent `"ja"` fill on absent field) is
**rescinded**. Existing Phase 1 bundled presets, gallery seed YAMLs,
and DL-time demo replay YAMLs get `language: ja` **explicitly
appended** as part of Step A. Existing `ScenarioRecord` DB rows on
testers' devices are not migrated — testers reinstall the app for
Step A's UI changes, so the install-base reset absorbs the schema
break. (User-authored YAML stored in DB on a current TestFlight
build is intentionally allowed to be lost across reinstall — see D11
for the full migration policy.)

### D3. Per-language scenario YAML file layout — sibling files

**(closes stub Open Question)** Per-language scenarios live in
**sibling files** with a `_<lang>` suffix on the filename, not in a
single multilingual YAML. Example: `word_wolf.yaml` (Japanese) and
`word_wolf_en.yaml` (English) coexist under
`Pastura/Pastura/Resources/Presets/`.

Each file is a complete scenario in one language — same `phases`,
`personas`, `rounds` structure, with all user-facing strings (`name`,
`description`, `context`, `prompt`, `template`, `personas[].background`,
`personas[].goal`, `extraData` string values) in the target language.

The file itself declares its language via `language: en` (or `ja`).
The filename suffix is convention, not load gate — the loader trusts
the YAML field.

**Why sibling files over a single multilingual YAML.** (a) Diffing a
single-language edit stays localized to one file. (b) Bundled-preset
drift between languages is auditable per-file
(`scripts/check_demo_replay_drift.py` extends from `REQUIRED_LANGUAGE`
to `ALLOWED_LANGUAGES = {"ja", "en"}` per ROADMAP Step C-2). (c) The
DL-time demo replay (Step D) can ship per-language bundled YAML
without forcing a runtime language-switch mid-replay. (d) Translation
quality for `personas[].background` is acceptable in self-contained
files but degrades in mixed multilingual blocks.

### D4. Per-language scenario IDs reuse `ScenarioRecord.sourceId`

**(closes stub Open Question)** Per-language scenarios have
**independent primary keys** in `Pastura/Pastura/Data/Models/ScenarioRecord.swift`'s
`id` column. The cross-language canonical link reuses the existing
`sourceId: String?` column — no GRDB migration required.

Concrete shape:

| `id` (PK)        | `sourceId`   | `language` (via `yamlDefinition`) | Notes                          |
|------------------|--------------|-----------------------------------|--------------------------------|
| `word_wolf`      | `word_wolf`  | `ja`                              | Phase 1 baseline, unchanged    |
| `word_wolf_en`   | `word_wolf`  | `en`                              | New in Step D                  |

`SimulationRecord.scenarioId` (the FK to `ScenarioRecord.id`) keeps
referencing the per-language `id` — Past Results queries by exact `id`
return the same simulation rows they did in Phase 1. Cross-language
queries (e.g., "show me all results for any word_wolf variant") group
by `sourceId`.

For locally-authored scenarios that never get translated, `id ==
sourceId` (existing Phase 1 behavior) — D4 introduces no new burden on
single-language users.

This reuses the column that the inline doc on
`ScenarioRecord.swift:30-34` already named for "future namespacing
schemes or multi-source provenance" — D4 makes that future concrete.

### D5. `simulation_language` schema + Engine wiring via `Scenario.engineLanguage`

**(closes stub Open Question; Engine wiring implemented in Step E PR1)**
`simulation_language` is parsed and schema-validated in Step C-1 and
**propagated to the Engine in Step E PR1**. Storage shape: an optional
sibling on `Scenario` — `public let simulationLanguage: String?` —
accepting `"ja"`, `"en"`, or absent (`nil`).

Step C-1 loader behavior (shipped in PR #383):
- Parse top-level YAML key `simulation_language` if present.
- Validate against `{ja, en, nil}`; reject other values with a
  `SimulationError` matching the existing validation idiom.
- Store on `Scenario.simulationLanguage`.

Step E PR1 Engine wiring:

The override resolves at a **single Models-layer point**:

```swift
extension Scenario {
  /// Engine-consumer resolver per D6 row 1.
  public var engineLanguage: String { simulationLanguage ?? language }
}
```

Every Engine site in the D7 Translation Table reads
`scenario.engineLanguage` (or `context.scenario.engineLanguage` from
inside a `PhaseHandler`) instead of `scenario.language`. The previous
`scenario.language` reads in `PromptBuilder`, the 6 LLM phase handlers,
`ScoreCalcHandler`, and `WordwolfJudgeLogic` flip to
`engineLanguage` in PR1.

The resolver is named `engineLanguage` (not `effectiveLanguage`) to
encode single-consumer scope in the name — D6 has four consumer rows,
each with a different resolver, and a generic `effectiveLanguage`
would invite misuse from UI / Editor / Picker callsites that **must**
continue using their own D6 resolvers (device locale-derived,
preset-variant selection, etc.).

Two authoring-axis Engine sites are intentionally **excluded** from
the rename and continue reading `scenario.language` directly:

- `ScenarioValidator` validates the **authoring** language field —
  the `simulation_language` override has its own validator path and
  doesn't substitute for `language` in validation.
- `ScenarioSerializer` writes the authoring `language` field back to
  YAML — round-tripping must preserve the file's declared language,
  not the runtime override.

A CI script (`scripts/check_engine_language_axis.sh`) verifies that
no Engine file outside the two authoring-axis allow-listed sites uses
`scenario.language` / `context.scenario.language` in `pickLanguage(`
or `formatConversationLog(language:` argument position. The script
locks D8's Engine-deps guarantee + this D5 wiring into a CI-checked
shape rather than relying on PR-review-only enforcement.

**D8 invariant preserved**: `Scenario.engineLanguage` is a pure
`String`-typed computed property; resolving it imports zero
`Foundation.Bundle` / `Foundation.Locale` / `LocaleResolver` symbols.
Engine continues to read only `Scenario` fields.

LLM output-language **adherence enforcement** (the LLM actually
*emits* in the requested language) ships in **Step E PR2** with the
following contract:

- **Detector abstraction.** A `LanguageDetector` protocol existential
  (`Pastura/Pastura/LLM/LanguageDetector.swift`) keeps Engine / LLM /
  Models / Data layers free of `NaturalLanguage` per D8. The
  production concrete is `NLLanguageDetector`
  (`Pastura/Pastura/App/NLLanguageDetector.swift`, Apple
  `NLLanguageRecognizer` with `languageHypotheses(withMaximum: 1)` and
  confidence threshold ≥ 0.5). A new CI guard
  (`scripts/check_naturallanguage_axis.sh`) blocks future
  `import NaturalLanguage` regressions in the four guarded
  directories.
- **Detection input filter.** Adherence is checked against the joined
  values of `OutputSchema.Field.kind == .string` fields only;
  `.enumeration(...)` fields (e.g., `action` on choose phases) are
  excluded because their values are author-supplied tokens rather
  than LLM-emitted language. Joined input below 12 codepoints skips
  the check and emits a `StreamingDiag langCheckSkipped agent=…
  reason=too_short` line.
- **Retry / event semantics.** `LLMCaller.call(detector:expectedLanguage:)`
  runs the check **after** `parse_failed` and `empty_field` in the
  existing `maxRetries=2` budget. On mismatch the retry-cause analyzer
  line is `retryCause cause=language_mismatch`; on exhaustion
  `SimulationEvent.languageMismatch(agent:detected:expected:)` is
  emitted **and** the parsed `TurnOutput` is still returned — sim
  continues, structurally distinct from `parse_failed` /
  `empty_field` exhaustion which throws.
- **Plumbing.** `SimulationRunner.init(detector:)` →
  `ExecutionContext.detector` → `PhaseContext.detector` (new optional
  8th property, default nil) → 4 LLM handlers + `ConditionalHandler`
  subContext propagation. Default-nil keeps existing tests / callers
  on the pre-Step E PR2 retry semantics; the production wiring point
  is `SimulationView.swift`'s `SimulationViewModel` construction,
  which injects `NLLanguageDetector()`.
- **Measurement, not threshold.**
  `PasturaTests/Localization/LanguageAdherenceBenchmark.swift`
  (env-gated by `LANGUAGE_ADHERENCE_BENCHMARK=1` +
  `LLAMACPP_QWEN_MODEL_PATH`) is the harness developers run when
  adopting a new model. ADR-010 deliberately does NOT pin per-model
  `N%` / `M%` thresholds — locking a Qwen-measured floor would
  hard-bind ADR-010 to one model, conflicting with Pastura's
  multi-model trajectory (ADR-002, multi-model PR #218, LiteRT-LM
  planned). Adoption-time judgement reads the benchmark's CSV log
  (`LANG_BENCH preset=… agent=… parsedOK=… adherent=…` plus
  `LANG_BENCH_SUMMARY preset=… parseRate=… adherenceRate=…`) and
  evaluates per model per cycle.

### D6. Language resolution priority — scoped by consumer

**(new — promotion of stub Open Question implied by ROADMAP Step D)**
This refines ROADMAP § Localization Plan's single-chain priority
(`simulation_language > scenario.language > Bundle.main.preferredLocalizations`)
into **per-consumer resolvers**. The chain semantics never collapse
across consumers in practice — Engine never reaches `Bundle.main`.
ROADMAP's chain notation is shorthand; this ADR is the authoritative
expansion. (Follow-up: C-1 PR replaces ROADMAP's chain with a
back-pointer to this section.)

The effective language is resolved differently per consumer. There is
no single global resolver:

| Consumer                                       | Resolver expression                                              |
|------------------------------------------------|------------------------------------------------------------------|
| **Engine** (prompt / scoring / default text)   | `scenario.simulationLanguage ?? scenario.language` (Step E adds the override; C-1 collapses to `scenario.language`) |
| **New scenario creation seed** (Editor initial `language` value) | `LocaleResolver.deviceDefault()` from D2 (App layer) — sets the Editor's initial `language` value when the user starts authoring a new scenario; user can override via the field before saving |
| **Preset / gallery initial language selection** (which language variant to surface first) | `LocaleResolver.deviceDefault()` from D2 — matched against available variants of the same `sourceId` (Step D); falls back to any available variant if the device-default's variant is absent. **Layer split**: `ScenarioRepository.variants(of: sourceId)` (Data layer) returns ALL rows regardless of `language`; the **picker View / App-layer ViewModel** applies `LocaleResolver` to choose which row to surface. Repository code never imports `LocaleResolver`. |
| **UI shell** (`Localizable.xcstrings`)         | `Bundle.main.preferredLocalizations` (Apple's standard `String(localized:)` resolution) |

The device-locale-derived default (D2) **seeds new-data creation and
multi-variant selection**, never **fills missing fields in stored
YAML** (D1's mandatory rule applies there). Engine reads only
`scenario.language` and `scenario.simulationLanguage` from `Scenario`
— it never invokes `LocaleResolver` or any `Bundle.main` path.

The consumers are intentionally decoupled. A user on a `ja`
device can pick an `en` preset and run it with
`simulationLanguage: en` — the UI shell stays Japanese, the preset
picker had already shown an `en` row in its default sort, the Engine
emits English.

**`Bundle.main.preferredLocalizations` is read only in App / Views
layers.** Engine never imports `Bundle`. This guarantee is normative
in D8.

### D7. Engine hardcoded-Japanese strategy: Y (dynamic per `scenario.language`)

**(inherited from stub, body specifies the per-site table)** The
Engine reads `scenario.language` and emits the appropriate language at
each user-facing site. The translation contract per site is the
**Translation Table** below; this decision records *what* gets
localized and the strategy, not *how* the implementation dispatches
(helper function naming, switch vs. dictionary, etc., are Step C-1 PR
scope — the ADR's Editability window covers the strategy, not the
code shape).

Strategy X (`Localizable.xcstrings`-based) is rejected for two
compounding reasons (the stub recorded the first; this body adds the
second):

1. **Locale mismatch:** Apple's `String(localized:)` resolves against
   `Bundle.main.preferredLocalizations` (device locale). An `en`
   scenario on a `ja` device would emit Japanese prompt text —
   incompatible with Step E's cross-language goal and with running an
   `en` scenario on a `ja`-device tester.
2. **Dependency-rule break:** `Localizable.xcstrings` resolution requires
   reading `Bundle.main`, which Engine cannot import per CLAUDE.md
   Dependency Rules (Engine → LLM, Models only). Engine types are
   `nonisolated` per CLAUDE.md `## Default Actor Isolation`; pulling
   in App-layer Bundle access erodes that boundary even when the
   specific call shape avoids the named traps in
   `.claude/rules/swift-isolation.md`.

### D8. Engine dependency-rule guarantee

**(new — critic-driven normative addition)** Strategy Y maintains
Dependency Rules: Engine reads `Scenario.language: String` (Models
layer, `nonisolated`) and nothing else. **Engine does not import
`Bundle`, `Locale`, `Foundation.LocaleResolver`, or any App / Views
type.**

The Engine receives the resolved language as a member of `Scenario`
(D6's resolver runs in App / Models before Engine starts the
simulation; Engine sees only the final string). Step E does not relax
this — the `simulationLanguage` override is also a `Scenario` field.

This guarantee is verified in PR code review against CLAUDE.md
`## Dependency Rules` (manual review — there is no automated
import-graph lint today). Any Step C-1 / Step E PR that adds
`import Bundle` or equivalent App-layer access to an Engine file
violates the ADR.

**`String(localized:)` usage inside Engine / LLM / Models / Data
layers** is restricted by output binding, not banned outright:

- **Scenario-language-bound output** (PromptBuilder prompts,
  WordwolfJudgeLogic summaries, handler default fallbacks, anything
  the LLM consumes or the user sees as simulation content) — Engine
  switches on `scenario.language` and emits literal text directly
  via `switch` / `if`, **without** `String(localized:)`.
  `String(localized:)` would resolve against device locale (via
  implicit `Bundle.main`), which is the wrong axis for these strings.
- **Device-locale-bound output** (`LocalizedError.errorDescription`
  on `SimulationError` / `LLMError` / `DataError`, per CLAUDE.md
  `## Swift Coding Conventions` "Error message i18n prep") — Engine
  types may use `String(localized:)` because these strings are
  displayed by App / Views in device locale, not by Engine in
  scenario language.

The two axes never collide: error messages are never sent to the LLM
or shown as simulation content; prompts and summaries are never
displayed as alert text. C-1 PR review applies this split: any
`String(localized:)` in a *prompt or summary path* is a violation;
any `String(localized:)` on an `errorDescription` is required by
CLAUDE.md.

### D9. `Localizable.xcstrings` scoping boundary

**(inherited from stub)** Step A's xcstrings sweep stops at the
Views/ + App/ boundary. Engine, LLM, Models, Data layers retain
`nonisolated` per CLAUDE.md and handle their own language switching
via D7.

This boundary is enforced operationally by Step A's audit list (per
ROADMAP Step A details); future Engine-touching i18n work must use D7,
not xcstrings.

### D10. ContentFilter — full-set application regardless of UI locale

**(closes stub Open Question)** `ContentFilter` applies the **full
blocklist** to all simulation output, regardless of `scenario.language`
or device locale. There is no per-language filtering subset.

Rationale: ADR-005 (Content Safety) treats the blocklist as a
correctness gate, not a localization layer. The blocklist contains
patterns across both languages (`docs/blocklist/source.json` `lang`
field is metadata for human auditors per Step A's absorbed B-2
scope — it is not consumed by the runtime filter). An `en` scenario
on a `ja` device must reject Japanese blocklist hits in the LLM
output stream, even if Japanese should not naturally appear (the
filter is a safety net, not a language-purity validator).

Future per-language blocklist tuning (e.g., language-specific severity
thresholds) is out of scope for ADR-010 and would warrant a separate
ADR amending ADR-005.

**Why no automated DB migration:** the testers' user-authored
scenarios are small in count (TestFlight had **~5 active testers as of
2026-04-13 per #36 conditional Go** — the number was 1 month stale at
ADR body authoring) and the Phase 1 → Phase 2 UI discontinuity already
requires a reinstall for unrelated reasons. The complexity of a
`yamlDefinition` re-parse + `language` injection GRDB migration (v3)
is disproportionate to the value of preserving ~handful of
locally-authored scenarios.

**Revisit trigger:** C-1 PR author re-confirms the active tester count
before Step A merges. If TestFlight grew to ≥ 3× the 2026-04-13
baseline (15+ active testers) **and** any meaningful fraction have
locally-authored scenarios, reconsider Alternatives row κ (GRDB
migration v3).

## Translation Table

Per-site contract for D7. Each row enumerates one Engine string-site:
file path, function / member, Japanese literal, English literal, and
the language-input source. Code shape (helper API, dispatch
mechanism) is Step C-1 PR scope and intentionally not prescribed.

Format-string placeholders (`%@`, `%lld`) keep their positional

### Fallback rule

`scenario.language` is **non-optional** (D1) and validator-gated
(D11 test item 5 rejects unrecognized values at load), so Engine code
treats the type as effectively `{"ja", "en"}`. Recommended switch
shape:

```swift
switch scenario.language {
case "en":
  // English literal
default:
  // Japanese literal (covers "ja"; validator rejects anything else)
}
```

No `@unknown default` — that attribute is enum-only (SE-0192) and
inapplicable to `String` switches. No third defensive arm for
"unrecognized values" — the validator owns that gate, and adding an
unreachable arm at all ~22 Translation Table sites would create dead
code surface without correctness benefit.

## Alternatives Considered

| | Approach                                                                                       | Verdict                                                                                                                                                                                                                                  |
|---|------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| α | Engine uses `Localizable.xcstrings` + `String(localized:)` for scenario-language-bound output  | **Rejected.** D7 §1 (locale mismatch — `Bundle.main` resolves to device locale, wrong axis for `scenario.language`) and D7 §2 (dependency-rule break — `Bundle` access erodes Engine `nonisolated` boundary). Note: `String(localized:)` on `LocalizedError.errorDescription` is fine per D8 — error messages are device-locale-bound, not scenario-language-bound. |
| **β** | **Engine emits language dynamically per `scenario.language`** (Strategy Y)                  | **Accepted** as D7. Preserves Engine `nonisolated`, enables cross-language simulation, keeps the dependency graph clean.                                                                                                                 |
| γ | Single multilingual YAML file per scenario with inline ja/en strings                           | **Rejected** in D3. Diff legibility degrades for single-language edits; bundled-preset drift audit ambiguous; DL Demo Replay (Step D) language switch mid-replay surprising; translation quality of `personas[].background` poor in mixed blocks. |
| δ | Per-language scenario IDs without `sourceId` alias (new GRDB column)                           | **Rejected** in D4. The existing `ScenarioRecord.sourceId` already targets exactly this use case ("future namespacing schemes or multi-source provenance" — `ScenarioRecord.swift:30-34`); adding a column duplicates the slot.            |
| ε | Engine reads `Bundle.main.preferredLocalizations` as final fallback                            | **Rejected** in D6 / D8. Breaks Dependency Rules (Engine → Models only) and erodes the `nonisolated` boundary; collapses the consumer-scoped resolver into a global one, defeating cross-language simulation on a non-matching device.       |
| ζ | `simulation_language` wired in C-1 (not just parsed)                                           | **Rejected** in D5. Bundling C-1 with cross-language Engine output enforcement balloons C-1 scope and conflates "preset bilingual coverage" (D, required for App Store launch) with "cross-language adherence quality" (E, post-launch).  |
| η | Per-language `ContentFilter` subsets keyed by `scenario.language`                              | **Rejected** in D10. The blocklist is a safety gate, not a language-purity validator; language-specific severity is a future ADR-005 amendment.                                                                                          |
| θ | Keep the stub's Phase 1 BC rule (silent `"ja"` fill on absent `language`) — `language` field is optional in YAML, `ScenarioLoader` substitutes `"ja"` | **Rejected** in D1 / D2 / D11. Two compounding problems: (a) on `en`-locale devices, a Phase 1 preset (`prompt`/`context` written in Japanese, `language` absent) would be silently treated as `"ja"` — fine semantically — but Step D's English bundled presets would also be defaulted to `"ja"` if anyone forgot the field, masking authoring bugs. The mandatory rule (D1) catches such omissions at load time. (b) Conflates the "what language is this data?" question with the "what locale does the user prefer?" question — D2's redefined seed semantics keep these orthogonal. Step A's bundled-preset / gallery-seed / demo-replay edits absorb the BC migration cost (D11). |
| ι | Optional `language` field with **device-locale-derived** fill on absence (no Phase 1 BC pin) | **Rejected** in D1. Solves the en-locale-tester problem from θ (en-device sees `language: en` on Phase 1 ja prompts → at least the mismatch is visible) but makes test data flaky (CI runner locale changes flip the default). Mandatory-field + explicit migration (D11) wins: data self-describes; tests are deterministic. |
| κ | DB migration v3: re-parse `ScenarioRecord.yamlDefinition` and inject `language: ja` on existing rows | **Rejected** in D11. TestFlight tester base is small (~5 active per #36), Step A's UI changes already require a reinstall that resets local state, and the v3 migration adds GRDB code surface (parser invocation, error handling, rollback) without commensurate user benefit. Release notes call out the reinstall-required loss explicitly. |

## Consequences

**Positive**

- Step C-1 implementation has a fully-specified target: 11 decisions,
  ~22 translation sites, 9 DoD bullets, no Open Questions remaining.
- **Data self-describes.** Every Scenario YAML in the codebase
  (preset / gallery / demo replay) carries an explicit `language`
  field after Step A's migration. Mandatory-at-load (D1) prevents
  Phase 2+ authoring bugs (forgotten field, locale mismatch between
  prompt text and language declaration) from passing silently.
- **Tests are deterministic.** No `Bundle.main.preferredLocalizations`
  dependence in test data — every `Scenario.init` explicit, CI
  runner locale irrelevant to test outcomes.
- Step C-2 inherits a concrete schema (sibling files, sourceId alias)
  and unblocks `scripts/check_demo_replay_drift.py` extension.
- Step D inherits a concrete preset picker rule (D6 middle row) and
  bundled-YAML layout (D3).
- Step E's `simulation_language` wiring inherits a schema that already
  parses and validates correctly — no forward-compat break.
- The dependency-rule guarantee (D8) is normative, so any C-1 / E PR
  introducing `Bundle` to Engine is detectable in code review against
  the ADR text, not just CLAUDE.md.

**Negative**

- The Translation Table is now a maintenance surface: any new
  Engine-side user-facing string requires both a new row and a C-1
  follow-up. Mitigation: re-running the audit grep before each Engine
  edit (covered by `.claude/rules/i18n.md`'s leak detection workflow,
  Tier 2 audit script).
- `ScenarioRecord.sourceId` semantics expand from "gallery provenance"
  to "gallery provenance OR cross-language alias." A scenario that is
  both gallery-sourced and translated needs careful sourceId handling
  in Step D / curation. C-1 should not block on this — it surfaces
  in Step D / Phase 3 marketplace work. **Resolution candidates to
  evaluate when Step D adds gallery-distributed English presets:**
  (i) branch `sourceId` semantics on `sourceType` (when `"gallery"`,
  `sourceId` = gallery canonical id; when `nil`, `sourceId` =
  cross-language alias); (ii) add a third column `translationOf:
  String?` that carries the cross-language link, freeing `sourceId`
  to keep its Phase 1 gallery-provenance meaning; (iii) gallery
  schema carries per-language ids as a separate field
  (`languageVariants: [String: String]`), with `sourceId` always the
  canonical gallery id. Each candidate has different migration cost
  and Past Results compat profile; Step D evaluates against the
  marketplace ADR-006 surface.
- `simulation_language` as a parsed-but-unused field for a release
  cycle (C-1 → Step E) carries a minor forward-compat risk: if Step E
  redesigns the override semantics, the field name / shape may need
  amendment. Mitigation: Step E's wiring is bounded to "override
  Engine language at runtime"; the schema shape (string ISO code, same
  values as `scenario.language`) is unlikely to change.
- **Phase 1 install-base data loss.** Current TestFlight testers who
  have authored local scenarios (saved in `ScenarioRecord` without
  `language`) lose those rows on Phase 2 reinstall. The tester base
  is small (~5 active per #36), Step A's UI changes require reinstall
  for unrelated reasons, and Step A release notes call out the loss.
  Mitigation: explicit release-notes communication; no automated
  GRDB migration (Alternatives row κ).

**Neutral**

- D3 (sibling files) is a convention. The loader trusts the YAML's
  `language` field, so a misnamed file (e.g., `word_wolf.yaml` with
  `language: en` inside) is not a load-time error but a curation
  hygiene issue, caught by Step C-2's drift script extension.
- The Translation Table's "en literal (proposed)" column is a draft.
  C-1's PR may revise individual strings during implementation review;
  the ADR's value is fixing the *set* of sites and the *language
  source* per site, not the exact English wording. Wording revisions
  inside C-1 are not ADR amendments.

## Out of Scope (Step E and beyond)

These items are deliberately deferred and **not** part of this ADR's
decisions:

- **Engine wiring of `simulationLanguage` override.** Implemented in

  `scripts/check_engine_language_axis.sh`.

  contract. Per-model adherence / parse thresholds are deliberately
  **not** pinned in ADR-010 — locking a Qwen-measured floor would
  hard-bind ADR-010 to one backend and conflicts with multi-model
  / LiteRT-LM trajectories. Adoption-time evaluation reads the
  benchmark harness output (`LANG_BENCH_SUMMARY` lines) per model
  per cycle.

  — Implemented in Step E PR2 (PR #405). Env-gated by

  `LLAMACPP_INTEGRATION` (real-LLM cost vs. 10-minute CI budget).
- **`.languageMismatch` UI surfacing.** Tracked in #401. PR2 emits
  the event and drains it through `SimulationViewModel` with a
  `case .languageMismatch: break` marker; the in-app surface (toast /

- **Per-language blocklist tuning** (D10's deferred extension).
- **Languages beyond `ja` / `en`.** Out of scope for Phase 2 entirely;
  a future ADR would handle a third language by extending D1's
  accepted values, D3's filename suffix convention, D4's id /
  sourceId scheme (already extensible), and the Translation Table.
